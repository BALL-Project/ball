Verdict: NEEDS-REVISION

1. D-HC2 does not lock PDB record-kind/segment-id policy cleanly and contains a false premise (`V22-H1bPRIME-DESIGN.md` §2, §4, §9; `V2X-HIERARCHY-COLLAPSE.md` §2a). The doc says there is "no" HETATM accessor/field on `PDBAtom` and therefore HETATM maps only to `ResidueKind`, but `include/BALL/KERNEL/PDBAtom.h` defines `PDBAtom::PROPERTY__HETATM` and `source/FORMAT/PDBFileDetails.C` sets it on HETATM parse. The writer currently derives HETATM from `Residue::PROPERTY__AMINO_ACID`/`NON_STANDARD`, so the design may still choose residue-level normalized HETATM, but it must say explicitly that the atom-level HETATM bit is intentionally discarded/normalized. This is also a direct tension with HC1b §2a/HCP-0, which list ATOM/HETATM record kind and segment id among PDB atom fields to decide. §2 omits segment id entirely and turns record kind into `ResidueKind`; that is a lock mismatch, not an H3 detail.

2. D-HC2's PDB serial/CONECT claim is underspecified (`V22-H1bPRIME-DESIGN.md` §2, §9). The reader maps input `record.serial_number` to `PDB_atom_map_` for CONECT, but the writer currently assigns fresh coordinate serials via `atom_info.number` and writes CONECT from `atom_map_` keyed by output order (`source/FORMAT/PDBFileDetails.C` parse/write CONECT paths). If `serial` becomes an atom column, the design must define whether it preserves input serials, stores writer-assigned serials, or is merely a transient parse key, and how duplicate/missing/non-canonical serials are normalized. "CONECT round-trip needs stable serials" is not enough to implement safely.

3. D-HC5 overstates the iterator shim as behaviour-compatible (`V22-H1bPRIME-DESIGN.md` §3, §6, §7; §4 matrix row 1). Current typed iterators are `CompositeIterator`-based and include residues under the current owning tree, including the v0 `Chain -> SecondaryStructure -> Residue` shape. After D-HC4, residues are owned by chains and SS is an annotation sibling. A plain role-filtered `fragments(role=RESIDUE)` view can preserve broad "iterate residues of a protein/chain/system" cases, but it does not define compatibility for `SecondaryStructure::beginResidue()`/`rbeginResidue()` style consumers such as PDB HELIX/SHEET/TURN writing. The lock needs an explicit scoped view contract: order, depth traversal, mutation/erasure behavior, and what a residue iterator over an SS annotation returns.

4. D-HC4's SS span model is close but leaves overlap/reverse lookup ambiguous (`V22-H1bPRIME-DESIGN.md` §7, §9; `V2X-HIERARCHY-COLLAPSE.md` §2a). `{chain_ref, first_residue_ref, last_residue_ref}` is sufficient for single-chain HELIX/TURN and for individual SHEET strand records if each strand is represented as its own SS annotation. However §7 does not lock sheet payload (`sheet_id`, `strand_number`, `sense`) there, and makes the residue-ref list "optional" for non-contiguous annotations. Since overlap is allowed while v0 `Residue::getSecondaryStructure()` returns a single parent, the design must define `secondaryStructureOf(residue)` semantics under overlapping annotations: first match, primary annotation, list-returning API, or compatibility-only single result. Otherwise the reverse lookup migration is not locked.

5. D-HC1 terminal derivation is too broad as written (`V22-H1bPRIME-DESIGN.md` §1, §5, §6). The doc says N/C-terminal means first/last among a chain's role=RESIDUE children, but the existing helpers explicitly find the first/last residue marked `PROPERTY__AMINO_ACID` (`include/BALL/KERNEL/residue.h` free `getNTerminal`/`getCTerminal`). With `ResidueKind` now including WATER/LIGAND/ION/NONSTANDARD, first/last residue in a chain is not equivalent to first/last polymer residue. Lock this as first/last role=RESIDUE with polymer kind (`AMINO_ACID`, and likely `NUCLEOTIDE` where applicable) or document a deliberate semantic break.

6. The §4 matrix spot-checks are mostly sound but should be tightened as gate evidence (`V22-H1bPRIME-DESIGN.md` §4). `insertParent` being `PDBFileDetails.C`-only is confirmed. Branch/remoteness have no non-test consumers except parse-time population and pyBALL/test bindings, so dropping them is defensible under normalized fidelity. The "AtomContainer casts may survive as non-Atom check" claim is plausible for VIEW, but there are non-VIEW call-sites (`molecularInformation.C`, `system.C`, `sideChainPlacementProcessor.C`, `MOL2File.C`) that are not all just presentation-level "container-ness"; do not let the matrix imply this can be deferred blindly to VIEW/H7.

7. D-HC7 is acceptable but should carry a warning in the lock (`V22-H1bPRIME-DESIGN.md` §10; `V2X-HIERARCHY-COLLAPSE-PLAN.md` §1, HCP-0 #10). Reusing `BALL_CORE_ONLY` is coherent with the desired "core only" semantics and avoids another flag, but it redefines a flag whose current behavior is effectively "everything except Python." The design should require the HCP-1 baseline to assert exactly which modules are excluded and update user-facing CMake docs/help text when the guards are restored.
