# Track A v2.2 Cluster R32 — Codex CLI Round 32 (2026-05-20)
**Status:** Complete
**Verdict:** NEEDS-FIXES -- do not start H1b until the D56 migration primitive is fixed
**Reviewer:** Codex CLI 0.128.0
**Subject:** v2.2 H1a close review (container metadata table + parity skeleton)

## Probe answers

**P32-1. D56 detached-container lifecycle + migration is not fully satisfied.** Container index remapping is structurally correct: `migrate_one_` allocates a fresh row, snapshots scalar payload/name/selection/generation, copies the source child vector before recursion, recursively allocates child containers, and links them with destination `ChildRef`s (`source/KERNEL/moleculeStore.C:451-489`). Reverse edges are rebuilt through `append_child` (`source/KERNEL/moleculeStore.C:376-380`, `source/KERNEL/moleculeStore.C:482`, `source/KERNEL/moleculeStore.C:488`), and strings are re-interned into the destination pool (`source/KERNEL/moleculeStore.C:455-469`).

Two D56 gaps remain. First, atom remap misses silently fall back to the old atom index (`source/KERNEL/moleculeStore.C:486-488`). That is unsafe for orphan->System migration because the old index addresses the source store, while the destination store may have a different atom at that slot. The primitive should require a complete atom remap for every atom child, or expose an explicit checked identity-remap mode for same-store tests only. Second, `migrate_subtree_from` is copy-only: `src` is `const`, source rows are never released, and the source reverse-edge state remains live (`include/BALL/KERNEL/_moleculeStoreInternal.h:628-631`, `source/KERNEL/moleculeStore.C:494-500`). That does not implement the D56 lifecycle claim that detached rows are migrated out of the orphan store. Container-property migration is explicitly deferred in the implementation (`source/KERNEL/moleculeStore.C:474-476`); that deferral is acceptable for H1a only because no production path writes container properties yet, but the header still claims properties are copied (`include/BALL/KERNEL/_moleculeStoreInternal.h:625-626`) and must be corrected.

**P32-2. D57 ordered ChildRef edges mostly match the contract, with one H2 risk.** The primitive ordered operations preserve vector order and set/clear reverse edges on the directly affected child: append/prepend/insertBefore/insertAfter call `set_reverse_edge_` (`source/KERNEL/moleculeStore.C:376-405`), and remove erases the matching edge and calls `clear_reverse_edge_` (`source/KERNEL/moleculeStore.C:407-416`). Missing-pivot fallback to append is defensible as a defensive H1a primitive because correct mirror wiring should supply an existing pivot (`include/BALL/KERNEL/_moleculeStoreInternal.h:561-567`). However, the operations do not protect against appending/inserting a child that is already attached elsewhere; that would leave the old parent's child vector containing a stale edge while the reverse edge points to the new parent. H2 mutation wiring must either call remove-before-insert consistently or add checked move/reparent helpers.

**P32-3. Reallocation/use-after-free review: no blocker found.** `migrate_one_` avoids holding a destination `ContainerRow&` across recursive allocation or `append_child` reallocation; it only holds `nrow` while interning strings and assigning scalar fields (`source/KERNEL/moleculeStore.C:464-473`). It copies `srow.children` before recursion (`source/KERNEL/moleculeStore.C:461-462`). The test mirror helper also allocates/fills the current row, then indexes by `idx` after recursive calls instead of holding a row reference (`test/HierarchyParity_test.C:98-114`). `preorder` recursively walks a vector by const reference (`include/BALL/KERNEL/_moleculeStoreInternal.h:605-616`); that is safe for read-only visitors, but should remain documented as non-mutating traversal.

**P32-4. D58 schema is aligned with current headers.** The implementation uses common `name_offset`, `id_offset` for Protein/NucleicAcid/Residue/Nucleotide, `insertion_code`, and `ss_type` (`include/BALL/KERNEL/_moleculeStoreInternal.h:477-510`). Residue and Nucleotide enum flags are properties in the existing headers (`include/BALL/KERNEL/residue.h:48-70`, `include/BALL/KERNEL/nucleotide.h:47-57`), so modelling them as container properties rather than payload fields is correct (`include/BALL/KERNEL/_moleculeStoreInternal.h:481-484`). Chain has no private `id_`; using the inherited common name and no Chain-specific payload string is correct (`include/BALL/KERNEL/chain.h:43-60`, `include/BALL/KERNEL/_moleculeStoreInternal.h:487-490`).

**P32-5. D59 selection counters and property registry are sound for H1a.** `bump_selection_up` walks `parent_container_idx` from the starting container to the root and clamps underflow at zero (`source/KERNEL/moleculeStore.C:425-439`). Container properties use a `PropertyColumnRegistry` keyed by container index (`include/BALL/KERNEL/_moleculeStoreInternal.h:592-596`), and the test writes a residue-flags column at the residue container index (`test/HierarchyParity_test.C:326-340`). The caveat is migration: properties are not copied yet despite the header comment saying they are.

**P32-6. The parity test is a credible H1a skeleton, but not a full D60 guardrail yet.** It does exercise allocation/free-list reuse, interning, ordered child operations, reverse atom/container parent edges, selection counters, container property columns, manual v0->table mirroring, payload parity, and migration (`test/HierarchyParity_test.C:187-445`). The manual mirror is meaningful for H1a because no production mirror wiring exists yet; it tests the table as a data structure rather than testing the future H2 wiring against itself. Untested gaps: missing atom remap entries during migration, source-row release after orphan migration, property migration, duplicate/reparenting misuse of `ChildRef` ops, and mutation-heavy v0 parity after automatic insert/remove/splice/swap/clear/setProperty/select. Those are H2 parity obligations, except the migration gaps are H1a gate issues.

**P32-7. Non-invasiveness holds.** `rg` finds `container_table_` only in the internal header, `moleculeStore.C`, the new parity test, and comments/test registration. No v0 consumer path reads or writes it. The table is a member of `MoleculeStoreSideTables` behind the existing `std::unique_ptr` PImpl (`include/BALL/KERNEL/_moleculeStoreInternal.h:663-689`), so public `MoleculeStore` and `Atom` object layout is not changed by adding the table. The targeted `HierarchyParity_test` passes under the existing build.

**P32-8. R31 follow-ups status.** Stale/alias detached-handle behavior remains open and becomes urgent before H1b exposes container value handles. Chain id-vs-name is addressed: no Chain id payload, common name only (`include/BALL/KERNEL/_moleculeStoreInternal.h:487-490`) and ledger note (`.planning/v2.2/V22-API-BREAK-LEDGER.md:156-158`). The concrete parity skeleton is addressed, with the limitations above. The API-break ledger is seeded with pointer returns, pointer containers, pointer comparison/ordering, nullptr sentinel use, `Composite*`/`AtomContainer*` params, RTTI flows, address/lifetime/delete assumptions, mutable property references, timestamps, and implicit upcasts (`.planning/v2.2/V22-API-BREAK-LEDGER.md:21-147`).

## New findings

- **HIGH -- atom remap misses silently produce wrong destination atom edges.** In `migrate_one_`, a missing `atom_remap` entry falls back to `c.idx` (`source/KERNEL/moleculeStore.C:486-488`). For real orphan->System migration this can attach the migrated container to an unrelated destination atom slot, and `atom_parent_` will then mark that destination atom as parented by the migrated container. Fix: make remap completeness mandatory for migration across stores, fail/assert on a missing atom entry, and keep identity remap only as an explicit checked test mode.

- **HIGH -- `migrate_subtree_from` clones rows but does not migrate/release the detached source subtree.** The source table parameter is `const` (`include/BALL/KERNEL/_moleculeStoreInternal.h:628-631`), and the implementation only calls `migrate_one_` then returns the new root (`source/KERNEL/moleculeStore.C:494-500`). Source rows, source child edges, and source atom reverse edges remain live. That leaves the orphan container table leaking rows and leaves stale detached aliases looking valid. Fix: either make this function a true move that releases source rows and clears source reverse edges after successful copy, or rename it to a copy helper and add a separate D56 lifecycle primitive before H1b.

- **LOW -- migration comments contradict the implemented property deferral.** The header says `migrate_subtree_from` copies properties (`include/BALL/KERNEL/_moleculeStoreInternal.h:625-626`), while the implementation explicitly defers container-property migration to H2 (`source/KERNEL/moleculeStore.C:474-476`). Fix the comment now, and add an H2 checklist item/test for container property migration.

- **LOW -- `ChildRef` ops can create stale old-parent edges if used as reparenting primitives.** `append_child`/`prepend_child`/`insert_child_*` set the new reverse edge but do not remove the child from any old parent (`source/KERNEL/moleculeStore.C:376-405`). That is fine only if H2 mirror wiring always performs explicit remove-before-add. Add a checked move/reparent helper or parity tests that cover moving an existing child.

## Overall verdict

**NEEDS-FIXES -- do not start H1b yet.** H1a is otherwise non-invasive and the table shape is broadly correct, but D56 migration is not a true, safe detached-subtree migration yet. Required fixes before H1b:

1. Make atom remap completeness explicit and checked in `migrate_subtree_from` / `migrate_one_`.
2. Implement or explicitly separate source-row release for orphan->System container migration; do not leave `migrate_subtree_from` looking like a lifecycle move while it is only a clone.
3. Correct the property-migration comment/contract mismatch and record property migration as an H2 obligation.

After those fixes, H1b can start with the remaining `ChildRef` reparenting guard as an H2 mutation-wiring follow-up.
