## 1. What was tested

`Atom2`, a heap-allocated handle holding `(MoleculeStore*, idx, generation)`
with **no Composite / PropertyManager / Selectable inheritance**. Tests
cover the v1.x Atom API surface that `test/Atom_test1.C` exercises:

| Capability | Status | Notes |
|---|---|---|
| Default construction (`Atom2 a;`) | ✅ | Lazy per-Atom MoleculeStore allocated; ~80 B overhead per orphan atom |
| `Atom*` pointer identity (heap-allocated) | ✅ | `a != b`, `*a == *a` |
| Setters/getters round-trip (position, charge, element) | ✅ | Dispatch through store via `idx_` |
| `clear()` — semantic re-init | ✅ | Reimplemented on the handle (column zeroing) |
| `set(other)` / `get(other)` — value copy | ✅ | Cross-store copies handled |
| `swap(other)` — three-way swap | ✅ | Std::swap on each column |
| Cross-store `createBond` refusal | ✅ | Returns sentinel; bond table untouched |
| Adoption (`a.adoptInto(shared_store)`) | ✅ | Column data migrated; private store dropped; same `Atom*` survives |
| Iteration perf (5k atoms, handle dispatch) | ✅ | **2.4 ns/atom** — same as the K0.2 store-direct baseline |

**All 8 prototype tests pass.** The handle approach is sound.

## 2. What this tells us about the in-tree migration

### Confirmed feasible (no design changes needed)

1. **Atom-as-handle works** for the simple getter/setter API. The dispatch
   cost (~2.4 ns/atom) is well inside D14's ≤2× iteration-budget gate
   (baseline 1.75 µs/atom = 70× headroom on the perf metric — but the
   baseline iteration also walks the Composite tree, which adds tree-walk
   cost that we'd be removing here, so the comparison is favorable).

2. **Reference-return contract (D7)** holds. `getPosition()` returns
   `Vector3&` into `store_->position(idx_)`. Tests confirm reference is
   stable across non-resizing operations.

3. **Lazy per-Atom store** solves the default-construction problem
   elegantly. `Atom a;` works without a parent System; data lives in a
   private one-atom store that gets adopted (and dropped) when the atom
   joins a System.

4. **Adoption mechanic** lets us migrate from private store to shared
   store without losing atom identity or data. ~30 LOC.

5. **Cross-store bond refusal** is the right default. Atoms can only be
   bonded if they share a store, matching the v1.x "atoms must be in the
   same System" semantics.

### Newly-surfaced design questions

These didn't come up in the abstract decisions doc but matter for in-tree
work:

- **Q1. Where does the `Element*` pointer live?** v1.x Atom holds
  `const Element* element_;` pointing into the PTE singleton. K0.3a
  used `uint8_t element_index_` instead. To preserve v1.x source-compat,
  Atom needs to expose `Element&` from `getElement()`, so the column can
  hold a uint8 index that `getElement()` translates back via PTE.
  Verifying this round-trips byte-equal on the PTE_test fixture is
  trivial in-tree work, but it's a *new constraint* on PTE's API.

- **Q2. What about `MolecularInteractions* interactions`?** D9 says
  "removed; sparse store column." Confirmed feasible (store column =
  `vector<MolecularInteractions*>` with null defaults), but every
  call site that does `atom->interactions` (public field access)
  breaks at v2.0. Tests-only compat says fine; downstream MOLMEC
  code rewrites when re-enabled.

- **Q3. `static AtomIndexList free_list_`** ([atom.h:967](../../include/BALL/KERNEL/atom.h#L967)).
  v1.x class-static pool. With per-System stores owning their slots,
  this static is obsolete. Delete it; no test exercises it directly.

- **Q4. Persistence virtuals.** Per D12, persistence format breaks at
  v2.0. The K0.3 in-tree Atom *can* drop `persistentWrite` /
  `persistentRead` entirely (D12 says PersistentObject is gone). But
  the test `PersistenceManager_test` is already in the **delete list**
  per `KERNEL-V2-DECISIONS.md §6`. So this is consistent with the
  locked plan — just confirms it.

### Newly-surfaced risks (none of these block the design; all are
implementation costs to budget)

- **R1.** Atom currently inherits from Composite (which inherits from
  PersistentObject, Selectable, and via composition holds
  PropertyManager). All inherited methods that any test calls must be
  reimplemented on the new handle Atom:
  - `getModificationTime()`, `getSelectionTime()`, `stamp()` — Composite/Selectable
  - `clear()`, `destroy()`, `set()`, `get()`, `swap()` — Composite
  - `applyChild`, `applyDescendantPreorder` — Composite (visitor)
  - `getHandle()`, `getName()`, `setName()` — Object / inherited
  - `hasProperty(name)`, `setProperty(name, v)`, `getProperty(name)` — PropertyManager
  - `isSelected()`, `select()`, `deselect()` — Selectable
  Most of these are 5-20 line reimplementations on the handle. Aggregate
  cost: ~600-1000 LOC of new methods in atom.h/atom.iC/atom.C.

- **R2.** Container types (AtomContainer, Molecule, Residue, etc.) also
  drop Composite inheritance per D2. They become handle types too, with
  the per-System store owning their hierarchy as CSR arrays. This is
  K0.4 work. Atom rewrite alone is insufficient — you need to do them
  together or Atom will compile but tests that exercise
  `atom.getMolecule()` won't link.

- **R3.** Iterator templates (`BaseIterator`, `ForwardIterator`,
  `BALL_KERNEL_DEFINE_ITERATOR_CREATORS`, `BALL_DECLARE_STD_ITERATOR_WRAPPER`)
  presume Composite-tree traversal. Need rewriting to walk the store's
  CSR. This is K0.4 work.

## 3. Recommended in-tree migration shape (K0.3b–K0.3z)

The challenge: the locked contract says "full Composite removal" (D2)
AND "tests-only source-compat" (D10). To satisfy both we need to
rewrite Atom + Bond + every container handle + every iterator template
**before any test can pass again**. That's the "flag day" problem.

Three honest paths:

### Path 1 — Multi-session flag day (large branch)

- Branch a `k03-flag-day` worktree off `v2.0`.
- Rewrite all of KERNEL atomic with Composite removal in one large change set.
- Tests broken until rewrite complete. Could span weeks.
- Merge to `v2.0` only when 36/36 green again.
- Highest design fidelity to the locked decisions; longest red-bar
  window.

### Path 2 — Phased getter migration with parallel data (interim)

- K0.3b: Add store_ / idx_ / gen_ as additional fields on Atom (Atom
  keeps Composite base, keeps existing fields). Tests still pass.
- K0.3c: For one getter (e.g. `setPosition`), make it write to BOTH
  the v1.x field AND the store column. `getPosition` still reads from
  v1.x field. Tests still pass (semantics unchanged).
- K0.3d: Flip `getPosition` to read from store column. Stop writing to
  v1.x field. Tests still pass.
- K0.3e: Delete the v1.x `position_` field. Tests still pass (no caller
  touches it).
- ... repeat for every field ...
- K0.3z: Delete Composite/PropertyManager/Selectable bases. Tests now
  break only on the API-surface gaps that K0.4 will fill (visitor
  pattern, container traversal). Fix those.
- Largest number of small commits. Lowest risk per commit. Many
  intermediate states have parallel-data overhead that the locked
  contract explicitly rejected — but the parallel-data exists only
  *transiently* during migration, not as a steady-state design.

### Path 3 — Honest pause + replan (this session's recommendation)

- Recognize that K0 is 25–35 weeks at 1.0 FTE per the locked plan.
- This session: prove the design works in experiments (DONE — 8/8 prototype
  tests green); land the build fence (K0.1, DONE); land the
  MoleculeStore type (K0.2, DONE); document the migration shape (this
  doc).
- Next session: select Path 1 or Path 2 with the maintainer, then start
  the work as a series of multi-week commits.

**Claude's recommendation:** Path 2. The parallel-data interim is
distasteful but it's the only way to keep the 35-test K0.1 green-bar as
a continuous gate during the rewrite — which catches regressions
immediately rather than at the end of a multi-week flag-day burn-down.
The "parallel-data is forbidden" reading of D2 was about steady-state
design, not migration mechanics.

## 5. Memory budget so far

K0.2 MoleculeStore column footprint per atom:
- Vector3 positions × 3 (positions, velocities, forces) = 36 B
- float charges + radii = 8 B
- short atom_types + formal_charges = 4 B
- uint8 element + selection = 2 B
- uint32 name + type_name offsets = 8 B
- uint64 stable_id = 8 B
- Atom* back_ptr = 8 B
- **Total: 74 B/atom in columns** (well inside D13's 160 B budget)

Atom handle (when migration completes):
- `MoleculeStore*` = 8 B
- `uint32_t idx` = 4 B
- `uint64_t generation` = 8 B
- vtable pointer (if Atom keeps virtuals) = 8 B
- **Total: 24-28 B/atom** in the handle

Bond record: 12 B (confirmed in K0.2 test)
Bond CSR amortised: ~16 B/atom (typical 3 bonds/atom × 12 B / 2 sides + 4 B CSR offset)

Grand total (handle + columns + bonds): ~114 B/atom. **46 B headroom**
under D13's 160 B/atom hard cap for properties + interactions + future
columns. Comfortable.
