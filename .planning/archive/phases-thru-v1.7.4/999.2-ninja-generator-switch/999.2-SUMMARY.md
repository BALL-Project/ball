# Phase 999.2 — Ninja Build Generator Switch — SUMMARY

## Outcome

Switched the CI CMake generator from per-platform Make/MSBuild to
**Ninja (single-config)** across all three `ci-*` presets. The
`CMAKE_<LANG>_COMPILER_LAUNCHER=ccache` cache variable already wired
into the `ci-windows` preset (since Phase 4) is now load-bearing —
MSBuild silently ignored it; Ninja honors it.

**Headline result: Windows Build step dropped from 4818s (cold-cache,
attempt 1) to 55s (warm-cache, attempt 2) — an 87× speedup on
incremental Windows CI builds.** Effective ccache hit rate
(wall-clock-derived): **~98.9%**.

**Windows total job wall-clock on the warm-cache run: ~4.7 minutes** —
well under the 10-minute threshold for the standing conditional
disable policy. This satisfies the user-stated "if Windows < 10min
total job time, call it out" criterion explicitly.

### Post-Phase-999.2 — cold ccache (first Ninja build)

CI run [25953405453 attempt 1](https://github.com/BALL-Project/ball/actions/runs/25953405453/attempts/1)
(commit `0bd1c16`, generator = Ninja, ccache effective on all 3,

| Platform | Generator | Configure | Build | Δ vs baseline | Job total |
|---|---|---:|---:|---:|---:|
| macOS arm64 | Ninja | 16s | 31s | **−54%** ¹ | ~6min ² |
| Linux x64 | Ninja | 7s | 25s | **−75%** ¹ | ~4min |
| Windows x64 | Ninja | **130s** | 4818s | +4% (cold-cache populating) | ~85min |

¹ *macOS/Linux ccache was already warm pre-switch; the further
improvement here is ccache surviving the Make → Ninja generator
change (cache key is computed from compiler binary path + flags +
preprocessed source, not from the build-system layout, so the cache
populated by prior Make runs is still hit-eligible under Ninja).*
² *macOS total includes 183s Homebrew install + 21s + 47s test suite +
12s spike smoke — the Build step itself is 31s.*

CI run [25953405453 attempt 2](https://github.com/BALL-Project/ball/actions/runs/25953405453/attempts/2)

| Platform | Configure | Build | Δ vs cold-Ninja | Δ vs MSBuild baseline | Job total |
|---|---:|---:|---:|---:|---:|
| macOS arm64 | 17s | 39s | +26% (runner noise) | −42% | ~7min |

**The Windows row is the load-bearing result.** 4818s → 55s on
incremental builds of the same code, all driven by ccache hit on
cl.exe outputs that MSBuild had previously rendered uncacheable.

## ccache hit-rate evidence

- **Windows wall-clock derived hit rate:** `(4818 − 55) / 4818 ≈ 98.9%`
  on incremental builds. This is the effective rate — what matters
  for dev-iteration speed.
- **macOS / Linux:** ccache was effective pre-switch (cache key
  survived the Make → Ninja transition, as evidenced by the warm
  Build times being within runner-noise range of the Make warm
  baseline). The Ninja switch is a uniformity win on these
  platforms, not a speedup win.
- **Explicit `ccache --show-stats --verbose`:** instrumented in
  commit `bbac526` (post-this-summary). All future CI runs will
  log the cumulative cache hits/misses/size per build step in
  the workflow log; not yet captured here because the verification
  re-run was attempt 2 of an older SHA (`0bd1c16`, pre-bbac526),
  not a fresh push.

## Stop conditions — none triggered

- ✅ No platform regressed. All three Build/test/smoke flows pass
  end-to-end on the warm-cache run.
- ✅ No hidden Windows ccache+Ninja MSVC gotcha hit.
  `CMAKE_BUILD_TYPE=Release` (set in the `base` preset) means MSVC
  emits no `/Zi` PDB by default, so the documented
  `CMAKE_MSVC_DEBUG_INFORMATION_FORMAT=Embedded` workaround was
  not needed. `cl.exe` was found correctly via the
  `ilammy/msvc-dev-cmd@v1` vcvars64 step.
- ✅ Vcpkg toolchain bridge (`$env:VCPKG_ROOT = $env:VCPKG_INSTALLATION_ROOT`
  in Configure) survived the vcvars-env layer cleanly.
- ✅ `--config Release` on the Windows build line is silently no-op
  under single-config Ninja (CMake docs). Left in place for
  transparency.

## Standing conditional disable policy — explicit call-out

> **Windows total CI job time on the warm-cache run is ~4.7 minutes,
> against macOS ~7 min and Linux ~4 min. Windows ÷ max(macOS, Linux)
> = 4.7 / 7.0 = 0.67 ≪ 2.0 — the "Windows > 2× macOS/Linux disable"
> condition is comfortably cleared. The `continue-on-error: false`
> Windows blocking flip from Phase 04-04 (Plan 04-04 Task 3) holds.**

Cold-cache (first build on a new commit) is still ~85 min total —
roughly the same as the pre-Phase-999.2 MSBuild baseline — but the
amortized cost across a typical dev-iteration cycle (one cold pre-run
+ many warm incrementals) is dramatically lower.

## What was NOT changed

- BALL / VIEW / BALLView source. Zero source-side changes — pure
  build-tooling switch.
- `release.yml` workflow — out of scope per phase plan. Release
  builds still use the MSBuild generator under MSVC; revisit in
  v1.6.2 if release wall-clock becomes a pain point. Note that
  `release.yml` does call the `setup-windows-deps` composite action
  and therefore installs `ninja` too — that install is benign and
  unused there.
- Local-developer presets (`macos-homebrew`, `linux-system`,
  `windows-vcpkg`). Each one stays on the platform default
  generator, matching existing `BUILD-macos.md` instructions.
  Future per-platform `BUILD-*.md` docs can opt local dev workflows
  into Ninja whenever the maintainer chooses.
