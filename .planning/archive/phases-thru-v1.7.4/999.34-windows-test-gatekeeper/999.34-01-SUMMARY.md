## Decisions Made

1. **Inherit the quarantine table verbatim.** The plan listed `AssignBondOrderProcessor_test2` as a candidate for a Windows-scoped WILL_FAIL extension; investigation showed it only fails on Apple Silicon's FMA path, and MSVC x64 (like Linux x64 GCC) uses the Intel-compatible FP path that passes the test. Same for `AmberFF_test`. So the existing `IF (APPLE AND CMAKE_SYSTEM_PROCESSOR MATCHES "arm64|aarch64")` gate stays as-is — no `IF (WIN32)` block needed.
2. **Extend PATH, not LIBRARY_PATH.** Windows DLL discovery is dominated by PATH (after the EXE's own dir). `LD_LIBRARY_PATH` is a Unix convention; the Windows equivalent is just PATH. We extend with both `bin\` (BALL.dll + VIEW.dll) AND `vcpkg_installed\x64-windows-release\bin\` (Qt6 + Boost) so VIEW_TESTS (which link Qt) also resolve cleanly.
3. **`--config Release` on the Windows build step.** Held over from the multi-config-MSBuild era (no-op under Ninja single-config), but kept for explicit intent matching the existing `Build (Windows)` step in both files.
4. **No SignPath / no NSIS impact.** The test gatekeeper runs BEFORE windeployqt + WinSparkle bundling, so a Windows test failure aborts the release build before any installer-side cost is incurred. Aligns with the macOS sibling pattern where the test step runs before macdeployqt + codesign.
