<objective>
Close GitHub #527 by adding a transparency control to the Inspector
`materialSection` that ACTUALLY works in the interactive (GLRenderer) BALLView
scene — by routing it through `Representation::setTransparency()` (the
per-representation 0-255 alpha that GLRenderer honors), NOT through
`Stage::Material.transparency`.

Purpose & corrected backend (this supersedes the prior plan's backend, which a
plan-checker BLOCKED): the interactive `GLRenderer` does NOT consume
`material.transparency`. `GLRenderer::setMaterial_`
(source/VIEW/RENDERING/RENDERERS/glRenderer.C ~line 190) sets only specular /
shininess / ambient — it never reads `material.transparency`. Interactive GL
transparency is decided by `rep.getTransparency()`: GLRenderer's run==1
"transparent models" pass renders a representation transparently iff
`rep.getTransparency() != 0` (glRenderer.C ~lines 654/664/882), and
`Representation::setTransparency(0-255)` pushes that alpha to the color
processor / per-vertex alpha (representation.C ~lines 503-533, `alpha = 255 -
transparency_`). Only POVRay/RTfact (RTfact is DISABLED per CLAUDE.md) read
`material.transparency`; the legacy dialog itself admits this
(materialSettings.C:55 `//TODO OpenGL and POVRay do not make any use of
transparency!`), and MaterialController.C already documents it (the
"transparency stays as-is; per-rep transparency is owned by the ModelController
... Representation::setTransparency" comment at apply()). So a slider wired to
`material.transparency` would compile and debounce but NOT visibly change the
molecule — reproducing the exact #527 bug.

The Refresh `materialSection` ships four material sliders but NO transparency
control, while the broken legacy `MaterialSettings` transparency slider is still
compiled and reachable. After this plan the Material tab gains a transparency
control wired to the WORKING `Representation::setTransparency()` path, so the
Inspector supersedes that broken path. (Requirement VIEW-INSP-03.)

Output: a `transparency_` 0-255 slider in `MaterialSection` bound through a new
`transparency` property on `MaterialController`, applied via
`Representation::setTransparency()` + `Representation::update()`. Strictly
additive — the legacy dialog is left in place for Phase 999.53 to delete.

Overlap note (NOT a duplicate to remove): a WORKING transparency control already
exists in the **Model** section (modelSection.C ~lines 100/105/304-309 ->
ModelController::apply() ~line 182 -> `rep_->setTransparency(...)`). #527 reports
the *Material settings tab* slider as broken, and VIEW-INSP-03 specifies the fix
lives in `materialSection`. So this plan adds a second, deliberate entry point in
the Material tab onto the SAME shared `Representation` transparency state — both
sections read/write `Representation::getTransparency()/setTransparency()`, so
they stay mutually consistent (changing one and reverting/reopening the other
reflects the live value). We are NOT building a second, divergent transparency
concept; we are surfacing the working one in the tab #527 names.

Scope boundary (do NOT touch):
- The legacy `source/VIEW/DIALOGS/materialSettings.{C,h,ui}` — read only, for
  reference. Deletion is Phase 999.53.
- `Stage::Material.transparency` — do NOT write it. It is dead for interactive
  GL (POVRay/RTfact-only) and is the broken #527 backend.
- `modelSection` / `ModelController` — do NOT modify them. They already drive
  `Representation::setTransparency()`; we reuse the same Representation backend
  from MaterialController, but leave the Model section's code untouched.

THE WORKING TRANSPARENCY BACKEND (the path the interactive GLRenderer honors).
From include/BALL/VIEW/KERNEL/representation.h:
  Size getTransparency() const;       // /// get transparency (0 - 255)
  void setTransparency(Size value);   // /// set transparency (0 - 255), 0 = opaque
From source/VIEW/KERNEL/representation.C (setTransparency, ~lines 503-533):
  - Clamps to 255; if a color_processor_ exists it calls
    color_processor_->setTransparency(transparency_); else it walks the
    geometric objects setting per-vertex alpha = 255 - transparency_.
  - Sets changed_color_processor_ = true so the next update() rebuilds colors.
From source/VIEW/RENDERING/RENDERERS/glRenderer.C (PROOF this is the honored path):
  - setMaterial_(~line 190) sets ONLY specular/shininess/ambient — never
    material.transparency.
  - The multi-run render loop selects the transparent pass via
    rep.getTransparency() (~lines 654, 664) and ~line 882
    (else if (representation.getTransparency() == 0) ...). This is what makes a
    molecule visibly transparent in interactive BALLView.

HOW THE WORKING MODEL-SECTION CONTROL DRIVES IT (reference pattern — do NOT edit
these files; mirror the approach in MaterialController/MaterialSection):
  - ModelController (source/VIEW/KERNEL/controllers/modelController.C):
      * member `int transparency_;` init 0; getter `int transparency() const`.
      * revert(): `int tr = static_cast<int>(rep_->getTransparency()); if (tr != transparency_) { transparency_ = tr; Q_EMIT transparencyChanged(tr); }`
      * apply(): `rep_->setTransparency(static_cast<Size>(transparency_)); rep_->update(rebuild);`
      * setTransparency(int t): guard-on-equal, set, `Q_EMIT transparencyChanged(t);`
      * signal `void transparencyChanged(int v);`
  - ModelSection (source/VIEW/WIDGETS/inspector/sections/modelSection.C):
      * slider: `new LabeledSlider(0, 255, 0, QStringLiteral(""), content);` (0-255, NO "%" suffix)
      * `onTransparencyChanged_(int v)` -> `controller_->setTransparency(v); scheduleApply_();` (NO /100 — already on 0-255 scale)
      * `onControllerTransparencyChanged_(int t)` -> `if (transparency_->value() != t) transparency_->setValue(t);`

CURRENT MaterialController (source/VIEW/KERNEL/controllers/materialController.C +
include/.../materialController.h) — what you ARE editing:
  - Holds `Representation* rep_;` (getter `representation()`), and
    ambient/diffuse/specular/shininess float properties. apply() currently
    seeds a Stage::Material, overwrites the 4 intensity/shininess fields, and
    calls `scene->updateMaterialForRepresentation(rep_, material);`. Its comment
    block at apply() (~lines 169-171) explicitly says transparency is owned by
    the ModelController via Representation::setTransparency — confirming the
    correct backend for THIS plan is rep_->setTransparency, NOT material.transparency.
  - revert() re-reads the material; apply() has a ControllerApplyGuard
    re-entrancy shield and a MainControl::isBusy() defer. The new transparency
    work must NOT disturb these guards or the existing material-intensity path.

CURRENT MaterialSection slider pattern (source/.../materialSection.C +
include/.../materialSection.h) — what you ARE editing:
  - `makePercentSlider_(parent, init)` builds a 0-100 LabeledSlider with "%".
    Ambient/diffuse/specular use it; shininess uses a raw `new LabeledSlider(0, 128, ...)`.
    The new Transparency slider must be a RAW 0-255 LabeledSlider (NOT a percent
    slider) to match the Representation 0-255 scale and the Model-section control.
  - Each slider: connect(slider_, &LabeledSlider::valueChanged, this, &MaterialSection::onXxxChanged_);
  - onXxxChanged_(int v): set controller value + `debounce_.start();`
  - Controller->UI: connect(controller_, &MaterialController::xxxChanged, this, &MaterialSection::onControllerXxxChanged_);
    slot guards `if (slider_->value() != iv) slider_->setValue(iv);`.
  - debounce_ is a single-shot QTimer(100ms) whose timeout -> onDebounceFire_() -> controller_->apply().
  - Per-section reset already wired: setResettable(true, ...) +
    connect(resetRequested, [this]{ controller_->revert(); controller_->apply(); }).
    revert() re-emits *Changed -> sliders resync. The new slider inherits this for
    free as long as revert() handles transparency and onControllerTransparencyChanged_ is connected.
  - The destructor flushes a pending debounce: if active, stop() + onDebounceFire_().
