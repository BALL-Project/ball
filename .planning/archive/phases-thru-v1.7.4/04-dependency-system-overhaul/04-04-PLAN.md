<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| vcpkg registry → Windows build | `vcpkg.json` causes the vcpkg toolchain to download + build dependency source code from the vcpkg registry at configure time. Untrusted source crosses into the Windows build. |
| Chocolatey (`choco install winflexbison3`) → Windows CI runner | A third-party package manager installs `win_flex.exe` / `win_bison.exe` onto the runner; these binaries then run as build tools generating parser/lexer code. |
| `$env{VCPKG_ROOT}` → `windows-vcpkg` preset toolchainFile | The Windows configure resolves and executes `vcpkg.cmake` from a path derived from an environment variable. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-13 | Tampering | vcpkg pulling a different (compromised or simply changed) port version, making the Windows build non-reproducible or injecting hostile code | mitigate | `vcpkg.json` pins `builtin-baseline` to a specific 40-char vcpkg commit SHA (Task 1, Pitfall 4) — every Windows build resolves the exact same port versions. The baseline is a version-controlled value changed only via reviewed PRs. This is the vcpkg analogue of D-08's min-version pinning. |
| T-04-14 | Tampering | `choco install winflexbison3` resolving a hijacked or typosquatted package | mitigate | `winflexbison3` is a well-established Chocolatey package; the install runs on an ephemeral GitHub-hosted `windows-2022` runner (no persistence, no secrets beyond a `contents: read` token). The package name is pinned in the version-controlled workflow. Residual risk (a compromised upstream choco package) is bounded by the ephemeral, read-only-token runner — accepted beyond pinning the name. |
| T-04-15 | Tampering | A malicious PR editing `vcpkg.json` (e.g. adding a hostile dependency or changing the baseline to a compromised commit) | mitigate | `vcpkg.json` is a version-controlled repo file — changes go through PR review. CI runs only on `master` / `v1.6-modernization` (ci.yml `on:` pins this), so a fork PR cannot run a modified manifest with repo context. The Task 1 verify asserts the baseline is a pinned SHA and that no non-port deps were added. |
| T-04-16 | Elevation of Privilege | vcpkg port build scripts + `vcpkg.cmake` toolchain executing arbitrary code at configure time | accept | This is inherent to vcpkg manifest mode and to building any dependency from source. The exposure is bounded by the pinned baseline (known port-script revisions) and the ephemeral read-only-token CI runner. vcpkg is the maintained, standard Windows provisioning path (Research "Don't Hand-Roll" — the alternative is reviving the dead `ball_contrib` tarballs, which is worse). No additional in-phase mitigation. |
| T-04-17 | Denial of Service | vcpkg building Qt5 from source timing out / exhausting the CI runner | accept | A reliability concern, not a security one. Mitigated operationally by the `actions/cache@v4` step keyed on the `vcpkg.json` hash (Task 2) — warm cache avoids the rebuild. A timeout fails the job loudly; it does not corrupt anything. The user owns the iterative bring-up. |
</threat_model>
