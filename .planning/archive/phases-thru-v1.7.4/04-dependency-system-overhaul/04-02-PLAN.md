and the macOS/Linux CI configure steps to invoke those presets so doc + CI + presets

independent of Plan 01 — it touches different files and can run in parallel in Wave 1.

toolchain and brings the Windows CI job to green against it.

**D-07 preset-naming note:** D-07 specifies 4 named presets — `macos-homebrew`,
`linux-system`, `windows-vcpkg`, and one literally named `ci`. Per RESEARCH Open
Question 2 (which sanctioned this discretion), this plan ships a `ci-macos` /
`ci-linux` / `ci-windows` FAMILY instead of a single `ci` preset, because a single
`ci` preset cannot carry per-platform cache vars (compiler launchers, toolchain file).
The D-07 → `ci-*` mapping is made explicit in two maintainer-visible places: (a) the
new "Build presets" subsection of `BUILD-macos.md` states the `ci-*` family collectively
satisfies D-07's `ci` preset, and (b) Task 1 adds a one-line comment cross-referencing
D-07 in the BUILD-macos.md presets note. (See Task 1 / Task 2.)

**WARNING-3 fix — OpenBabel cache var lives in the ci-* presets:** Plan 03 enables
OpenBabel in CI. To keep `CMakePresets.json` the single source of truth for cache
variables (rather than Plan 03 passing a divergent `-DBALL_HAS_OPENBABEL=ON` CLI arg in
`ci.yml`), THIS plan authors `BALL_HAS_OPENBABEL=ON` into the `ci-macos` and `ci-linux`
presets' `cacheVariables` from the start. Plan 02 already knows OpenBabel is enabled on
mac/Linux — Task 3 writes exactly that into the FEAT-01 matrix. Plan 03 then only adds
the smoke step, not the cache var.

Output: new `CMakePresets.json`, updated `BUILD-macos.md`, updated

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `CMakePresets.json` → developer/CI shell | The preset file is executed-as-configuration by every `cmake --preset` invocation; it sets cache variables, a toolchain file path, and compiler launchers. |
| `$env{VCPKG_ROOT}` → `windows-vcpkg` preset `toolchainFile` | The preset resolves a toolchain script path from an environment variable; a hijacked `VCPKG_ROOT` could point at a malicious `vcpkg.cmake`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-05 | Tampering | A malicious PR editing `CMakePresets.json` to add a hostile `CMAKE_CXX_COMPILER_LAUNCHER` or `toolchainFile` and have CI execute it | mitigate | `CMakePresets.json` is a version-controlled repo file — changes go through the same PR review as source. CI runs only on the `master` / `v1.6-modernization` branches (ci.yml `on:` already pins this), so a fork PR cannot run preset changes with repo secrets. No new secret is exposed (the workflow token is `contents: read`). |
| T-04-06 | Tampering | `windows-vcpkg` preset resolving `toolchainFile` from a hijacked `$env{VCPKG_ROOT}` | mitigate | Plan 04 pins the vcpkg `builtin-baseline` in `vcpkg.json` and provisions vcpkg on the CI runner from the official microsoft/vcpkg repo at a known ref — `VCPKG_ROOT` on the CI runner points at that provisioned tree, not an arbitrary path. Documented for local Windows builds in the preset `displayName` + BUILD-macos.md presets note. |
| T-04-07 | Information Disclosure | `CMakePresets.json` embedding absolute local paths (`/opt/homebrew/...`) | accept | These are standard Homebrew/system install locations, not secrets; they are already public in `BUILD-macos.md` and `ci.yml`. No PII, no credentials. |
| T-04-08 | Repudiation | CI configure invocation no longer self-documenting (preset indirection hides the actual flags) | accept | The presets are a single version-controlled file; `cmake --preset ci-macos -N` (dry run) prints the resolved cache vars. Auditability is preserved, just one indirection away. Low risk for a single-developer build-system phase. |
</threat_model>
