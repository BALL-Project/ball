# Phase 05.1 Plan 02: C4311 Pointer Truncation Fix — Summary

**One-liner:** Migrated three pointer-identity call chains (`hashPointer`, MMFF94 stretch-bend hash lookup, TriangulatedSphere edge-comparator) from `(unsigned long)`/`(long)` casts to `reinterpret_cast<BALL::PointerSizeUInt>`, including the function-local `HashMap<long, Position>` storage Codex flagged in CONTEXT.md D-08 — eliminating C4311 and the latent upper-32-bit truncation on 64-bit Windows (LLP64).

## What Changed

### 1. `source/COMMON/hash.C:22` — `BALL::hashPointer`

```cpp
// Before
HashIndex hashPointer(void *const void_ptr)
{
    double d = ((double)((unsigned long)void_ptr)) * 0.6180339887;
    ...
}

// After
HashIndex hashPointer(void *const void_ptr)
{
    // Use BALL::PointerSizeUInt (global.h:207) so the pointer-value extraction
    // preserves all bits on 64-bit Windows (LLP64), where `unsigned long` is
    // only 32-bit and would truncate the upper half of a 64-bit pointer.
    double d = ((double)(reinterpret_cast<BALL::PointerSizeUInt>(void_ptr))) * 0.6180339887;
    ...
}
```

The cast on the following line (`(unsigned long)d`) was deliberately left alone — `d` is a `double`, the cast extracts the integer part for the subsequent fractional-part calculation, and `unsigned long` is the right type there. Not a pointer truncation.

### 2. `source/MOLMEC/MMFF94/MMFF94StretchBend.C` — `setupStretchBends_()`

**Storage type widening (the Codex-flagged audit step):**

```cpp
// Before — function-local hash table keyed by truncated atom-pointer product
HashMap<long, Position> stretch_map;
...
HashMap<long, Position>::Iterator stretch_it1, stretch_it2;

// After — full pointer width
HashMap<BALL::PointerSizeUInt, Position> stretch_map;
...
HashMap<BALL::PointerSizeUInt, Position>::Iterator stretch_it1, stretch_it2;
```

**Cast-site widening at all 4 sites (lines 359-360 insertion, lines 388-389 lookup):**

```cpp
// Before
long index = ((long) stretches_[stretch_pos].atom1) *
             ((long) stretches_[stretch_pos].atom2);
...
stretch_it1 = stretch_map.find((long) a1 * (long) a2);
stretch_it2 = stretch_map.find((long) a2 * (long) a3);

// After
BALL::PointerSizeUInt index = reinterpret_cast<BALL::PointerSizeUInt>(stretches_[stretch_pos].atom1) *
                              reinterpret_cast<BALL::PointerSizeUInt>(stretches_[stretch_pos].atom2);
...
stretch_it1 = stretch_map.find(reinterpret_cast<BALL::PointerSizeUInt>(a1) * reinterpret_cast<BALL::PointerSizeUInt>(a2));
stretch_it2 = stretch_map.find(reinterpret_cast<BALL::PointerSizeUInt>(a2) * reinterpret_cast<BALL::PointerSizeUInt>(a3));
```

Note the "composite identity from product of two pointers" idiom is preserved — the product of two `PointerSizeUInt` values is a single `PointerSizeUInt` that distinguishes (atom1, atom2) pairs (with the usual hash-collision caveat for the product operation itself, which is a pre-existing characteristic of this lookup table, not in scope for this plan).

### 3. `source/STRUCTURE/triangulatedSurface.C` — `PointerPairComparator::operator()`

```cpp
// Before — canonicalization compared 32-bit-truncated pointers on Windows
if((unsigned long)a.first > (unsigned long)a.second) {
    std::swap(a.first, a.second);
}
...
if((unsigned long)b.first > (unsigned long)b.second) {
    std::swap(b.first, b.second);
}

// After — full pointer width
if(reinterpret_cast<BALL::PointerSizeUInt>(a.first) > reinterpret_cast<BALL::PointerSizeUInt>(a.second)) {
    std::swap(a.first, a.second);
}
...
if(reinterpret_cast<BALL::PointerSizeUInt>(b.first) > reinterpret_cast<BALL::PointerSizeUInt>(b.second)) {
    std::swap(b.first, b.second);
}
```

The subsequent `(a.first < b.first)` line compares `TrianglePoint*` directly via the implicit `std::less<T*>` on the pair-of-pointer comparison — that's pointer comparison through the pointer type, not a `long` cast, and is unaffected.

## Decision: `PointerSizeUInt` over `std::uintptr_t`

The plan's Task 2 left this as a checkpoint; under the user's no-clarifying-questions execution policy I made the conservative correctness choice **`BALL::PointerSizeUInt`** and document the rationale here.

**Rationale:**

1. **Width-equivalent on all BALL-supported platforms.** `BALL_POINTERSIZEUINT_TYPE` (the typedef's underlying definition) is auto-detected by CMake to match `sizeof(void*)` — same as `std::uintptr_t` does via the C++11 standard.
2. **Codebase idiom — already pervasive.** A quick `grep` shows ~30+ sites already use `PointerSizeUInt` (`hash.h:49`, `persistenceManager.h` ×6, `timer.h/C`, `molecularSurfaceGrid.C` heavily); zero sites use `std::uintptr_t`. Picking `PointerSizeUInt` keeps the codebase consistent and respects the typedef that was apparently introduced for exactly this purpose.
3. **No new `#include` required.** `PointerSizeUInt` is declared in `<BALL/COMMON/global.h>`, which is pulled in transitively by `<BALL/common.h>`. All three modified files include `<BALL/common.h>` (or a header that does — `hash.h` includes it directly, `triangulatedSurface.h` pulls it via `vector3.h`, `MMFF94StretchBend.h` pulls it via `forceFieldComponent.h`). The macOS build green at `cmake --build build/ci-macos --target BALL -j 8` confirms reachability with no `#include` adjustments needed.
4. **Forward-compat with `std::uintptr_t`** if the project later prefers the standard idiom: the `BALL_POINTERSIZEUINT_TYPE` typedef is the single point of truth — flipping it to `std::uintptr_t` in `global.h` (or even just `typedef std::uintptr_t PointerSizeUInt;`) is a one-line follow-up that propagates without source churn.
