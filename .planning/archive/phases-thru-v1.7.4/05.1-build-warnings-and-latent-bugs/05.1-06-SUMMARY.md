# Phase 05.1 Plan 06: -Wstringop-truncation strncpy Audit Summary

**Audited all 10 gcc-flagged strncpy sites in BALL source (4 PDB writers + 6 CIF lexer rules) and replaced each with explicit memcpy + nul-termination; introduced a CIF_copy_text() helper to factor the repeated lexer pattern; eliminates all -Wstringop-truncation warnings while preserving fixed-width PDB record semantics.**

## Performance

- **Duration:** ~25 min
- **Started:** 2026-05-15
- **Completed:** 2026-05-15
- **Tasks:** 1
- **Files modified:** 3
- **Flagged sites audited:** 10
- **Total sites remediated:** 24 (10 flagged + 7 structurally-identical PDBFileDetails.C neighbours + 7 unflagged-but-identical CIFParserLexer.l rules behind the helper)

## Accomplishments

- All 10 gcc `-Wstringop-truncation` warnings from CI run 25899905204 mapped to specific BALL source lines (gcc's diagnostic cites `string_fortified.h:95` but the `inlined from` notes name the call sites).
- Each flagged site classified Remediation **B** (memcpy + explicit nul-termination) — appropriate because every destination is a fixed-width PDB record field or a parser %union char buffer consumed by C-string-family APIs.
- Extended the fix to 7 structurally-identical PDBFileDetails.C neighbour sites (1473, 1777, 1783, 1802, 1842, 1847, 1867) and to all 17 strncpy sites in CIFParserLexer.l (via the helper) — keeps the file consistent and removes the latent same-class concern even where gcc didn't statically prove source-length equality.
- Introduced `static inline void CIF_copy_text(char* dst, const char* src)` in the CIFParserLexer.l prelude — single point of truncation policy for the lexer (17 call sites collapse to one helper invocation each).
- `libBALL.dylib` rebuilds green on macos-arm64 / Qt 6.11; **zero `-Wstringop-truncation` warnings on the three edited files** in the local build. Pre-existing unrelated `-Wvarargs` warning at PDBFileGeneral.C:1602 (line far from edits) is untouched and out of scope.
- BACKLOG Task **A6** closed — gcc's case-by-case `-Wstringop-truncation` audit drops the 10 instances to 0 on the next CI run.

## Deviations from Plan

### Auto-fixed (Rule 2 — added critical correctness alongside flagged sites)

1. **[Rule 2 — Critical correctness] Extended Remediation B to 7 structurally-identical unflagged PDBFileDetails.C sites**
   - **Found during:** Task 1 enumeration
   - **Issue:** Sites at lines 1473, 1777, 1783, 1802, 1842, 1847, 1867 use the same `strncpy(LString3-dest, source, 3)` pattern as the 3 flagged sites in the same file. gcc didn't flag them because source lengths are statically unknown / partially proven; but the latent nul-termination concern is identical and a future glibc / gcc version could trip the same warning. Fixing them now keeps the file consistent (every `strncpy` to a PDB fixed-width slot is gone) and avoids a re-audit when the warning re-fires.
   - **Fix:** Same memcpy + explicit nul-termination pattern as the flagged sites.
   - **Files modified:** source/FORMAT/PDBFileDetails.C (7 additional inline blocks).
   - **Commit:** same atomic commit as the rest of the plan.

2. **[Rule 2 — Critical correctness] Extended Remediation B to all 17 CIFParserLexer.l strncpy sites via a helper inline**
   - **Found during:** Task 1 enumeration
   - **Issue:** The 17 strncpy sites in the .l file all use the identical pattern `strncpy(CIFParserlval.text, yytext, CIFPARSER_LINE_LENGTH)`. gcc flags 6 of them (because flex inlines duplicate rule bodies and gcc de-duplicates the warning across textually-identical inlines). The remaining 11 have the same latent concern — yytext can in principle exceed CIFPARSER_LINE_LENGTH-1, leaving the destination non-nul-terminated.
   - **Fix:** Single static inline `CIF_copy_text(dst, src)` helper at the .l prelude; all 17 call sites collapsed to `CIF_copy_text(CIFParserlval.text, yytext)`. Truncation policy lives in one place.
   - **Files modified:** source/FORMAT/CIFParserLexer.l (1 helper inline + 17 call-site replacements).
   - **Commit:** same atomic commit.

3. **[Rule 3 — Blocking issue] Added explicit `#include <cstring>` to PDBFileGeneral.C and PDBFileDetails.C**
   - **Found during:** Task 1 implementation
   - **Issue:** Files previously used `strncpy` which is reachable via the BALL/COMMON/debug.h → cstring transitive include chain. Switching to `std::memcpy` / `std::strlen` works for the same transitive reason, but relying on transitive includes is fragile (any future header refactor could break the build).
   - **Fix:** Added `#include <cstring>` adjacent to the existing `#include <cstdlib>` in both files.
   - **Files modified:** source/FORMAT/PDBFileGeneral.C (1 include line), source/FORMAT/PDBFileDetails.C (1 include line).
   - **Commit:** same atomic commit.

No deviations from plan beyond these auto-fixes; no checkpoint hit; no architectural decisions surfaced.
