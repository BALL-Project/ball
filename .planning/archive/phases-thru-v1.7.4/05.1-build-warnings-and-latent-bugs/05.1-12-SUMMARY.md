Diagnosed the recurring `/usr/bin/tar exit code 2` warning on Linux CI by
surveying 15 recent runs, found the warning is on the **apt-archives** cache
(unreadable root-owned `lock` / `partial/` files), not the ccache cache as
BACKLOG D3 stated; applied a 1-line `path:` narrowing to silence it.

## Task 1 — Root cause identification

`gh run view 25899905204 --log` gives the exact context (timestamps preserved):

```
04:19:26.99  [command]/usr/bin/tar --posix -cf cache.tzst --exclude cache.tzst -P \
              -C /home/runner/work/ball/ball --files-from manifest.txt \
              --use-compress-program zstdmt
04:19:27.00  /usr/bin/tar: ../../../../../var/cache/apt/archives/lock: Cannot open: Permission denied
04:19:27.01  /usr/bin/tar: ../../../../../var/cache/apt/archives/partial: Cannot open: Permission denied
04:19:27.14  /usr/bin/tar: Exiting with failure status due to previous errors
04:19:27.14  ##[warning]Failed to save: "/usr/bin/tar" failed with error: \
              The process '/usr/bin/tar' failed with exit code 2
04:19:27.16  Post job cleanup.
04:19:27.30  [command]/usr/bin/tar --posix -cf cache.tzst --exclude cache.tzst -P \
              -C /home/runner/work/ball/ball --files-from manifest.txt \
              --use-compress-program zstdmt
04:19:28.86  Sent 18251840 of 152469568 (12.0%), 17.4 MBs/sec
04:19:29.71  Sent 152469568 of 152469568 (100.0%), 78.7 MBs/sec
04:19:29.82  Cache saved with key: ccache-linux-x64-6056f74976db65ac6843649a3011be5858f83f36
```

Two findings:

1. **BACKLOG D3 misclassified the failing step.** The warning is for `tar`
   trying to read `/var/cache/apt/archives/{lock,partial}` — that's the **apt
   cache step**, not the ccache step. The path `/home/runner/work/ball/ball` is
   the workspace root but the tar manifest evidently traverses `..` segments
   into `/var/cache/apt/archives/`. The ccache cache-save (path
   `~/.cache/ccache`) does NOT emit any warning — it succeeds cleanly.

2. **The "failure" is recoverable.** The action retries with a fallback that
   excludes the unreadable entries (the second `tar` invocation) and the cache
   IS still saved (`Cache saved with key: ccache-linux-x64-...`). The
   misleading log surface is: a hard-red `##[warning]` followed seconds later
   by `Cache saved`. Most readers stop at the warning and miss the success.

**Root cause (one of the three BACKLOG options, refined):**
**file permissions on the cached directory**, but on the **apt cache** rather
than ccache. APT's `lock` file is mode 0640 owned by root, and `partial/` is
mode 0700 owned by root. The runner's `runner` user has uid 1001 and cannot
read either. tar's exit code 2 is the canonical "fatal error during archive
creation" — Permission denied at open() qualifies. The unprivileged-runner +
root-owned-runtime-state mismatch is structural to GitHub Actions hosted
runners; it isn't a "race" or "size limit" or "corrupted state" cause.

(The fourth-cause "cache size > 10 GB" was ruled out: the saved cache reports
152 MB compressed. The "runner disk pressure" cause was ruled out: tar's exit
2 is at the per-file open() boundary, not a write/space ENOSPC. The "corrupted
state" cause was ruled out: the same two specific paths fail on every run, not
a random subset.)

## Task 2 — Decision (auto-resolved per no-clarifying-questions policy)

Plan options listed: `split-cache-key` / `pre-save-cleanup` / `permissions-fix`
/ `no-fix-transient`. **None match cleanly** — the real cause is
"cached-path-contains-root-owned-runtime-state-files", which is a flavor of
`permissions-fix` but the right fix isn't `chmod` (the runner can't chmod
root-owned files without sudo, and changing permissions on apt's lockfile is
a Bad Idea anyway). The closest precedent is "narrow the cached path to
exclude the unreadable bits" — call it **option 5: narrow-cached-path**.

Selected: **option 5 (narrow-cached-path)**.

Rationale: the `lock` and `partial/` entries are runtime APT state that has
**no place in a cache** anyway — they're regenerated on every `apt-get update`
and have no value for cache restore. The `.deb` archives, by contrast, ARE
the content `apt-get install` downloads and uses on a warm cache. Restricting
the cached path to `/var/cache/apt/archives/*.deb` keeps the useful content
and excludes the un-cacheable runtime state by construction.

Decided autonomously per:
- the executor's `no-clarifying-questions` mode
- the plan's success-criterion #4: "If recurring (≥2 occurrences), apply the
  most-conservative fix and document" — narrowing the path is more
  conservative than re-architecting the cache-key scheme

## Task 3 — Fix applied

**File:** `.github/workflows/ci.yml` (Linux apt-archives cache step, lines
139-159).

**Diff:**
```diff
       - name: Cache apt archives (Linux)
         if: matrix.os == 'linux-x64'
         uses: actions/cache@v5
         with:
-          path: /var/cache/apt/archives
+          # Phase 5.1 Plan 12 (Task D3): scope the cached path to `*.deb` only.
+          # [...17 lines of forensic comment explaining why...]
+          path: /var/cache/apt/archives/*.deb
           key: apt-${{ matrix.os }}-${{ hashFiles('.github/workflows/ci.yml') }}
           restore-keys: |
             apt-${{ matrix.os }}-
```

The comment block preserves the diagnosis trail in-source so a future
maintainer hitting an unrelated tar warning on the same step doesn't
re-investigate.

## Key Decisions

1. **Fix applied (not no-fix-transient).** 7/7 recurrence rate on the runs
   that reached the cache phase is chronic, not transient.
2. **`narrow-cached-path` over the four plan-listed options.** The plan's four
   options (split-cache-key, pre-save-cleanup, permissions-fix,
   no-fix-transient) all assumed the ccache cache was the failing step. With
   the apt cache identified as the real source, the minimal additive fix is to
   narrow the cached path glob — none of the four was a clean match.
3. **`*.deb` glob over the full `archives` directory.** This is what
   `apt-get install` downloads (proof: `Get:40 .../ccache_4.5.1-1_amd64.deb`
   in every run log). Restoring `.deb` archives is the entire reason this
   cache exists; the `lock` file and `partial/` dir are runtime APT state that
   shouldn't be cached.
