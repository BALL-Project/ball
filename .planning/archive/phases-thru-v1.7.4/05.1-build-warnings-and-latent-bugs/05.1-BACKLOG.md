## Tier A — Real bugs (fix before Phase 5 ships)

### Task A1: C4717 `getline` infinite recursion ✓ Codex-verified

**Where:** [`include/BALL/DATATYPE/string.iC:1759-1769`](../../../include/BALL/DATATYPE/string.iC#L1759)

**Bug:** The two `getline(istream&, BALL::String&&, ...)` overloads call `getline(is, move((string&)str), ...)`. No `std::getline(istream&, std::string&&, ...)` overload exists in the standard (cppreference lists four overloads, all `string&`). Overload resolution falls to the being-defined `BALL::String&&` version because `BALL::String(string&& s)` is non-explicit ([`string.h:161`](../../../include/BALL/KERNEL/string.h)), implicitly constructing a new `BALL::String&&` from the `std::string&&` argument. Infinite self-recursion. Stack overflow on call. gcc/clang produce the same recursion but don't emit C4717; MSVC catches it.

**Fix (4 token removals):**
```cpp
// string.iC:1761
return getline(is, (string&)str, delim);   // drop move()
// string.iC:1767
return getline(is, (string&)str);          // drop move()
```
The lvalue `&` overloads at lines 1748-1757 already use this exact pattern. The cast invokes `String::operator string&()` ([`string.h:252`](../../../include/BALL/DATATYPE/string.h)) returning a real `std::string&` to the internal `str_` buffer, which `std::getline(istream&, string&, ...)` fills in place. ABI / link compat unchanged (function signatures unchanged).

**Severity:** correctness; guaranteed stack overflow if anyone calls `std::getline(stream, std::move(some_BALL_String), ...)` on any platform.

### Task A2: C4311 pointer truncation `T* → long` ⚠️ Codex-concern (incomplete)

**Where:**
- [`source/COMMON/hash.C:22`](../../../source/COMMON/hash.C#L22) — `(unsigned long)(void* const)`
- [`source/MOLMEC/MMFF94/MMFF94StretchBend.C:359,360,388,389,...`](../../../source/MOLMEC/MMFF94/MMFF94StretchBend.C#L359) — `(long)(BALL::Atom*)` ×6+
- [`source/STRUCTURE/triangulatedSurface.C:1288`](../../../source/STRUCTURE/triangulatedSurface.C#L1288) — `(unsigned long)(_Ty1)`

**Bug:** On 64-bit Windows (MSVC LLP64 model), `long` is 32-bit but pointers are 64-bit. Casting `T*` to `long` silently truncates the upper 32 bits, corrupting any pointer-as-identity use (hash keys, dedup, identity comparison). On 64-bit Linux/macOS (LP64), `long` is 64-bit so the same code happens to work — explains why CI passed everywhere despite the latent corruption on Windows.

**Fix — cast site (necessary but not sufficient):**
```cpp
// Before:
unsigned long h = (unsigned long)ptr;
long a_idx     = (long)atom_ptr;

// After:
std::uintptr_t h     = reinterpret_cast<std::uintptr_t>(ptr);
std::uintptr_t a_idx = reinterpret_cast<std::uintptr_t>(atom_ptr);
```

**Codex flagged:** MMFF94StretchBend uses `HashMap<long, Position>` and `long`-typed iterators/keys downstream of these casts. Widening the cast alone isn't enough — the **storage types must also move to `std::uintptr_t`** (or BALL's existing `PointerSizeUInt` typedef at [`global.h:207`](../../../include/BALL/COMMON/global.h#L207), which already exists for this purpose), otherwise the truncation just moves one assignment site downstream. Audit each call chain end-to-end.

**Severity:** correctness on Windows; latent data corruption in MMFF94 force-field calculations. Fix at the same time the casts are fixed.

### Task A4: `-Wtautological-constant-out-of-range-compare` ✗ Codex-corrected scope

**Where:** [`source/VIEW/KERNEL/representation.C:269-270`](../../../source/VIEW/KERNEL/representation.C#L269)

**Code:**
```cpp
if (drawing_precision_ < 0 || drawing_precision_ > BALL_VIEW_MAXIMAL_DRAWING_PRECISION ||
    drawing_mode_      < 0 || drawing_mode_      > BALL_VIEW_MAXIMAL_DRAWING_MODE)
```

**Codex correction:** The two halves of this check are NOT symmetric.
- `DrawingPrecision` is an enum with `DRAWING_PRECISION_INVALID = -1` — the `< 0` check *meaningfully* catches the invalid sentinel. **Keep this half.**
- `DrawingMode` has only non-negative enumerators — the `< 0` check IS tautological. **This half can be dropped** (or the comparison hoisted through a signed-integer view).

**Fix:**
```cpp
if (drawing_precision_ < 0 || drawing_precision_ > BALL_VIEW_MAXIMAL_DRAWING_PRECISION ||
    drawing_mode_      > BALL_VIEW_MAXIMAL_DRAWING_MODE)
```
…or, cleaner, give `DrawingMode` an explicit `INVALID = -1` sentinel matching `DrawingPrecision` so the symmetric check survives. Decide during implementation by reading the enum definitions.

**Severity:** code-quality, no behavioral impact (the tautological check is a no-op).

### Task A5: `-Wformat-overflow` in `CIFParserParser.y` (19 instances)

**Where:** [`source/FORMAT/CIFParserParser.y:230,233,236,239`](../../../source/FORMAT/CIFParserParser.y#L230) (via generated `.C`)

**Bug:** `sprintf` into too-small buffers in the error-reporting path (`%s` directive writing up to 2549 bytes into a 1-2550-byte buffer; `__builtin___sprintf_chk` may write past terminating nul). Buffer-overflow class warning.

**Fix:** Replace `sprintf` with `snprintf` passing the destination buffer size, or size the buffer based on the actual maximum input. Verify against the Bison version compat — the generated `.C` may be inheriting an old-skeleton pattern.

**Severity:** security-adjacent (memory corruption on malformed CIF input is possible if the parser path is reachable from untrusted data; BALL is a desktop molecular tool so attack surface is narrow but real).

### Task A6: `-Wstringop-truncation` (10 instances)

**Where:** various `strncpy` call sites (gcc traces to `__builtin___strncpy_chk` in `string_fortified.h:95`). Need to enumerate exact BALL source sites.

**Bug:** `strncpy` may truncate without nul-termination; gcc flags cases where the specified bound equals the destination size or the source length.

**Fix:** Audit each site. Prefer `std::string` assignment or explicit length+nul handling. For sites where truncation is intended, use `memcpy` with explicit nul-termination instead of `strncpy` to silence the warning intentionally.

**Severity:** memory safety; case-by-case.

## Tier B — Windows DLL hygiene

### Task B1: C4910 `extern template class BALL_EXPORT ...` ✓ Codex-verified

**Where:** [`include/BALL/MATHS/vector3.h:1145,1148`](../../../include/BALL/MATHS/vector3.h#L1145) + [`source/MATHS/vector3.C:10,13`](../../../source/MATHS/vector3.C#L10)

**Bug:** `extern template class` declares "don't instantiate here, link from elsewhere"; `__declspec(dllexport)` requires generating code. Contradictory. C4910. The matching definitions in `vector3.C` exist but lack `BALL_EXPORT`, so the instantiation is generated unexported — clients can't link to it from the DLL.

**Fix — move `BALL_EXPORT` from declaration site (`.h`) to definition site (`.C`):**

| File | Before | After |
|---|---|---|
| `vector3.h:1145` | `extern template class BALL_EXPORT std::vector<Vector3>;` | `extern template class std::vector<Vector3>;` |
| `vector3.h:1148` | `extern template class BALL_EXPORT TVector3<float>;` | `extern template class TVector3<float>;` |
| `vector3.C:10` | `template class TVector3<float>;` | `template class BALL_EXPORT TVector3<float>;` |
| `vector3.C:13` | `template class std::vector<Vector3>;` | `template class BALL_EXPORT std::vector<Vector3>;` |

### Task B2: Mirror the C4910 fix in atom.h/atom.C (hygiene)

**Where:** [`include/BALL/KERNEL/atom.h:1010`](../../../include/BALL/KERNEL/atom.h#L1010)

**Issue:** `template class BALL_EXPORT std::vector<Atom*>;` sits directly in the header *without* `extern`. Works on MSVC via COMDAT folding but every TU emits a definition — poor form, slows compile, fragile. Codex confirmed the same B1 pattern is the right move: `atom.h` gets `extern template class std::vector<Atom*>;`, [`source/KERNEL/atom.C`](../../../source/KERNEL/atom.C) gets the `BALL_EXPORT` definition.

### Task B3: C4251 STL members of DLL-exported classes (3495 instances)

**Issue:** Endemic Windows-DLL warning — exported classes have `std::vector<T>` / `std::string` / etc. members, MSVC warns clients linking against the DLL might see a different STL ABI. Cosmetic when the entire surface uses one MSVC toolchain (Phase 4's vcpkg pin ensures this); genuinely dangerous when mixing CRTs. BALL already partially silences this in [`include/BALL/COMMON/exception.h:18`](../../../include/BALL/COMMON/exception.h#L18) but only inside a narrow push/pop window for `std::string`.

**Fix:** Broaden to a project-wide `#pragma warning(disable: 4251)` in [`include/BALL/COMMON/global.h`](../../../include/BALL/COMMON/global.h) under `BALL_COMPILER_MSVC`, with a comment explaining the rationale. ~3 lines added.

**Sequencing:** Land B1 first — the proper explicit-instantiation export may quiet a non-trivial subset of these warnings on its own; re-measure before applying B3.

### Task B4: C4996 `BALL::GeneticIndividual` deprecation noise (5 instances)

**Decision needed:** either un-deprecate (the methods are still used internally), or refactor to stop using the deprecated methods inside BALL itself, or add `#pragma warning(suppress: 4996)` at the STL-instantiation sites. Cosmetic only; pick the cheapest option.

### Task D4: Windows release workflow `LNK1104: tbb12_debug.lib` — `--config Release` missing on multi-config generator

**Where:** [`.github/workflows/release.yml`](../../../.github/workflows/release.yml) Build (Windows) step (same pattern in [`.github/workflows/ci.yml`](../../../.github/workflows/ci.yml) Build (Windows) — backport once verified).

**Bug:** `cmake --build --preset ci-windows --target BALL VIEW BALLView` runs against Visual Studio's *multi-config* generator. Without `--config Release` the build defaults to **Debug** config, which makes MSBuild link against `tbb12_debug.lib`. The vcpkg `x64-windows-release` overlay triplet builds only Release variants by design (~50% time + space saving on CI), so `tbb12_debug.lib` doesn't exist and the linker fails with `LNK1104: cannot open file 'tbb12_debug.lib'`.

**Why this didn't trip earlier in CI:** the regular `ci.yml` Windows job has been running for weeks with a warm vcpkg binary cache populated *before* the release-only triplet landed, so the Debug TBB binaries were already in the cache and got linked silently. The `release.yml` workflow ran with a cold cache (different cache key from ci.yml — `release.yml` was a brand-new workflow), forced a fresh vcpkg install, and the Debug-variant gap surfaced.

**Surfaced:** release workflow run [25908337693](https://github.com/BALL-Project/ball/actions/runs/25908337693) on tag `v1.6.0` (2026-05-15). Caused the Windows installer for v1.6.0 to be skipped — only the macOS arm64 installer shipped.

**Fix:**
```yaml
- name: Build (Windows)
  shell: pwsh
  run: |
    cmake --build --preset ci-windows --config Release --target BALL VIEW BALLView
```
Apply in **both** `release.yml` (the immediate gap) AND `ci.yml` (where it's latent — will fail the moment the warm cache expires or the cache key changes). One-line edit per file.

**Severity:** medium for ci.yml (latent — will surface eventually); high for release.yml (blocking v1.6.0 Windows installer right now). Trivial fix.

**Verification path:** push the fix, re-run the release workflow against `v1.6.0` via `gh workflow run release.yml -f tag=v1.6.0`. Windows job should now produce `BALLView-v1.6.0-windows-x64.zip` and the GitHub Release gets the second asset attached. Same fix in ci.yml is verified by the next regular push CI run going green with the modified build command.

### Task D5: BALLView.app Info.plist has empty CFBundleIdentifier, CFBundleVersion, CFBundleName

**Where:** [`source/APPLICATIONS/BALLVIEW/`](../../../source/APPLICATIONS/BALLVIEW/) (BALL's CMake `CFBundle*` config). Possibly `cmake/BALLConfigBundle*.cmake` or similar.

**Bug:** The macdeployqt-processed BALLView.app from v1.6.0 has this Info.plist:

```xml
<key>CFBundleIdentifier</key><string></string>
<key>CFBundleShortVersionString</key><string></string>
```

All bundle-identity fields are empty strings — the Info.plist template exists but the CMake variables that fill it (`MACOSX_BUNDLE_BUNDLE_NAME`, `MACOSX_BUNDLE_GUI_IDENTIFIER`, `MACOSX_BUNDLE_BUNDLE_VERSION`, etc.) aren't set on the BALLView target.   MACOSX_BUNDLE_SHORT_VERSION_STRING "${PROJECT_VERSION}"
```cmake
  MACOSX_BUNDLE_LONG_VERSION_STRING  "BALLView ${PROJECT_VERSION}"
  MACOSX_BUNDLE_COPYRIGHT          "© BALL maintainers. LGPL-2.1."

  MACOSX_BUNDLE_ICON_FILE          "BALLView.icns"

```

Or fix the Info.plist.in template that's already in the repo to use `@PROJECT_VERSION@` / `@CMAKE_PROJECT_NAME@` / a hardcoded `CFBundleIdentifier`.

**Decide:** the canonical CFBundleIdentifier string. Common conventions:
- `de.uni-tuebingen.ball.ballview` — Tübingen institutional reverse-DNS (probably the right answer given the org)
- `org.ball-project.ballview` — matches GitHub org `BALL-Project`
- `de.ball-project.ballview` — variant

This is a Phase 8 prerequisite (notarization REQUIRES it), so D5 should ideally land before Phase 8 kicks off. Trivial source-side fix; the harder decision is the canonical identifier string.

**Severity:** medium now (bundle works post-D4-mac resign, but the metadata is broken); high for Phase 8 (notarization blocker).

### Task D4-mac: macOS .app SIGKILL'd on launch (macOS 26+) — needs ad-hoc resign after macdeployqt

**Where:** [`.github/workflows/release.yml`](../../../.github/workflows/release.yml) macOS path.

**Bug:** v1.6.0's macOS .app crashed at load on macOS 26.4.1 with `Termination Reason: Namespace CODESIGNING, Code 2, Invalid Page` (SIGKILL Code Signature Invalid). Crash incident `D4252593-FDD2-4001-94FD-E36402AE15BE`, 2026-05-15.

**Root cause:** `macdeployqt` rewrites `install_name` paths in the bundled Qt frameworks (so they resolve relative to the .app, not Homebrew's `/opt/homebrew/Cellar/`). The path rewrite changes the dylib bytes → invalidates the Qt frameworks' original (Homebrew-applied) signatures. Pre-macOS 26 this used to "just work" with `xattr -dr com.apple.quarantine`; macOS 26 tightened CODESIGNING enforcement — now SIGKILLs any bundle with internal signature inconsistency at load.

Forensic evidence on the v1.6.0 artifact:
```
$ codesign --verify --deep --strict BALLView.app
BALLView.app: code has no resources but signature indicates they must be present
```
The main binary was `adhoc,linker-signed` (ld's default for arm64 binaries) but the bundle had no `_CodeSignature/CodeResources` manifest because macdeployqt doesn't generate one.

**Fix:** add an ad-hoc resign step in `release.yml` AFTER `macdeployqt` AND AFTER bundling `data/` (must be the LAST step before zip, otherwise subsequent file additions re-invalidate the seal):
```yaml
- name: Ad-hoc resign bundle (macOS — required after macdeployqt + data bundling on macOS 26+)
  if: matrix.os == 'macos-arm64'
  run: |
    codesign --force --deep --sign - "${{ steps.locate-mac.outputs.app }}"
    codesign --verify --deep --strict --verbose=2 "${{ steps.locate-mac.outputs.app }}" 2>&1 | tail -10
```
Landed in release.yml (this commit) and the v1.6.0 release asset re-uploaded locally with the resigned bundle (SHA-256 `cdf1f80bd09c015e9c3fa65c591584cf93754a3926556bad943ed98a60f0eb36`).

**Verified post-fix:**
- `codesign --verify --deep --strict` passes
- Bundle now has `_CodeSignature/CodeResources` (174 KB)
- Main binary signature identity `BALLView-55554944df708d0a9fac3a828f3bb7994ff79293`
- `spctl --assess` still says "rejected" — expected, no Developer ID — right-click→Open dance still applies but bundle now LOADS

**Phase 8 successor:** the proper fix is `codesign --sign "Developer ID Application: ..." --options runtime` + notarization (per `08-SIGNING-RESEARCH.md`). D4-mac is the BALL-1.6.x stopgap until Phase 8 lands.

### Task D3: Linux ccache cache-save tar failure (1 instance)

**Where:** Linux build job, post-build cache save step:
> Failed to save: "/usr/bin/tar" failed with error: The process '/usr/bin/tar' failed with exit code 2

**Impact:** The Linux ccache cache for the next run wasn't saved. Subsequent runs on the same cache key cold-compile, slowing iteration. Build itself still green. Could be transient (race / runner storage pressure / cache size limit hit) or real (corrupted state, permission issue).

**Investigation steps before fix:**
1. Run the workflow again; check if the failure recurs on the same Linux job. Single failure across N runs → transient, ignore.
2. If recurring: enable `ACTIONS_RUNNER_DEBUG=true` on the cache step to capture the tar invocation + stderr.
3. Common causes: cache size exceeds 10 GB limit (split ccache into multiple keys), runner disk pressure (clean before cache), file permissions on ccache_dir (chmod).

**Fix:** likely a `tar` flag adjustment or a cache-key split, depending on root cause. Sub-Phase 5.1 task that's mostly diagnosis.
