**MaterialController + LightController now own the full Stage material/light field sets, and scene.C's applyPreferences + the 5 light-editor refresh sites drive the rendered scene through those controllers instead of the legacy MaterialSettings/LightSettings dialog apply()/updateFromStage() bodies — build green (BALL_UI_V2=ON), GUI render UAT pending.**

## Accomplishments
- **MaterialController** grew the three Stage::Material colors (ambient/specular/reflective as QColor mirror members + setters/signals/Q_PROPERTYs) and a new `applyDefaultMaterial()` that writes the complete mirrored field set onto the Stage default material then calls `Scene::updateAllMaterials()` — mirroring the legacy `MaterialSettings::apply()` preferences branch (materialSettings.C:85-90). The per-rep `apply()` branch is unchanged.
- **LightController** grew an authoritative `std::vector<LightSource> lights_` member + accessors; `revert()` now pulls the FULL live light list (not just ambient); `apply()` was rewritten to clear + re-add the full controller-owned list (mirroring `LightSettings::apply()` lightSettings.C:384-393); a public `syncFromStage()` entry point was added for the Scene refresh sites. The aggregate ambient-intensity slider surface the Inspector LightsSection binds to is preserved.
- **scene.C** `applyPreferences()` light branch now drives `LightController` and the material branch drives `MaterialController::applyDefaultMaterial()`; the 5 `light_settings_->updateFromStage()` refresh sites (UPDATE_CAMERA, resetCamera_, setDefaultLighting, readPreferences, setCamera) now call `LightController::syncFromStage()`. All surrounding behavior (coordinate-system block, fog/background renderer loops, `lightsUpdated(false)`, final `updateGL()`) preserved verbatim.
- **Build green:** `cmake --build build-ui-on --target BALLView` (BALL_UI_V2=ON, macOS arm64) — libVIEW.dylib + BALLView.app link clean.

## Decisions Made
See `key-decisions` in frontmatter. The core decision: during this migration window the controllers re-assert the live Stage state through their backend on applyPreferences (the Inspector is the authoritative editing surface), rather than reading the soon-to-be-deleted dialog widgets. This is behavior-preserving for the rendered scene and matches the StageController cut-over recipe.

## Deviations from Plan

None — plan executed exactly as written. The plan explicitly granted discretion on the controller reach-mechanism ("do not invent a parallel Scene-owned controller pointer if one is already reachable"); since none was reachable (Inspector owns the controllers privately, no singleton), transient stack-local controllers were used, which is the minimal, leak-free interpretation.

## Issues Encountered
- **Controller reachability:** scene.C has no handle to the Inspector-owned controllers (they are private members of `InspectorView`, not singletons). Resolved by constructing transient controllers on `stage_` at each render-refresh site — the controllers operate on the `Scene::getInstance(0)`/Stage singletons, so this is correct and lifecycle-free.
- **Acceptance-grep vs documentation comments:** the new explanatory comments originally referenced the old call names (`light_settings_->apply()`, etc.), which a literal `grep -c` would count. Comments were reworded to describe the legacy calls without the exact call syntax so the acceptance greps (`== 0`) reflect the genuine state: there are zero LIVE legacy reach-throughs on Scene's render path (verified with a comment-excluding grep).
