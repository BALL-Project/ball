## Decisions Made
See `key-decisions` in frontmatter. The core decisions: (1) applyPreferences re-asserts the live state through the controller backend (the Inspector is authoritative), matching the 999.58-01 pattern; (2) mouse/wheel sensitivity use an unset sentinel because they have no backend getter and the controller-driven path must not clobber the live value; (3) the isBusy defer-guard was added to protect the renderer-switch / rep-rebuild.

## Deviations from Plan

None to the plan's task actions. Two notes:
- **[Rule 2 - missing critical functionality, plan-mandated]** The `MainControl::isBusy()` defer-guard the plan's Task 1 requires was not previously on `StageController::apply()` (only the ControllerApplyGuard re-entrancy shield was). Added it (mirrors StereoController) so the extended apply()'s renderer-switch + bulk rep-rebuild cannot run mid-busy-cycle (T-99858-04 mitigation). Committed with Task 1 (`b2f905941a`).
- **Include path casing:** the canonical on-disk directory is `BALL/VIEW/KERNEL/MODES/` (uppercase). The initial lowercase `modes/` include emitted a `-Wnonportable-include-path` warning; corrected to `MODES/` to match the on-disk casing and the rest of the tree before the final build.

## Issues Encountered
- **Mouse/wheel sensitivity have no backend getter.** `InteractionModeManager` exposes `setMouseSensitivity`/`setMouseWheelSensitivity` only (no getters), and the legacy dialog hardcoded its sliders to 5 at construction rather than reading the live value. There is therefore no way to read sensitivity back in `revert()`. Resolved with an unset sentinel (`< 0`): the controller pushes sensitivity only when the Inspector explicitly sets it, so the behavior-preserving applyPreferences path leaves the live interaction sensitivity untouched.
- **`stage_settings_->updateFromStage()` at scene.C:388 (REMOVE_COORDINATE_SYSTEM handler) is still a live `stage_settings_->` call** but is OUT OF THIS PLAN'S SCOPE and is NOT on the render path. `updateFromStage()` (stageSettings.C:205-230) is a one-way readback that only populates the stage DIALOG widgets (`setColor`/`setValue`/`setChecked` on dialog controls) — it mutates no render state, exactly like the `getGLSettings()` readback this plan removed. The dialog is still constructed and hosted in Preferences (Plan 03 removes the construction + registration), so its widgets must stay coherent until then. Left intact deliberately; documented honestly rather than reworded to game the apply/getGLSettings grep. The plan's success-criterion #3 ("no live `stage_settings_->{apply,getGLSettings,...}` reach-throughs on the render path") is satisfied: this is a dialog-widget readback, not a render-path call.
