# `999.64` — Per-section "Reset section" affordance

**v1.7.x-36 (new)** · Wave B · ~1–2 days

> **Ingest note (2026-05-22).** The handover PLAN.md minted this as `v1.7.x-31 (new)`, but `v1.7.x-31` is already used in this repo for the #501 renderer-plugin startup-warning item (Phase 999.54). Re-minted to the next free patch-queue ID **v1.7.x-36** during ingest. The handover phase id `999.63` was renumbered to **999.64** (+1) to clear the collision with the in-flight `999.58` set.

> **Codex reconciliation (2026-05-22, MEDIUM #10).** This is a
> **REPLACEMENT, not a from-scratch add.** Ground truth (2026-05-22
> audit): the `InspectorSection` header reset affordance ALREADY exists
> (`setResettable()` + `resetRequested()` signal,
> `inspectorSection.{h,C}`), and ~9 sections ALREADY implement reset as a
> two-step `controller_->revert(); controller_->apply()`
> (backgroundSection / clippingSection / coloringSection / labelSection /
> lightsSection / materialSection / modelSection / stageSection /
> stereoSection). That two-step is the dual-path-in-miniature the
> contract closes: `revert()` re-reads the owner into the controller,
> then `apply()` pushes it back — two owner round-trips, two potential
> events, and "defaults" actually means "whatever revert re-read". This
> phase REPLACES the two-step with a single `Controller::reset()` that
> captures current → invokes method-defined defaults → emits ONE event +
> records the reversible payload.

## Goal

Replace the ad-hoc two-step per-section reset (`revert(); apply()`) with
a single `Controller::reset()` going through the §2 contract, wired to
the already-present header Reset glyph. One event, one payload, true
method-defined defaults — across all 14 sections.

## Why now

The section-level reset affordance shipped (v1.7.x-18) but its
implementation is the two-step `revert(); apply()` — which (a) means two
owner round-trips, (b) can emit two events, and (c) conflates "reset to
defaults" with "re-read current owner state". The `999.59` contract gives
us a clean single-call implementation: `Controller::reset()` captures the
current state as the payload's `before`, sets the method-defined defaults
as `after`, and runs one §2 `apply()` — exactly one event, one reversible
payload.

## Scope

**In:**

1. **`Controller::reset()`** on the base class (`999.59-01` defines the
   base + the `virtual void reset()`). Each Controller overrides:
   - Captures current state (becomes payload `before`).
   - Computes method-defined defaults (becomes payload `after`).
   - Runs the SINGLE §2 `apply()` path (guard / mutate / one event /
     declared invalidate / record). NOT `revert()` then `apply()`.
   The single `apply()` carries `before=current`, `after=defaults` —
   undoable in v2.0.
2. **Replace the two-step in all ~9 sections.** Each section's reset
   handler currently does `if (controller_) { controller_->revert();
   controller_->apply(); }`. Replace with `if (controller_)
   controller_->reset();`. The `setResettable()` / `resetRequested()`
   header plumbing stays — only the slot body changes.
3. **Read-only sections** (Properties / Summary / RepHeader) implement
   `reset()` as a no-op + comment (they have no Controller to reset).

**Out:**
- "Reset all sections" — separate v1.7.5 affordance (different scope).
- Per-row reset cleanup — orthogonal, v1.7.5.
- Reset-confirmation dialog — the existing `setResettable(confirm_text)`
  confirm path stays available per-section; the explicit decision is no
  *mandatory* confirm, because v2.0 undo makes accidental reset trivially
  recoverable and the contract already captures the payload.

## Files touched

**Edited:**
- `inspectorSection.{h,C}` — the glyph/hover/`resetRequested()` plumbing already exists; no structural change, just confirm the relay reaches the new single-call path.
- `controller.{h,C}` (base) — `virtual void reset();` (base defines; default = no-op for read-only sections). The base + the `apply()` it calls land in `999.59-01`.
- All 9 Controllers — implement `reset()` (~10 LOC each): capture current → set defaults → `apply()`.
- The ~9 sections listed in `files_modified` — swap the two-step reset slot body for the single `controller_->reset()` call.

## Acceptance criteria

- [ ] Every of the 14 sections shows a Reset glyph on header hover (already true; verify unbroken).
- [ ] Clicking reset reverts the section's state to the Controller's **method-defined defaults** (not just a re-read of current owner state).
- [ ] The two-step `controller_->revert(); controller_->apply()` is gone from all ~9 sections; each now calls `controller_->reset()`.
- [ ] Exactly ONE `ApplyPayload` / one event emitted per reset (verified by counting events in a contract test — contrast the old two-step which could emit two).
- [ ] No flicker / no transient "between defaults and current" state — `ControllerApplyGuard` from `999.59` protects this.
- [ ] Reset works on the read-only sections too (Properties / Summary / RepHeader) — they implement `reset()` as a no-op + comment.

## Risks

- **Defaults vary by Representation type.** A SES Surface's "default sphere radius" is nonsensical. Each Controller's `reset()` is allowed to delegate to a Representation-type-aware default-provider — `999.59`'s payload already carries `target`.
- **A section relied on `revert()`'s re-read side effect.** Audit each of the ~9 sections during the swap: if a section used `revert()` to resync widgets from the owner (rather than to reset to defaults), that resync stays as a separate explicit call; only the *reset* semantics move to `reset()`.

apply()` shape (one event, one payload). Don't reintroduce the two-step.
