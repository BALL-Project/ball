# Phase 999.45 Plan 01 — Workspace consolidation (ProjectDock + BottomDrawer + WorkspaceManager + configMigration)

## Objective

Replace the legacy 5-dock-on-startup layout with a refreshed default — left `ProjectDock` (3 tabs: Structures / Representations / Datasets), right Inspector dock (registered by 999.44 under objectName `"inspectorDock"`), bottom `BottomDrawer` (collapsed 24 px / expanded 240 px) for Logs + FileObserver, center 3D scene. Expose a `WorkspaceManager` with **3 named presets** — `Default` / `Classic` / `Focused` — plus a `UserDefined` slot. Ship binary `.layout` files in `data/BALLView/workspaces/`, add a first-run migration prompt + `~/.BALLView.pre-v2.bak` auto-backup, add a clickable workspace label to the status bar, and add `configMigration.C` that lifts the legacy `~/.BALLView` flat file into platform-correct XDG / `Library/Application Support` / `%APPDATA%` locations on first launch with `BALL_UI_V2=ON`.

Everything that affects user-visible behavior is gated behind `BALL_UI_V2` (default OFF in v1.7-RC stages; flipped ON in 999.48). The new widget classes (`ProjectDock`, `BottomDrawer`, `WorkspaceManager`) compile in both branches — they are additive VIEW classes; only their registration in `Mainframe` is `#ifdef BALL_UI_V2`. With the flag OFF, `Mainframe` falls back to the legacy 5-dock layout exactly as today (this IS the Classic preset, so the wiring is shared).

## Dock objectName convention (coordination with 999.44)

WorkspaceManager addresses docks by `QObject::objectName` (Qt's `saveState()` / `restoreState()` require unique names). The convention this plan publishes:

| Dock                              | objectName              | Owner       | Default area  |
| --------------------------------- | ----------------------- | ----------- | ------------- |
| ProjectDock                       | `"projectDock"`         | **999.45**  | Left          |
| InspectorDock                     | `"inspectorDock"`       | **999.44**  | Right         |
| BottomDrawer                      | `"bottomDrawer"`        | **999.45**  | Bottom        |
| MolecularControl (legacy/Classic) | `"MolecularControl"`    | legacy      | Left          |
| GeometricControl (legacy/Classic) | `"GeometricControl"`    | legacy      | Left          |
| DatasetControl (legacy/Classic)   | `"DatasetControl"`      | legacy      | Top           |
| LogView (legacy/Classic)          | `"LogView"`             | legacy      | Bottom        |
| FileObserver (legacy/Classic)     | `"FileObserver"`        | legacy      | Bottom        |

The Classic preset uses the legacy dock names; Default / Focused use the new dock names. WorkspaceManager's `apply(Preset)` adds/removes docks accordingly.

## Scope-trim breadcrumbs (recorded upfront)

- **Status-bar workspace label** ships as a minimal clickable `QLabel` with a `QMenu` popup of preset names + "Save current as…". The Handover §5.5 ambition of a fancy popup with preview thumbnails is forwarded to a v1.7-RC patch.
- **`.layout` file format**: binary `QByteArray` produced by `QMainWindow::saveState()` (Qt's documented format) wrapped in a small framing header (`"BALLVIEW-WS-V1\n<base64 payload>\n"`) so the file is greppable and the version is explicit. A JSON sidecar (`*.json`) records the dock visibility map + preset display name. We ship presets as **source files** generated at first run from code (not pre-baked binary blobs), because `QByteArray` produced by Qt 6 saveState is opaque and varies by Qt version — generating them from the code paths the first time WorkspaceManager is constructed guarantees they round-trip cleanly under whatever Qt the user is running. The `data/BALLView/workspaces/*.layout` files committed to source are **JSON descriptors** of the preset (areas + sizes + visibility), and WorkspaceManager materializes them into `saveState()` blobs at runtime. This is more portable than committing Qt-version-bound binary blobs.
- **configMigration.C platform paths** use Qt's `QStandardPaths::AppConfigLocation` + `AppLocalDataLocation` per Handover §09; the actual platform-specific paths Qt produces match the §09 spec (verified in code comments).
- **No new `WorkspaceManager` Qt INI section** — uses the same `~/.BALLView` (legacy) or `<AppConfig>/BALLView.ini` (post-migration) file. Section name: `[Workspace]`. Keys: `currentPreset`, `userDefinedPayload` (base64).
- **First-run prompt** uses `QMessageBox::question` with two custom buttons; **not** a hand-coded `SectionHeader` dialog. The §5.4 prompt is one line of body text — `QMessageBox` is the right tool. Future ornamentation deferred to v1.7-RC patch.
- **Translation strings**: all new user-visible strings are wrapped in `tr()` per project convention. The community translation round (maintainer-Q4) picks them up; English + best-effort de_DE ship in v1.7.

## Tasks

### Task 1 — `WorkspaceManager` skeleton (preset enum + API + `.layout` JSON loader)

type=auto

`include/BALL/VIEW/KERNEL/workspaceManager.h` + `source/VIEW/KERNEL/workspaceManager.C` — `class WorkspaceManager : public QObject` with:

- `enum Preset { Default, Classic, Focused, UserDefined }`
- `static WorkspaceManager& instance()` (singleton, attached to `QApplication`)
- `Preset currentPreset() const` / `void setCurrentPreset(Preset)`
- `QString presetDisplayName(Preset) const` (returns `tr("Default")` etc.)
- `bool apply(Preset, QMainWindow* main)` — performs the layout (dock add/remove/dock-area moves + sizes + visibility). Returns false if preset unknown or main is null.
- `bool save(QMainWindow* main, const QString& name)` — saves current state as a user-defined preset under `~/.config/BALLView/workspaces/<name>.layout` (post-migration path) or platform equivalent.
- `bool load(QMainWindow* main, const QString& name)` — loads a user-defined preset by name.
- `QStringList userPresets() const` — list of available user-defined preset names.
- `Q_SIGNALS: void presetChanged(Preset)`

The built-in presets (`Default`, `Classic`, `Focused`) live as compiled-in JSON in `data/BALLView/workspaces/*.layout` (loaded via `BALL::Path::find`). Format described in the file header comment. `apply()` calls `QMainWindow::saveState()` first (so the in-memory state matches the preset request) and `QMainWindow::restoreState()` for the binary path; for the JSON-described built-ins, `apply()` walks the JSON and reconstructs dock visibility / dock-area assignments / split sizes programmatically.

Register in `source/VIEW/KERNEL/sources.cmake` (sources + moc).

Commit: `feat(999.45/01): add WorkspaceManager skeleton (KERNEL singleton + Preset enum + apply/save/load API)`

### Task 5 — `WorkspaceManager::apply()` implementation (built-in presets)

type=auto

Fills in the stub from Task 1: parse each preset's JSON descriptor, walk the `docks` array, and for each dock:

1. Look up the registered `QDockWidget*` by `objectName` (via `main->findChild<QDockWidget*>(name)`). If not found (e.g., `inspectorDock` when 999.44 hasn't landed locally), skip with a debug log — don't fail.
2. `main->addDockWidget(area, dock)` to place it in the target area.
3. `dock->setVisible(visible)`.
4. After all docks placed, call `main->resizeDocks(...)` with the size hints from JSON.
5. Toolbars: walk `main->findChildren<QToolBar*>()` and set visible per the `toolbarsVisible` flag.

For `Classic`, the legacy 5 docks must exist; if they're not present (e.g., `BALL_UI_V2=ON` build that doesn't create them by default), the preset is a no-op + warning. The intent for v1.7 is that **both layouts are constructed at startup**, and WorkspaceManager just shows/hides + repositions; this is simpler than constructing/destroying docks per preset switch (which would trash the message-bus registrations).

Commit: `feat(999.45/05): implement WorkspaceManager::apply() for Default/Classic/Focused presets`

### Task 6 — `configMigration.{h,C}` (legacy `~/.BALLView` → platform-correct path)

type=auto

`include/BALL/VIEW/KERNEL/configMigration.h` + `source/VIEW/KERNEL/configMigration.C` — `class ConfigMigration` with one static method:

- `static MigrationResult run(const QString& legacyPath)` — checks for legacy `~/.BALLView`, if present and the target platform path doesn't already exist:
  1. Compute target path via `QStandardPaths::writableLocation(QStandardPaths::AppConfigLocation) + "/BALLView.ini"` (Linux: `~/.config/BALLView/BALLView.ini`, macOS: `~/Library/Application Support/BALLView/BALLView.ini`, Windows: `%APPDATA%/BALLView/BALLView.ini`).
  2. Make target directory if missing.
  3. Copy legacy file to target path.
  4. Migrate the `workspaces/` subdirectory the same way (legacy `~/.BALLView_workspaces/` → `<AppConfig>/BALLView/workspaces/` if such legacy dir exists; if not, no-op).
  5. Write a `migrated_from = <legacy path>` marker key to `[Migration]` section of the target file.
  6. Return `MigrationResult { performed, sourcePath, targetPath, error }`.
- The legacy file is **not** deleted (the user keeps it as a self-service backup; Task 7 makes a `.pre-v2.bak` copy explicitly before the migration prompt fires).
- Idempotent: if target already exists, skip with `performed=false`.
- Cache directory is computed but `ConfigMigration` doesn't migrate cache (Qt apps regenerate cache on first run; not load-bearing).

Register in `source/VIEW/KERNEL/sources.cmake`.

Commit: `feat(999.45/06): add ConfigMigration — legacy ~/.BALLView → XDG/AppSupport/AppData on first launch`
