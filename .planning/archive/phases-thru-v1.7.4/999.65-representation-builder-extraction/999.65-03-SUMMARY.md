## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Notifier routing required a friend forwarder + a header change not listed in `files_modified`**
- **Found during:** Task 1 (first VIEW build).
- **Issue:** The plan's interface note suggested routing the builder's messages "through main_control_". My first cut used a `.C`-local anonymous-namespace `RestoreNotifier` calling `mc_.notify_(message)` directly — which failed to compile: `ConnectionObject::notify_` is **protected**, and a free/anonymous-namespace class is not a friend (only `RepresentationManager` itself is, via `connectionObject.h:61`). RepresentationManager is also a `BALL::Object`, NOT a `ConnectionObject`, so Plan 02's nested-class-reaches-inherited-protected trick does not apply here.
- **Fix:** Added a small `RepresentationManager::notifyMessage_(Message*)` member (the friend member CAN reach `main_control_->notify_`) and pointed `RestoreNotifier` at it. This required editing `include/BALL/VIEW/KERNEL/representationManager.h` (a `class Message;` forward decl + the `notifyMessage_` declaration), which is NOT in the plan's `files_modified` list (`representationManager.C`, `displayProperties.C`, `displayProperties.h`). The change is the minimal correct way to preserve the plan's stated message routing + byte-identical ownership-transfer semantics.
- **Files modified:** `include/BALL/VIEW/KERNEL/representationManager.h`, `source/VIEW/KERNEL/representationManager.C`.
- **Verification:** VIEW + BALLView re-linked clean BALL_UI_V2=ON; the message flow (ADD_TO_GEOMETRIC_CONTROL, <2-rep CENTER_CAMERA, per-rep UPDATE_PROPERTIES) matches both the legacy dialog path and the manager's existing `main_control_->notify_(...)` calls.
- **Committed in:** `022a875199` (Task 1 commit).
