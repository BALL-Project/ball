  <action>
    In `GLRenderWindow::initializeGL()` (source/VIEW/RENDERING/glRenderWindow.C),
    after `checkGL()` and before/after `scene->initializeGLContext()` (the context
    is current throughout — pick a spot where `this->context()` is valid), emit ONE
    single machine-parseable line to `std::cout` per D-04. Prefix it with a stable,
    greppable token: `BALLVIEW_GL_DIAG ` followed by compact `key=value` pairs
    (space-separated) OR single-line JSON — Claude's discretion, but it MUST be one
    physical line and trivially greppable.

    Required fields (D-04 + the "Specific Ideas" section — these are the fields that
    would have caught the Phase 2 detached-window / HiDPI / no-paintGL bugs):
      - gl_vendor      = glGetString(GL_VENDOR)
      - gl_renderer    = glGetString(GL_RENDERER)
      - gl_version     = glGetString(GL_VERSION)
      - gl_profile     = format().profile() (expect CompatibilityProfile)
      - surface_version = format().majorVersion()"."format().minorVersion()
      - depth_bits     = format().depthBufferSize()
      - stencil_bits   = format().stencilBufferSize()
      - samples        = format().samples()
      - device_pixel_ratio = devicePixelRatioF()
      - default_fbo    = defaultFramebufferObject()
      - fbo_size       = (width()*devicePixelRatioF())"x"(height()*devicePixelRatioF())
                         — the real framebuffer pixel size; mismatch vs widget size
                         was the HiDPI bug
      - renderer_backend = the selected backend identifier. Use a literal "GL" /
        "fixed-function-gl" string here — this phase has only the GL backend; the
        field exists so the QRhi/GL-core spike (Phase 05.1) can populate it. Do NOT
        invent a backend-query API.

    Flush after the line (`std::endl` or `std::cout.flush()`) so CI captures it even
    if BALLView is killed shortly after. Use `std::cout` (not `BALL::Log`) — D-04
    says stdout, and CI greps stdout. Guard nothing behind a debug flag — it must
    appear on every startup. Keep it to a few lines of code; this is the ONLY source
    change in this phase.
  </action>

    that Plan 02's CI workflow invokes on macOS and Linux.

    Arguments / env it accepts:
      - `$1` = path to the BALLView executable (default: autodetect
        `build/bin/BALLView.app/Contents/MacOS/BALLView` then `build/BALLView`).
      - `BALL_DATA_PATH` / `BALLVIEW_DATA_PATH` — if unset, default both to

        per D-08 — the script just respects the prefix, it does not hardcode xvfb).

    What it does (D-01 / D-09 — reuse the existing export path, render the automatic
    startup-demo peptide; do NOT build a new GL harness):
      1. Pick an output PNG path in a temp dir.
      2. Launch BALLView headless with the env vars set, capturing stdout+stderr to a
         log file. Trigger the existing `exportPNGAfterTTL` / `Scene::exportPNG`
         offscreen export so the auto-loaded demo peptide is rendered and written to
         the PNG. The exact trigger mechanism is Claude's discretion — work it out
         from `Scene::exportPNG`/`exportPNGAfterTTL` and `main.C`'s argv parsing:
         add a minimal `-export-png <path>` (or `-smoke`) CLI flag to `main.C` that
         calls the existing export-after-TTL path on the main renderer's RenderSetup
         and quits after the export, OR drive it some equally non-invasive way. If
         the demo peptide genuinely cannot be wired to a headless export, fall back
         to opening a fixed known PDB from `data/` (D-09 documented fallback) — but
         try the demo path first and note in the SUMMARY which path was used.
         NOTE: if a `main.C` CLI flag is the chosen trigger, that is a small, allowed
         addition to this phase's scope (D-01 + Claude's-discretion in CONTEXT) —
         add `source/APPLICATIONS/BALLVIEW/main.C` to this plan's effective edits
         and keep the flag minimal (parse, call existing export path, quit).
      3. Assert the PNG exists.
      4. Assert the PNG is NON-BLANK: a real molecule render is not a single flat
         color. Implement a non-blank check that needs no extra dependency — e.g.
         use Python's stdlib via `python3 -c` with no PIL (parse PNG IHDR for
         dimensions, and to test "non-blank" decompress IDAT and check for >1
         distinct pixel value), OR if ImageMagick/`sips` is acceptable use it but
         gate on its presence with a fallback. Prefer the stdlib-`python3` route so
         the script has zero extra deps on every runner.
      5. Assert PNG dimensions match the expected viewport size (D-02). Read the
         expected width/height from the `BALLVIEW_GL_DIAG` `fbo_size` field in the
         captured log (D-05 cross-check) — grep the log for `BALLVIEW_GL_DIAG`,
         parse `fbo_size`, and compare to the PNG's IHDR dimensions. If the diag
         line is absent, FAIL (that means no GL context was created — exactly the
         Phase 2 blank-render bug class).
      6. Exit 0 on all-pass; print a clear diagnostic and exit non-zero on any
         failure (missing PNG / blank PNG / dimension mismatch / missing diag line).
         On failure, leave the PNG + log in place and print their paths so Plan 02's
         CI can upload them as artifacts.
