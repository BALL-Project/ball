<domain>
## Phase Boundary

Stand up an early automated regression net: a 3-OS GitHub Actions build matrix
(macOS-arm64, Linux, Windows) + a headless render smoke check + a GL-capability
startup diagnostic. Pulled forward from the old Phase 9 per the Codex adversarial

**In scope:** `.github/workflows/` CI definition, the render smoke check, the

Requirements: CI-01, DIAG-01.

<decisions>
## Implementation Decisions

### Render smoke check
- **D-01:** Reuse BALL's existing `exportPNGAfterTTL` / `Scene::exportPNG` offscreen-export path. The smoke check launches BALLView with the startup demo, lets the TTL fire a PNG export, then asserts the PNG is non-blank (and at the expected viewport size). Do NOT build a new GL test harness — reuse what BALL already has.
- **D-02:** The smoke check's pass/fail oracle is: PNG produced + non-blank pixels + expected dimensions, cross-checked against the `DIAG-01` diagnostic line (see D-05).

### Windows CI job
- **D-03:** The Windows job is present from day one but **non-blocking** (`continue-on-error: true` / not a required check). It flips to required once Phase 4 lands the vcpkg manifest. macOS + Linux jobs are blocking/required immediately.

### GL-capability diagnostic (DIAG-01)
- **D-04:** BALLView logs the GL-capability diagnostic to **stdout as a single machine-parseable line** at startup — GL vendor / version / profile, `QSurfaceFormat` (profile, version, depth/stencil/samples), device-pixel ratio, default FBO size, selected renderer backend. Compact `key=value` or single-line JSON.
- **D-05:** That line doubles as the smoke check's oracle — CI greps it to confirm a real GL context was created (catches the "renders blank because no context" class of bug, like the Phase 2 detached-window and HiDPI regressions).

### CI dependency provisioning
- **D-06:** Provision deps via **native package managers + caching**: macOS uses Homebrew (`qt@5 boost eigen fftw tbb glew open-babel lp_solve libsvm flex bison`) with brew caching; Linux uses apt system packages. This makes CI test the *exact* path contributors follow in `BUILD-macos.md` — no `install-qt-action` divergence. Cache aggressively to keep build times reasonable.

### Build scope
- **D-07:** CI builds the `BALL VIEW BALLView` targets, **Release** build type, `-DBALL_PYTHON_SUPPORT=OFF -DUSE_RTFACT=OFF` — matching the Phase 1 `BUILD-macos.md` flow. Not the `TOOLS`/applications.

### Linux headless render-smoke
- **D-08:** The render-smoke runs on Linux too (not build-only) — under `xvfb-run` with `LIBGL_ALWAYS_SOFTWARE=1` (Mesa llvmpipe). Mesa's llvmpipe fully supports the compatibility profile, so BALLView's fixed-function GL 2.1 path renders in software. Catching cross-platform render regressions is the whole point — Linux is not reduced to build-only.

### Smoke-check input molecule
- **D-09:** The smoke check renders the **automatic startup-demo peptide** — it runs with no CLI plumbing and we have already verified it renders (Phases 2 / 02.1). It is deterministic enough (same peptide every launch). Fallback if headless export can't be wired to the demo cleanly: a fixed known PDB from `data/` — but try the demo first.

### CI trigger / branch policy
- **D-10:** CI runs on **push to `master` and `v1.6-modernization`**, and on **pull_request targeting those**. Not all branches (noise). `v1.6-modernization` is the active milestone branch; `master` is the eventual merge target.

### Matrix breadth + caching
- **D-11:** **Release-only** matrix across the 3 OSes (CI speed; Release is what the milestone goal is about). A Debug job is a deferred enhancement (see Deferred). Add **ccache** — significant CI speedup, standard practice. Structure the matrix YAML so an extra axis (e.g. the future `ui_v2` axis) can be added later without a rewrite.

### Claude's Discretion
- Exact CI cache keys, job names, matrix YAML structure, and whether to split configure/build/smoke into separate steps.
- Whether the grep-gate lint is its own job or a step in each build job.
- The exact headless-export trigger mechanism for the demo (TTL value, any `main.C` CLI flag needed) — planner/researcher works this out from `Scene::exportPNG`/`exportPNGAfterTTL`.
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `Scene::exportPNG()` + `exportPNGAfterTTL` (`scene.C`): existing offscreen PNG export — the smoke check's capture mechanism (D-01).
- `GLRenderWindow::grabFramebuffer()`: alternative frame-capture if the TTL path needs a fallback.
- `check-no-legacy-gl-symbols.sh`: ready-made grep gate, already used manually in Phases 2 / 02.1 — becomes a CI lint.
- `BUILD-macos.md`: the configure/build commands CI copies verbatim.

### Established Patterns
- Build is CMake; deps come from Homebrew on macOS (Phase 1 decision — `ball_contrib` abandoned, see PROJECT.md). Linux is system packages; Windows is vcpkg (Phase 4, not yet present — hence D-03).
- BALLView needs `BALL_DATA_PATH` / `BALLVIEW_DATA_PATH` env vars at runtime (used throughout the smoke tests this session).

### Integration Points
- New: `.github/workflows/ci.yml` (or similar).
- New: a smoke-check script (shell/python) that runs BALLView headless + asserts the exported PNG.
- Modified: a few lines in `glRenderWindow.C` / `main.C` for the `DIAG-01` startup line.

### Constraints from this session
- Phase 2 hit three "renders blank because the GL context/FBO is wrong" bugs (detached window, HiDPI viewport, paintGL never called). The `DIAG-01` line + non-blank-PNG assertion exist specifically to catch that class of regression automatically — keep that the design intent.
</code_context>

<specifics>
## Specific Ideas

- The `DIAG-01` line should record exactly the fields that would have caught the Phase 2 bugs: GL profile/version (compat 2.1 expected), default FBO size vs widget size × DPR, and the selected renderer backend.
- macOS runner is `macos-14`/`macos-15` (arm64); Linux `ubuntu-22.04` or later; Windows `windows-2022` — planner confirms current GitHub-hosted runner labels.
</specifics>

<deferred>
## Deferred Ideas

- Wiring the `test/` tree into `ctest` — explicitly Phase 9 (Test Suite Triage).
- The vcpkg manifest for Windows deps — Phase 4 (Dependency System Overhaul); D-03 is the bridge until then.
- `CMakePresets.json` — Phase 4 (DEPS-05). CI may consume it once it exists, but this phase doesn't create it.
- Screenshot/golden-image regression (pixel-diff against goldens) — richer than non-blank assertion; a later enhancement, not this phase.
- Ninja generator for CI uniformity — backlog 999.2; can fold into CI when promoted.
- A **Debug build job** (catches asserts/UB the Release matrix misses) — deferred; CI starts Release-only for speed. Add later, cheapest on the Linux runner.
- CI failure artifacts (uploading the blank PNG + stdout log on smoke-check failure) — good practice; planner may include it, but not a required decision.

None of the above was scope creep from the user — they're pre-existing roadmap boundaries noted so the planner doesn't pull them in.
</deferred>
