# Ed25519 Appcast-Signing Keypair — Procurement & Escrow Runbook

> **AGENT-DRAFTED — REQUIRES HUMAN EXECUTION**
>
> Phase 999.8-full scaffolding committed the integration code, but the
> production Ed25519 keypair MUST be generated by a human before the first
> auto-update-enabled v1.7.0 binary ships. **This is a v1.7.0 release-blocker**
> per 999.8-SPIKE.md §5 (R-appcast-key-bus-factor, HIGH severity) — once a
> public key is embedded in shipped binaries, that pubkey is committed for the
> lifetime of those installs.

## TL;DR

Generate one Ed25519 keypair. Embed the public key in:

1. **macOS `Info.plist` (`SUPublicEDKey` key)** — see `cmake/MacOSXBundleInfo.plist.in`.
2. **Windows binary (compiled in via `win_sparkle_set_dsa_pub_pem(...)`)** — see `source/APPLICATIONS/BALLVIEW/main.C` Phase 999.8-full block.
3. **GH Actions secret `AUTOUPDATE_ED25519_PUBLIC_KEY`** — gates the `publish-appcast` job.

Store the private key in:

1. **1Password org-vault** entry `BALL/Auto-Update/Ed25519-Private` (primary).
2. **GH Actions secret `AUTOUPDATE_ED25519_PRIVATE_KEY`** (runtime use).
3. **Sealed printed envelope, off-site** (bus-factor recovery, per Phase 8a `08a-SECRETS-RUNBOOK.md` pattern).

---

## 1. Generation (choose ONE path)

### Path A — Sparkle's `generate_keys` (recommended; matches macOS UX)

After running `packaging/macos/vendor-sparkle.sh`, the Sparkle release
tarball also contains `bin/generate_keys`. Procure it once:

```sh
# On a macOS workstation, in a dedicated checkout (NOT your dev tree):
cd /tmp
curl -fSL -o sparkle.tar.xz https://github.com/sparkle-project/Sparkle/releases/download/2.6.4/Sparkle-2.6.4.tar.xz
tar -xJf sparkle.tar.xz
./bin/generate_keys
```

This produces:
- A new Ed25519 keypair stored in the macOS Keychain (item name `https://sparkle-project.org`).
- A printed **base64-encoded public key** suitable for `SUPublicEDKey` in Info.plist.

Export the private key as a PEM for cross-platform / 1Password use:

```sh
./bin/generate_keys -x ed25519-private.pem
```

### Path B — `openssl` (cross-platform; matches Windows WinSparkle UX)

```sh
openssl genpkey -algorithm ED25519 -out ed25519-private.pem
openssl pkey -in ed25519-private.pem -pubout -out ed25519-public.pem
```

Convert the public key to Sparkle's base64 format (drops the PEM envelope,
keeps only the 32-byte raw key):

```sh
openssl pkey -in ed25519-private.pem -pubout -outform DER | tail -c 32 | base64
```

WinSparkle accepts the full PEM (`ed25519-public.pem`) directly via
`win_sparkle_set_dsa_pub_pem()`.

## 2. Storage — three copies, three places

| Copy | Location | Purpose | Rotated by |
|---|---|---|---|
| 1 | 1Password org-vault entry `BALL/Auto-Update/Ed25519-Private` — paste the full `ed25519-private.pem` into a Secure Note | Primary recovery copy; accessible to all designated maintainers | Org admin |
| 2 | GitHub Actions org-level secret `AUTOUPDATE_ED25519_PRIVATE_KEY` — paste the full PEM | Runtime use by `publish-appcast` job in `release.yml` | Repo admin |
| 3 | Printed PEM + QR-code rendition in a sealed envelope, stored off-site (bank safety deposit box or equivalent) | Bus-factor recovery if 1Password + GH are simultaneously inaccessible | Documented in `08a-SECRETS-RUNBOOK.md` (same envelope as Apple cert) |

**Two-human-knows recovery path:** at least two named maintainers MUST know
the location of copy #3 and have legal/practical access to it. The Phase 8a
secrets runbook already documents the names; add the Ed25519 envelope to
the same physical location.

## 3. Public-key registration

### macOS — `Info.plist` (`SUPublicEDKey`)

Edit `cmake/MacOSXBundleInfo.plist.in` and add:

```xml
<key>SUFeedURL</key>
<string>https://ball-project.github.io/ball/appcast-macos.xml</string>

<key>SUPublicEDKey</key>
<string>BASE64_FROM_GENERATE_KEYS</string>

<key>SUEnableAutomaticChecks</key>
<true/>

<key>SUScheduledCheckInterval</key>
<integer>86400</integer>

<key>SUAllowsAutomaticUpdates</key>
<false/>
```

The base64 string is what `generate_keys` prints OR what the openssl
single-liner in §1 emits.

### Windows — compiled in via `main.C`

Replace the placeholder PEM in `source/APPLICATIONS/BALLVIEW/main.C`
(Phase 999.8-full block) with the real `ed25519-public.pem` contents.
The PEM is text — paste verbatim, preserving the `-----BEGIN PUBLIC KEY-----`
and `-----END PUBLIC KEY-----` markers and the literal `\n` line breaks
inside the C string.

### GH Actions secrets

Set both at the org level (under BALL-Project organization → Settings →
Secrets and variables → Actions):

| Secret name | Value | Used by |
|---|---|---|
| `AUTOUPDATE_ED25519_PUBLIC_KEY` | base64 pubkey (single line) | `publish-appcast` job — sanity check that release.yml's embedded pubkey matches the signing key |
| `AUTOUPDATE_ED25519_PRIVATE_KEY` | Full PEM (multiline) | `publish-appcast` job — input to `sign_update` / openssl when generating `<sparkle:edSignature>` |

## 4. Verification

After registering all three pubkey copies, before the first signed tag:

```sh
# 1. Sign a dummy file with the private key
echo "smoke test" > /tmp/smoke.txt
sign_update /tmp/smoke.txt  # Sparkle tool — uses Keychain
# OR with openssl:
openssl pkeyutl -sign -inkey ed25519-private.pem -rawin -in /tmp/smoke.txt | base64

# 2. Verify the embedded pubkey can validate the signature
#    (manually decode the Info.plist SUPublicEDKey, base64-decode, write to
#    a temp DER pubkey wrapped in the SubjectPublicKeyInfo envelope, then
#    run `openssl pkeyutl -verify -pubin -inkey pub.der -rawin -in smoke.txt -sigfile sig`)
```

If verification fails, **do not tag v1.7.0**. The mismatch indicates a copy
went wrong — re-derive the pubkey from the private key and re-embed.

## 5. Rotation policy

**Don't rotate without strict need.** Rotating the Ed25519 pubkey is
**user-hostile**: installed binaries embed the old pubkey and reject all
appcast entries signed with the new private key — every existing user is
permanently stranded on the version they had at rotation time, with no
auto-update path forward (they must manually download the new version from
GitHub Releases).

**Acceptable rotation triggers:**
- Private key disclosed (e.g., leaked GH secret) — rotate immediately, ship
  a security advisory directing users to manually re-download.
- Maintainer turnover where the departing maintainer's name was on the
  envelope AND legally retains a copy — rotate to invalidate.

**Unacceptable rotation triggers:**
- "Routine hygiene." Ed25519 keys have no operational lifetime; cryptanalysis
  against Ed25519 will likely break the entire ecosystem before BALL's key
  in particular is at risk.

## 6. Dev-only key (committed)

`packaging/appcast/dev-public-key.pem` holds the placeholder dev pubkey. This
is for CI smoke-testing the publish-appcast job WITHOUT exposing the
production private key on every PR run. **The dev pubkey is NEVER embedded
in any shipped binary** — release.yml only references it on `release` job
runs where `RELEASE_TYPE=dev`.

The dev private key counterpart lives in GH Actions secret
`AUTOUPDATE_ED25519_PRIVATE_KEY_DEV` (separate from the production secret)
and may be regenerated any time without user impact.

---

## 7. Critical-path interlock

Sequence MUST be:

1. Generate keypair (§1).
2. Store private key in 3 places (§2).
3. Register public key in `Info.plist` + `main.C` + GH secrets (§3).
4. Verify (§4).
5. Tag `v1.7.0` and ship.

If steps 1–4 are not complete, the build-time check added to `release.yml`
(`AUTOUPDATE_ED25519_PUBLIC_KEY unset && RELEASE_TYPE != dev`) fails the
release job with an explicit error — preventing accidental shipment of
binaries that embed the placeholder pubkey.
