Bundle WR-02 (the misleading-log issue: the legacy-discard `Log.info()` currently fires unconditionally on `hasEntry==true`, even when the loop terminates without finding the line) by moving the log emission inside the matched-prefix branch, so it fires only when `deleteLine` actually executes. Bundle WR-01 (the off-by-one constant `BALL_VIEW_NUMBER_ELEMENTS_LOCAL = 111` that excludes atomic number 111 / Roentgenium from the diff filter) by replacing the local magic-number constant with `Element::NUMBER_OF_ELEMENTS` from `include/BALL/KERNEL/PTE.h:190` and changing the comparison from `>=` to `>`. This makes the filter inclusive of the full atomic-number range covered by the compiled defaults table (currently 1..110; future-proofed for an extension to include Rg without re-introducing the off-by-one).

Without this fix, the legacy line survives forever, the read-path log spams every launch, and any stale `ElementColorOverrides=` at the tail of the section also survives.

Output: a single-file edit to `source/VIEW/DIALOGS/coloringSettingsDialog.C` — three localized changes (two sentinel replacements, one log relocation, one filter constant change).

NOTE on `getSectionNextLine` semantics: this function ADVANCES the iterator AND RETURNS a reference to itself. So `getSectionLastLine(name).getSectionNextLine()` constructs a temporary, calls getSectionNextLine on the temporary (advancing it past the last line, making it past-the-end), and returns the advanced temporary. Capturing this into `INIFile::LineIterator end = ...;` produces a stable past-the-end sentinel — but ONLY because LineIterator's copy-constructor (preserved value) is the relevant operation, NOT a reference to the temporary. The dockingAlgorithm.C usage confirms this pattern works in practice. The executor MUST capture into a NEW `LineIterator end` variable (do not use a reference); the lifetime of the temporary `getSectionLastLine(name)` ends at the semicolon, but the value is copied into `end` first via LineIterator's copy constructor (defined at INIFile.h:451 — `IteratorTraits_(const IteratorTraits_& traits);`).

DO NOT replace the existing for-loop iteration mechanism (`++it`) with `it.getSectionNextLine()`. The existing loop bodies in `coloringSettingsDialog.C` use `++it` (lines 205, 244 post-Plan-01), which is `IteratorTraits_::operator++()` (INIFile.h:469). This advances by ONE line, not by section — within a single section iteration this is equivalent to `getSectionNextLine` until the section boundary, where `getSectionNextLine` advances past the section's last line and `++it` walks into the next section's lines. Since the new sentinel is the past-the-end of THIS section, `++it` will not overshoot before hitting the sentinel — both work, but `++it` is the established convention in the post-Plan-01 file and should be preserved. The dockingAlgorithm.C pattern uses `getSectionNextLine()` for loop advancement only because it iterates sections deeply and skips section boundaries; for a single-section scan, `++it` is correct.

So the actual textual change in this plan is ONLY the sentinel construction:
- BEFORE: `INIFile::LineIterator end = inifile.getSectionLastLine("COLORING_OPTIONS");`
- AFTER:  `INIFile::LineIterator end = inifile.getSectionLastLine("COLORING_OPTIONS").getSectionNextLine();`

The loop body (`for (; it != end; ++it) { if ((*it).hasPrefix(...)) { ... } }`) is preserved verbatim. Only the `end` initializer changes.
