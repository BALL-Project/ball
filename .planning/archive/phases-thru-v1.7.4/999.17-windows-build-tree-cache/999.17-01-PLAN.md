<interfaces>
**Today's Windows wiring (ci.yml):**
- `Cache ccache` step (lines 88-95): `actions/cache@v5`, key `ccache-windows-x64-{sha}` with restore-key `ccache-windows-x64-`.
- `Configure (Windows)` step: `cmake --preset ci-windows`. Currently 2m32s warm; rebuilds the entire `build/ci-windows/` tree because no tree-cache exists.
- `Build (Windows)`: 55s warm.

**Target shape:** a sibling cache step (`actions/cache@v5`) restoring `build/ci-windows/{CMakeCache.txt, CMakeFiles, build.ninja, vcpkg_installed}` keyed on the hash of structural inputs. On a key-hit, Configure re-uses the restored tree; on a miss, Configure runs from scratch and the new tree gets cached on the next run.

**Structural-input set (cache key inputs):**
- `CMakeLists.txt` (everything that drives the configure shape)
- `cmake/**` (preset / module definitions)
- `vcpkg.json` (Windows package manifest — vcpkg_installed/ is keyed on this)
- `CMakePresets.json` (the ci-windows preset definition)

**Cache scope (cache step `path:` value):**
- `build/ci-windows/CMakeCache.txt`
- `build/ci-windows/CMakeFiles/`
- `build/ci-windows/build.ninja`
- `build/ci-windows/vcpkg_installed/`

DO NOT cache `build/ci-windows/bin/` or build artifacts — ccache already covers per-TU compile artifacts; caching object files in the build tree would defeat the freshness check.

**Fallback if Ninja silently re-configures regardless of cache hit:** scope drops to caching `vcpkg_installed/` alone (3× simpler, vcpkg restore is the bulk of the Configure time anyway). Recorded as the "minimum viable cache" fallback in the ROADMAP entry.
</interfaces>
</context>

                build/ci-windows/CMakeFiles/
                build/ci-windows/build.ninja
                build/ci-windows/vcpkg_installed/
              key: ci-windows-cmake-tree-${{ hashFiles('CMakeLists.txt', 'cmake/**', 'vcpkg.json', 'CMakePresets.json') }}
              restore-keys: |
                ci-windows-cmake-tree-
