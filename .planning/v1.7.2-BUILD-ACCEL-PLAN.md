# v1.7.2 — Build acceleration (lead items)

**Status:** queued for the start of v1.7.2 (per maintainer direction 2026-05-21).
**Context:** `poseClustering.C` dominated the Windows release build (~57 min,
boost template metaprogramming). v1.7.1 already **quarantined** the cost into
`poseClusteringSerialization.C` (boost archives) + `poseClusteringGraphViz.C`
(write_graphviz) — pure relocation, parallelism + ccache isolation, no behavior
change (commit `5e10b27797`). v1.7.2 goes for the actual **elimination**.

## ① LEAD ITEM — hand-roll a compact cluster-tree serializer (eliminate boost::serialization)

**Why:** boost::serialization is the single heaviest Boost component to compile;
it is the bulk of the (now-isolated) `poseClusteringSerialization.C` cost. The
data it serializes is trivial, so a hand-rolled format removes the dependency
and drops that TU's compile from tens of minutes to ~seconds.

**Scope (in `poseClusteringSerialization.C`):**
- Replace `boost::archive::{binary,text}_{i,o}archive` + `adj_list_serialize.hpp`
  + `ClusterProperties::serialize` with a hand-rolled reader/writer.
- **Keep the public API unchanged:** `serializeWardClusterTree(std::ostream&, bool binary)`
  / `deserializeWardClusterTree(std::istream&, bool binary)` signatures stay; the
  `bool binary` flag still selects a binary vs text variant of the NEW format.
- **What to serialize** (matches today's payload exactly — `center` variant is
  already NOT serialized):
  - graph order (vertex count) + the root vertex index (`cluster_tree_[boost::graph_bundle]`)
  - per vertex: `std::set<Index> poses`, `Size size`, `float merged_at`
  - the edge list (each `parent -> child`), to rebuild the directed tree
  - rebuild via `add_vertex` / `add_edge` in `deserialize`, then set the graph-bundle root
- Prepend a magic + format-version header (e.g. `"BALLWARD\x01"`) so a wrong/old
  file fails loudly instead of mis-parsing.

**Format break — required follow-through:**
- Old boost-serialized `.ward`/`.dat` trees will NOT load. This is acceptable
  (niche docking research format; `DockPoseClustering` + `ExtractClustersFromWardTree`
  rebuild together). Note it in `RELEASE-NOTES` v1.7.2 "Breaking changes".
- **Regenerate the committed fixture `test/data/PoseClustering_wardtree.dat`**:
  `test/PoseClustering_test3.C:360/366` reads it and asserts 6 clusters / specific
  scores. Regenerate it deterministically from the existing test inputs
  (`PoseClustering_test*.dcd/.pdb/.txt`) serialized with the NEW format, so the
  read-back assertions (`extractClustersForThreshold(0.5)` → 6 clusters) still hold.

**Callers to keep working (rebuild together, new format):**
- `source/APPLICATIONS/TOOLS/DockPoseClustering.C` (writes the tree)
- `source/APPLICATIONS/TOOLS/ExtractClustersFromWardTree.C:94` (reads it)

**Validation:** `PoseClustering_test3` (round-trip 290–449 + fixture read 359) +
`PoseClustering_test1` (graphviz) pass; `poseClusteringSerialization.C` compiles
in seconds; the boost::serialization includes are gone from the tree.

**Effort:** ~40–80 LOC + fixture regen. Low-medium. Risk: format break (handled
above). This is the real Windows-build-time killer.

## ② release.yml ccache reuse

`release.yml` installs ccache but does NOT restore/save a ccache build cache
(only the vcpkg cache). So every tag builds cold. Add `actions/cache` for the
ccache dir (key aligned with `ci.yml` where possible) so a release tag of an
already-CI-built commit hits cache — unchanged TUs (incl. the heavy ones)
become near-instant. Biggest win for *repeat* releases.

## ③ (fallback) de-optimize the pathological TU on MSVC

If anything heavy remains after ①, `set_source_files_properties(... COMPILE_OPTIONS "/O1")`
for the specific slow TU on MSVC. Largely moot once ① lands.
