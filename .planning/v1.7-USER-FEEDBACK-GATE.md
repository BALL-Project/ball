# v1.7-USER-FEEDBACK-GATE.md

**Status:** OPEN — gates v1.7.0 final tag.
**Captured:** 2026-05-18 (during v1.7.0-rc1 packaging-iteration cycle).
**Owner:** orchestrator + user.

---

## Why this gate exists

v1.7 is the BALLView Refresh: a comprehensive UI rewrite (9 Wave 4 phases,
~76 source files touched by the BALL_UI_V2 flag-removal pass, 4 shared
widgets + Unified Inspector + Workspace + CommandPalette + WelcomeScreen
+ Classic-dock retirement). Per-phase CI matrices validated each phase
in isolation; the pre-RC adversarial review caught 8 CRITICAL security
findings + 8 IMPORTANT correctness ones (all fixed pre-tag).

But **no end-to-end user validation has happened yet.** Automated CI is
blind to:
- Icon completeness (does every toolbar/menu/dialog action have a glyph?)
- Visual rendering correctness on real displays (macOS Retina, mixed-DPR,
  HiDPI scaling — `tabOrder_test` runs offscreen)
- Cross-Inspector live-commit reactivity (does changing a Representation
  setting actually update the rendered scene?)

This gate is the explicit "ship-stops-until-human-validates" checkpoint
between **v1.7.0-rc1** (packaging green, artifacts produced) and
**v1.7.0** (final tag, master fast-forward, public release).

## Trigger conditions

The gate **opens** when:
- ✅ v1.7.0-rc1 tag exists
- ✅ release.yml produced all 4 platform artifacts (DMG + Linux × 3 +
  Windows NSIS + ZIP)
- 🟡 Artifacts are downloadable from the GitHub Actions run

The gate **closes** (and v1.7.0 final tag is unblocked) when:
- The 3 captured issues below are either:
  - (a) Fixed, with fix commits + a new RC re-roll showing the issue
    resolved, OR
  - (b) Explicitly accepted as v1.7.0-known-issues and deferred to
    v1.7.x patch cycle, with the user's written acceptance
- Any additional issues surfaced during user validation are similarly
  resolved or accepted
- User issues a "ship v1.7.0" signal to the orchestrator

### UFG-01 — Toolbar icons incomplete
**Severity:** ⚠ IMPORTANT (visible polish gap; not a functional regression)
**Status:** ✅ FIXED for rc2 — commit `c4bbc511f2` (`fix(ufg-01/icons)`).
**Symptom:** Some toolbar actions lack glyphs after the Phase 999.42 XPM → SVG migration.
**Confirmed root cause:** the dialogs that contribute toolbar entries (`MolecularFileDialog`, `DownloadPDBFile`, `DownloadElectronDensity`, `PubChemDialog`, `DisplayProperties`, `MolecularStructure`) called `ModularWidget::setIcon(action, "<key>", /*toMainToolbar*/true)` with 10 keys that had never been registered as aliases in `theme.qrc`. The `Icons::get` façade returned a null QIcon and the toolbar painted an empty cell. The Phase 999.42 migration map enumerated the keys it knew about but missed the keys originating from these dialog classes (the legacy XPM array names didn't match the new `actions/*` naming convention).
**Fix landed:** vendored 10 additional Lucide v0.460.0 SVGs + registered alias mappings in `theme.qrc`:
- `actions/document-open` → folder-open.svg (alias of existing)
- `actions/download-pdb` → download.svg
- `actions/download-electrondensity` → cloud-download.svg
- `actions/download-pubchem` → flask-conical.svg
- `categories/preferences-display` → monitor.svg
- `actions/object-focus` → focus.svg
- `actions/mode-edit` → pencil.svg
- `actions/molecule-set-element` → tag.svg
- `actions/create-bond` → link.svg
- `actions/continuous-loop` → repeat.svg
- `actions/screenshot` → camera.svg

`source/APPLICATIONS/BALLVIEW/iconBrowser.C` kept in sync. Outstanding: `mimetype/text-x-povray` (POV export — menu-only, `add_to_main_toolbar=false`, not toolbar-visible). Documented as a TODO comment in `theme.qrc`.

### UFG-02 — Rendering issues in macOS interface
**Severity:** 🚨 CRITICAL (potential RC1 blocker)
**Symptom:** Rendering glitches in the BALLView macOS UI (specifics from user TBD — could be widget chrome, GL canvas border, dock decoration, Inspector animation).
**Likely root cause candidates:**

- Phase 999.42 palette-removal sweep removed `<palette>` blocks from .ui files where the palette WAS doing useful work on macOS specifically
- Phase 999.44 InspectorSection `QPropertyAnimation` 160ms OutCubic on `maximumHeight` may cause flicker on Retina (was flagged as IMPORTANT I-4 in adversarial review but deferred)
- Phase 999.45 WorkspaceManager's `restoreState()` may interact badly with the QOpenGLWidget scene container under macOS-specific dock-layout behavior
**Investigation surface:**
- User needs to capture screenshots / video of the specific glitches
- macOS-specific overrides in QSS (`*[platform="macos"]` selectors if any)
- `source/VIEW/KERNEL/theme/theme-neutral.qss`
- Phase 999.42 SEMANTIC-COLOR-AUDIT.md
**Triage:** without specific glitch description, can't bound fix scope. **Need user to elaborate.**

### UFG-04 — Inspector tab labels truncated

**Severity:** ⚠ IMPORTANT (visible polish gap; affects UX of the new
Unified Inspector — the headline v1.7 feature)
**Status:** ✅ FIXED for rc2 — commit `6bf15f0bd0` (`fix(ufg-04/inspector-tabs)`).
**Reported:** 2026-05-18, from the same v1.7.0-rc1 screenshot triage.
**Symptom:** The InspectorTabs strip at the top of the right-rail
Inspector dock rendered as `Sele... / Represent... / Sc...` instead of
the full `Selection / Representation / Scene` labels.
**Confirmed root cause:** `InspectorTabs` constructor called
`setExpanding(true)` + `setUsesScrollButtons(false)`. The QDockWidget's
default minimum width is ~180 px (no explicit `setMinimumWidth`); under
that combination Qt's `QTabBar` distributes the available width equally
across the 3 tabs and elides each label individually when its share is
narrower than the label's natural width. Not macOS-specific — the same
elide path fires on every platform when the dock is too narrow.
**Fix landed:** two-part:
- `inspectorTabs.C` — `setExpanding(false)` + `setElideMode(Qt::ElideNone)`
  + `setUsesScrollButtons(true)` as fallback for user-narrowed dock
- `inspectorDock.C` — `setMinimumWidth(280)` to fit the full tab strip at
  the default font on macOS / Ubuntu / Windows

### UFG-05 — Inspector REPRESENTATION header garbled overlap

**Severity:** 🚨 IMPORTANT (visible polish defect; potential blocker depending
on user severity perception)
**Status:** ✅ FIXED for rc2 — commit `1b4a8dd299` (`fix(ufg-05/header-overlap)`).
**Reported:** 2026-05-18, from the same v1.7.0-rc1 screenshot triage.
**Symptom:** The Inspector's `REPRESENTATION` section header showed
overlapping text bleeding through it from the section's content area
("OPENG/SACCOUTH" fragments visible in the bug screenshot — clearly
fragments of "OpenGL" + "Saccharide", both strings produced by
`Representation::getProperties()` and rendered into the
`RepHeaderSection` QLabel below the header).
**Confirmed root cause:** `SectionHeader` was a plain `QWidget` with no
background set. Qt's default for a QWidget is transparent paint — the
chevron, the QLabel, and the QFrame::HLine each paint themselves, but
the gaps between them pass through to whatever the parent painted. The
Inspector's expand/collapse uses a `QPropertyAnimation` on the content
widget's `maximumHeight`; as sibling sections shift through the header's
parent region during the animation, fragments of `QComboBox` options +
`QLabel` text from `RepHeaderSection` get left behind in the un-cleared
header rect.
**Fix landed (safe-bet per planning guidance):**
- `SectionHeader` constructor sets `Qt::WA_OpaquePaintEvent` +
  `setAutoFillBackground(true)`
- New `paintEvent` override calls `painter.fillRect(event->rect(),
  palette().color(QPalette::Window))` before the layout's child widgets
  paint themselves on top

### UFG-07 — Selection UX redesign: highlight, not checkbox

**Severity:** ⚠ DESIGN-CHANGE (user-requested UX modernization, not a bug)
**Reported:** 2026-05-18, after initial screenshot triage.
**Symptom (current):** Left-hand `ProjectDock › Structures` tree (MolecularControl) shows `Name [highlight]` + `Type` columns, with a third "Checked" column rendering the selection checkbox. Selection state is conveyed by checkbox tick.
**Requested change:**
- Drop the `Checked` selection-checkbox column entirely
- Drop the `Type` column entirely
- Convey selection state via name-text **color highlight** instead (selected = highlight color; unselected = normal)
- Tree becomes single-column: just the Name
**Likely investigation surface:**
- `source/VIEW/WIDGETS/molecularControl.{h,C}` — tree model + columns + selection
- `source/VIEW/WIDGETS/geometricControl.{h,C}` — sister tree (Representations); may need analogous redesign for consistency
- `source/VIEW/WIDGETS/datasetControl.{h,C}` — third sister tree (Datasets); same consideration
- The QStandardItemModel / QAbstractItemModel column count drops from 3→1
- The QStyledItemDelegate paints selection via a custom foreground role
- Existing checkbox-based selection signals re-routed to a click-to-toggle on the row
**Triage:** medium scope (~150-300 LOC). Touches the selection-bus that the new Inspector subscribes to via Phase 999.44's `SelectionInspectorAdapter` — verify the adapter survives the column-count change. Likely no Controller-extraction interaction. Cross-platform safe (no macOS-specific bits).
**Disposition:** queue for RC2 fix wave per "keep everything in v1.7" directive.

### UFG-06 — Bottom Logs drawer doesn't expand

**Severity:** 🚨 CRITICAL (functional regression — visible chrome that does nothing on click)
**Reported:** 2026-05-18, follow-up to initial screenshot triage.
**Symptom:** Clicking the collapsed `Logs ▾` strip at the bottom of the window does not expand the drawer to its 240px state. Drawer stays at the 24px collapsed strip.
**Likely root cause candidates:**
- Phase 999.45 `BottomDrawer` (`source/VIEW/WIDGETS/bottomDrawer.C`) — the toggle slot may not be wired to the strip's mousePressEvent, OR the QPropertyAnimation on the drawer's `maximumHeight` may be stuck at 24px
- `mainframe.C` may not have called `addDockWidget(Qt::BottomDockWidgetArea, bottomDrawer_)` with `setAllowedAreas`/`setFeatures` such that the toggle actually animates instead of trying to re-dock
- The `Logs` tab inside the BottomDrawer needs the LogView widget to be reparented under the drawer's tabbed area — if not, even when expanded the drawer is empty
**Investigation surface:**
- `source/VIEW/WIDGETS/bottomDrawer.{h,C}` — toggle slot + animation
- `source/APPLICATIONS/BALLVIEW/mainframe.C` — BottomDrawer wiring lines (search "BottomDrawer" or "bottomDrawer_")
- `source/VIEW/WIDGETS/logView.C` if LogView is involved in tab population
**Triage:** small-scope fix candidate. Either a missing signal-slot connect, a wrong `maximumHeight` target value, or a missing `setExpanded(true)` call. Should be a one-commit fix once the broken wire is identified.

### UFG-03 — Representations + colorings no longer update
**Severity:** 🚨 CRITICAL (functional regression — RC1 blocker)
**Symptom:** Changing Representation settings (model, coloring, material) in the new Unified Inspector doesn't propagate to the rendered scene.
**Likely root cause:** Phase 999.44 Controller extraction refactor (sub-PR 4.5). The Inspector sections bind to Controllers (`StageController`, plus the 5 Representation Controllers landed in Plan 999.44-04). Controllers are supposed to apply changes via the same code path as the legacy dialogs did — but the apply() cut-over in commit `062d3fc901` (999.44-06) only fully migrated StageController; the Representation Controllers may still be stubs forwarding to a no-op.
**Investigation surface:**
- `source/VIEW/KERNEL/controllers/PATTERN.md` — Controller cut-over status table
- `source/VIEW/KERNEL/controllers/{model,coloring,material,...}Controller.C` — check if `apply()` actually invokes the underlying VIEW Scene::update path
- 999.44-01 SUMMARY.md "Deferred to v1.7 RC patch cycle" section — Plans 999.44-04..04h enumerate the 8 deferred Controller cut-overs (~3072 LOC)
- This is the **same dependency cluster** that blocks the 9-file legacy dialog deletion (per RC-PATCH agent's diagnosis: `displayProperties.C:451+487` `createModelProcessor`/`createColorProcessor` factories are still on the production rendering path)
**Triage:** **this is the deferred-to-v1.7.x cluster manifesting as a v1.7.0-blocker.** Either:
- (a) Land the 8 Controller cut-over plans NOW (~3072 LOC, requires re-opening the v1.7.x patch cycle scope into pre-RC2)
- (b) Ship v1.7.0 with the Inspector visible-but-non-functional for Representation/Coloring sections, with a clear "set via Tools › Legacy Settings" workaround in RELEASE-NOTES (degrades UX significantly)
- (c) Hide the broken Inspector sections at runtime (display "Migration in progress — use Tools › Legacy Settings"), defer functional implementation to v1.7.x

## Gate-closure workflow

1. **User downloads** v1.7.0-rc1 artifacts:
   - macOS: `BALLView-v1.7.0-rc1-macos-arm64.dmg`
   - Linux x64: `BALLView-v1.7.0-rc1-linux-x64.tar.gz` (or AppImage / DEB / RPM)
   - Linux arm64: `BALLView-v1.7.0-rc1-linux-arm64.tar.gz` (or AppImage / DEB / RPM)
   - Windows: `BALLView-v1.7.0-rc1-windows-x64.zip` (or NSIS installer, when ready)
2. User exercises the UI across the 4 platforms (or as many as they can):
   - Load a sample molecule (`File › Open from PDB` → `1ubq` is the
     curated default per Phase 999.47)
   - Walk through every menu item, every toolbar button
   - Open the Unified Inspector, exercise all 3 tabs and visible sections
   - Switch workspaces (Default ↔ Focused)
   - Open the CommandPalette (Cmd/Ctrl+K), try `?` / `>` / `:` modes
   - Apply theme tints (state tints visible on hover/select)
3. User triages findings into:
   - **Blocker for v1.7.0:** fix-first list (added here as UFG-NN, fixes
     re-roll RC)
   - **Accept for v1.7.0:** added to RELEASE-NOTES "Known issues" + tracked
     for v1.7.x patch cycle
4. Orchestrator dispatches fix agents for the blocker list; re-rolls
   RC for each fix wave
5. Final user "ship it" signal → orchestrator promotes v1.7.0-rc1 →
   v1.7.0 tag → release.yml → master fast-forward

## What to NOT do during this gate

- Don't auto-tag v1.7.0 even if all CI is green — wait for explicit user
  ship signal
- Don't auto-promote any RC roll without user re-validation of the issues
  they captured
- Don't merge to master — RC tags are mutable; final tag triggers the
  master fast-forward per RELEASE-PROCESS.md
