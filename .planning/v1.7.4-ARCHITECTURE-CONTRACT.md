## 0. The regression class we are closing

Every "works here, not there" UFG bug in the v1.7.0 RC cycle traced to
the **same structural shape**:

> Operation X has implementation A (legacy) and implementation B (new
> UI). The redesign touched B but A stayed, or B was a hollow mirror
> of A. Whichever path a given test exercised determined whether it
> "worked."

The v1.7.4 contract eliminates the shape by enforcing **one mutation
funnel per state domain**, with re-entrancy, ordering, and reversal as
part of the funnel's contract — not afterthoughts.

**Exactly 9 controllers**, all `QObject`s under
`source/VIEW/KERNEL/controllers/`:
`ModelController` · `ColoringController` · `MaterialController` ·
`ClippingController` · `LabelController` · `StageController` ·
`CameraController` · `LightController` · `StereoController`.

Ground-truth note (2026-05-22 audit): **7 of the 9 already mutate** their
owner (Camera/Stereo/Light/Model/Coloring/Material were cut over during

work is therefore **harmonizing the divergent mutating `apply()`s onto

read-only mirrors. Any "8 controllers" count anywhere in the milestone
docs is a stale error: it is always 9.

Six rules, all enforced. The next sections define them.

## 2. The `apply()` contract — every Controller must satisfy

`apply()` returns **`bool`**: `true` when it mutated the owner, `false`
when it was dropped (re-entry) or rejected (precondition / validation
failure). The bool is the diagnostic the `999.60` re-entrancy test
asserts on, and the signal an Inspector section uses to decide whether
to resync. There is no `void`-returning variant — the whole contract is
`bool` everywhere.

```cpp
bool XController::apply()
{
  // ── 1. Preconditions ──────────────────────────────────────────────
  // Verify required state exists. Fail-fast on missing rep / scene.
  if (!representation_) return false;
  if (!isInValidRange_(payload_pending_)) {
    Log.error() << "XController: invalid value, rejected." << std::endl;
    return false;                      // rejected — not mutated
  }

  // ── 2. Re-entrancy guard ──────────────────────────────────────────
  // Ignore any notification we trigger below until we leave this scope.
  // apply() runs ONLY on the GUI thread (thread-safety note below), so
  // the guard is a nest-aware GUI-thread flag, not a mutex.
  if (applying_) return false;         // dropped — caller re-entered
  ControllerApplyGuard guard(applying_);

  // ── 3. Capture for reversibility (v2.0 undo will consume) ─────────
  ApplyPayload payload {
    .command_id = "x.setFoo",
    .before     = snapshotState_(),
    .after      = pending_,
    .target     = representation_,
    .t_us       = SystemClock::nowMicroseconds(),
  };

  // ── 4. Mutate the SINGLE owner ────────────────────────────────────
  // Owner-side mutation now goes through the friend-scoped surface (§3).
  representation_->setFromController_(pending_);
  current_ = pending_;

  // ── 5. Emit ONE typed event ───────────────────────────────────────
  emit appliedEvent(payload);

  // ── 6. Request the controller's DECLARED invalidation ─────────────
  // Each controller declares its own invalidation level (§2a). Most
  // request a SOFT refresh (no display-list rebuild). Model/Stage
  // declare heavier invalidation because a model-processor swap or a
  // renderer switch genuinely requires it. NEVER a blanket full-scene
  // rebuild "to be safe": that is the v1.7.x-13 freeze.
  invalidateDeclared_();               // §2a — per-domain, documented

  // ── 7. Record reversible intent ───────────────────────────────────
  // v1.7.4: capture only; do not push to a stack (no stack yet).
  // v2.0: pushed onto UndoStack here.
  recordIntent_(payload);

  return true;                         // mutated
  // guard destructor releases the re-entrancy block on scope exit
}
```

**Sub-rules:**

- `apply()` is **synchronous**. No `QTimer::singleShot(0, ...)` inside.
  Async cost goes in a separate `ControllerJob` (see §6) — not in `apply()`.
- `apply()` returns `bool` (`true` = mutated, `false` = dropped/rejected).
  Hard errors still raise `BALL::Exception`; soft rejections log + return `false`.
- `apply()` is **idempotent over the same payload** — apply(X); apply(X) leaves the owner in the same state, fires the event twice (which the bus must dedupe at the consumer end). Both calls return `true` (each mutated, even if to the same value).
- Re-entrancy guard is `ControllerApplyGuard` from
  `include/BALL/VIEW/KERNEL/controllers/controllerApplyGuard.h` (already
  in-tree; upgraded to nest-aware in `999.59-01`). It is **required in
  every `apply()`, including `ClippingController::apply()`** — which
  currently omits it (see §4 thread-safety note).
- `apply()` MUST request its **declared invalidation** (§2a) — not a
  hard-coded `update(false)`. Soft refresh is the common case; the two
  controllers that need more declare it explicitly.

### 2a. Per-domain invalidation — there is no single rule

The v1.7.x-13 freeze came from over-invalidating (full rebuild from
`apply()`); a naive "always `update(false)`" rule over-corrects in the
other direction and leaves stale geometry for controllers whose mutation
genuinely changes what the model-builder emits. **Each controller
declares its own invalidation level as part of its contract:**

| Controller | Declared invalidation | Why |
|------------|-----------------------|-----|
| Coloring / Material / Label / Camera / Light / Stereo / Clipping | `representation_->update(false)` — soft refresh, no display-list rebuild | Color / material / transform / clip-plane changes do not change the primitive set; a soft refresh re-draws existing geometry. |
| **Model** | `representation_->update(true)` — display-list **rebuild** | A model-processor swap (e.g. Stick → Surface) changes the primitives themselves; a soft refresh would re-draw stale geometry. `ModelController::apply()` correctly rebuilds today; the contract codifies it. |
| **Stage** | controller-declared side effects: rep-delete on vertex-buffer-mode toggle + renderer switch, then `mc->redrawAllRepresentations()` | A vertex-buffer-mode toggle or renderer switch is a scene-wide structural change. These side effects are documented as `StageController`'s declared invalidation, not smuggled in under a generic rule. |

The mechanism is a per-controller `invalidateDeclared_()` override (or an
`InvalidationLevel` enum the base reads). A controller that needs a
rebuild says so in one place; reviewers and the `999.60` tests check that
the declared level matches the domain. "Always `false`" and "always
`true`" are both contract violations.

**Anti-patterns banned in v1.7.4:**

- Direct `stage_->setX()` / `rep_->setX()` from any non-Controller TU
  (except the documented `RepresentationBuilder` / file-IO friends, §3).
- Multiple events fired from one `apply()` ("I changed X and also Y").  If two domains change, two Controllers run sequentially.
- Setters that mutate AND notify — owner setters must be pure mutations.
- A blanket invalidation rule that ignores the domain (§2a).

## 3. Owner-API narrowing — the structural enforcement

Discipline rots. The contract above survives ONLY if the owner API makes
bypass a compile error. **This is the largest single piece of v1.7.4
work and the Codex review's #3 finding: the fallout was underestimated.**
A grep of the current tree finds **~47 direct owner-setter call sites
across 13 non-controller files** — far more than the "≤8 file-IO sites"
the first draft of this contract claimed. The narrowing is real work and
is staged across `999.59-03 .. 999.59-05` (see those plans). The honest
inventory:

### 3b. Stage — `StageMutation` owner-side facade, not a friend pile

`Stage` is mutated by **five domains** — background, fog, camera, lights,
stereo. Granting `friend class CameraController; friend class
StereoController; friend class LightController; friend class
StageController;` makes the setters "private but not narrow" (Codex
MEDIUM): four friends is not narrowing. Instead, `Stage` exposes a single
owner-side mutation facade:

```cpp
class Stage {
 public:
  const ColorRGBA& getBackgroundColor() const;     // pure reads stay public
  const Camera&    getCamera() const;
  // ... getters ...

 private:
  // The ONE mutation surface. Controllers obtain a StageMutation token
  // from the owner; only StageMutation can call the private setters.
  void setBackgroundColor_(const ColorRGBA&);
  void setCamera_(const Camera&);
  void setEyeDistance_(float);
  void setFocalDistance_(float);
  void setFogIntensity_(float);
  friend class StageMutation;          // the SINGLE friend
};

// Owner-side builder/facade. Controllers mutate Stage only by holding
// one of these. One friend on Stage, not five. Each Controller takes a
// StageMutation in its apply() and calls the typed mutators.
class StageMutation {
 public:
  explicit StageMutation(Stage& s) : stage_(s) {}
  StageMutation& backgroundColor(const ColorRGBA& c);
  StageMutation& camera(const Camera& c);
  StageMutation& eyeDistance(float v);
  StageMutation& focalDistance(float v);
  StageMutation& fogIntensity(float v);
 private:
  Stage& stage_;
};
```

Note `setCamera`/`setBackgroundColor` are currently `virtual` on `Stage`;
the cut-over keeps them virtual on the private surface (subclass override
points are preserved) — `999.59-04` handles the MSVC strict-`friend`
lookup for the facade.

### 3c. Representation — `RepresentationBuilder` friend

Same shape, simpler: `Representation::setX()` move to a private
`setX_()`, and a single `RepresentationBuilder` friend class is the legal
mutation surface for the **builder/file-IO** call sites in §3a. Loaders
(`MolecularFileDialog::openMolecularFile()`, `PDBFile::read()`) and the
dataset/surface builders populate Representations through
`RepresentationBuilder`, not direct setters. Documented per-friend in
`999.59-04-PLAN.md`. `Composite::setSelection` is already routed through
`MainControl::setSelection_`; v1.7.4 narrows the residual public surface.

### 3d. Python — bindings shimmed + regenerated IN v1.7.4 (not deferred)

**Codex HIGH #4: privatizing the owner setters breaks PyBALL unless the
bindings move in the same release.** This is resolved by bringing the
binding work INTO v1.7.4 (`999.59-06`), not deferring it to v2.1:

- `source/PYTHON/EXTENSIONS/VIEW/representation.sip` today exposes
  `setTransparency`, `setDrawingMode`, `setColoringMethod`,
  `setModelType`, etc. — exactly the setters being narrowed. These are
  **removed** from the `.sip` (they no longer exist on the public C++
  surface) and replaced by new controller bindings.
- New `source/PYTHON/EXTENSIONS/VIEW/controllers.sip` exposes the 9
  Controllers' public surface: `mainControl.coloringController()
  .setMethod("Element"); ...apply()`. Bindings see Controllers, never
  owners — enforced because the owner setters are now private.
- A **one-release deprecation shim**: the legacy
  `representation.coloring_method = "Element"` Python attribute survives
  in v1.7.4 with a `DeprecationWarning` that prints the
  controller-surface replacement, then is removed in v1.8. The shim is a
  thin `.sip` `%MethodCode` that forwards to the controller.
- **CI:** the SIP bindings are currently disabled in the modernization
  build (CLAUDE.md: "Removed/disabled: SIP Python bindings"). v1.7.4
  re-enables a **SIP-refresh build-check job** that regenerates the
  bindings and compiles them, so a future setter rename can't silently
  rot the Python surface again. Deep PyBALL test-coverage stays v2.1; the
  build-check is the v1.7.4 floor.

This keeps the contract's "bindings expose Controllers, not owners"
promise *enforceable in v1.7.4* instead of aspirational.

## 4. The notification bus — one event per apply, typed

`ConnectionObject` stays in v1.7.4 (replacement is v2.0). The contract:

- Every `Controller::apply()` emits **exactly one** typed event:
  `CompositeMessage` · `SceneMessage` · `RepresentationMessage` · `SelectionMessage` · `ColoringMessage` (the typed list lives in `KERNEL/message.h` and is extended per phase).
- The bus broadcasts to all leaves **except the sender**.
- A consumer that receives an event MUST react by **re-reading from the owner**, never by trusting the message payload to be authoritative.

> **Why "re-read."** The message can be batched, dropped, or re-emitted by a guard. Treating it as a notification ("something in domain X changed; go look") is robust; treating it as a state delivery ("here is the new value") is the dual-path defect in miniature.

`v1.7.x-14` was exactly the dual-meaning-of-message defect:
`setSelection_` iterated every tree row and `setData()` unconditionally because the message's "what changed" payload was incomplete.

### Re-entry through the bus — and the thread-safety scope

The bus can synchronously re-enter the Controller that triggered the
event. The `ControllerApplyGuard` is the only thing protecting against
this. The Controller is allowed to ignore — silently — any incoming
notification while its own `apply()` is in flight; this is intentional.

**Thread-safety scope (Codex HIGH #6).** `apply()` and the bus
re-entry it guards against are **GUI-thread-only**. The guard is
therefore a **nest-aware flag, not a mutex** — thread-safety is
explicitly *not required* and the guard does not pay for it. (Async work
runs in a `ControllerJob` on a worker thread and re-enters the GUI thread
via `QMetaObject::invokeMethod` to a queued slot that itself runs the §2
`apply()` contract — so even the async path takes the guard on the GUI
thread, §6.) The first draft over-specified the guard as "thread-safe";
the contract corrects that to "nest-aware, GUI-thread-only".

The current in-tree `controllerApplyGuard.h` is a plain RAII `bool&`
flag — correct for single-level re-entry but not nest-aware.
`999.59-01` upgrades it to a small depth counter so a controller that
legitimately calls a helper that re-enters `apply()` at a deeper level
behaves predictably, and so `ClippingController::apply()` (which omits
the guard entirely today) gains it.

**Diagnostic.** If a controller drops an incoming event, it logs at
`Log.info()` once per `apply()` cycle. `999.60` contract tests assert
the drop count == 0 on the contract-conforming Controllers in steady
state, and assert `apply()` returns `false` on the dropped re-entry.

## 5. View = pure presentation

> Widgets render source-of-truth + emit user intent. **No business logic
> in widgets.**

Concretely:

- An Inspector section's debounced "apply" calls `controller_->setX(v)` and `controller_->apply()`. The section does not validate, does not compute "should we?", does not branch on representation type.
- A toolbar `QAction`'s slot calls the **registered command body** (§8) which builds a payload and calls `apply()`. The slot has no algorithm. **UFG-15 banned.**
- The legacy dialog (during its sunset) also delegates to the Controller. The dialog's own "Apply" button calls the same `controller_->apply()` an Inspector section would. Identical code path → identical postcondition.

If a widget needs to *display* derived state (e.g. "show histogram of B-factor values across the current selection"), the derivation is **owned by the Controller** (`ColoringController::distribution()`) and the widget calls it. Never let the widget walk the molecular hierarchy.

> **Render-only hints are NOT mutations.** A live drag-preview (e.g. the
> histogram handle drag in `999.63`) that paints a transient visual hint
> WITHOUT changing the owner is allowed, but it is a *render-only* path
> (`ColoringController::previewRange()`), explicitly **non-owner**: it
> creates no `ApplyPayload`, emits no typed event, and is forbidden from
> calling any owner setter. It is a second *render* path, never a second
> *mutation* path. `999.60` includes a test asserting `previewRange()`
> mutates nothing. Commit happens only on release through `apply()`.

## 6. Async work — `ControllerJob` (minimal v1.7.4 scaffold)

Some operations are expensive (energy minimization, FDPB, MD step). They
can't run inside `apply()` — the GUI thread would lock.

**Scope note (Codex LOW #13): `ControllerJob` is kept at full scope but
deliberately minimal in v1.7.4.** It is the async-base scaffold the
contract's thread-safety model (§4) references: the reason `apply()` can
declare itself GUI-thread-only is precisely that long work is shunted to
`ControllerJob` and re-enters the GUI thread through a queued slot. No
v1.7.4 Controller *ships* a long job, so v1.7.4 lands only the base class
+ the queued-result plumbing (no concrete job, no new UI). It justifies
its place by closing the thread-safety story, not by delivering a
feature. The first concrete consumer (minimization Controller) is v2.0.

The contract:

- Long operations are modeled as a `ControllerJob` — a small `QObject` with `started` / `progress(int pct)` / `finished(ApplyPayload)` signals.
- The Controller's `apply()` *kicks* the job (assigns to the `Jobs` drawer-tab queue) and returns `false` (nothing mutated synchronously). The owner is not mutated yet.
- When the job finishes on its worker thread, it `QMetaObject::invokeMethod`-queues an internal `applyResult_(payload)` slot on the Controller. That slot runs through the §2 contract — guard / mutate / emit / invalidate — on the GUI thread.

This is **already the shape** for raytracer renderings and energy minimization in BALL. v1.7.4 codifies the base. Minimal `ControllerJob` base in `999.59-05`.

## 7. Selection — one source, four consumers, contract-tested

`Composite::isSelected()` is the source of truth. Consumers (`MolecularControl` tree, `Scene` picker, `MainControl::getSelection()`, action enable-gates) MUST agree.

`999.60` ships the **selection-consumer agreement test**:

```cpp
TEST(SelectionContract, four_consumers_agree)
{
  loadSample("1bna.pdb");
  selectResiduesByName({"DG", "DC"});       // via MolecularControl

  auto from_tree    = tree.checkedComposites();
  auto from_scene   = scene.pickerSelected();
  auto from_control = mainControl.getSelection();
  auto from_action  = QAction("optimize").isEnabled()
                        ? mainControl.getSelection()
                        : empty();

  EXPECT_EQ(from_tree, from_scene);
  EXPECT_EQ(from_scene, from_control);
  EXPECT_EQ(from_control, from_action);
}
```

Four-way equality — fails immediately if a future refactor decouples one consumer.

## 8. CommandRegistry — explicit command-body migration

`CommandRegistry` already exists (Phase 999.46) but **today it is purely
QAction-discovery**: `registerFromAction(QAction*, category)` synthesizes
a `Command` whose `trigger` is just `action->trigger()` and whose
`isEnabled` is just `action->isEnabled()` (see
`include/BALL/VIEW/KERNEL/commandRegistry.h:110-127`). There is **no
"one implementation per command body"** today — the algorithm still lives
in each QAction's slot. Codex MEDIUM caught this: the contract's claim of
"one registered command implementation" was aspirational.

v1.7.4 does **not** turn the registry into a dispatcher (that's v2.0), but
it DOES require an explicit migration so the toolbar/menu path is
contract-testable:

What v1.7.4 DOES require (`999.60`-c, migration land in `999.59-03`):

- For every operation that has BOTH a toolbar QAction AND a menu QAction
  (the dual-surface set that the UFG-15 dual-algorithm class lives in),
  the command body is migrated from the QAction slot to a registered
  `Command::trigger` `std::function<void()>` that builds the Controller
  payload and calls `apply()`. The two QActions' slots become 1-liners
  that invoke the registered command by id.
- `registerFromAction` stays for the long tail of single-surface actions
  (no dual path → no dual-algorithm risk), but dual-surface mutating
  operations MUST use a registered body. A CI grep asserts that a
  dual-surface mutating operation has exactly **one** registered
  implementation, count > 1 fails.
- The `999.60` toolbar/menu surface helpers (`surface_toolbar`,
  `surface_menu`) invoke the **registered command body**, so the parity
  test actually exercises the migrated path — not `action->trigger()`
  indirection. This is how menu/toolbar parity becomes tested rather than
  asserted.

v2.0 then makes the registry the actual dispatcher (Python entry,
programmatic invocation, key-binding remap) — but it consumes the same
`std::function` payload v1.7.4 already requires.

## 9. Qt lifetime — the conventions doc (`999.61`)

Captured separately in `.planning/codebase/QT-LIFETIME.md`. The five conventions that apply to v1.7.4 Controller code specifically:

1. **Owner-rooted parentage.** Every Controller is parented to `MainControl` at construction. Sections (views) are parented to the Inspector tab. No raw `new` without a parent or an explicit `deleteLater` justification.
2. **`QPointer<T>` for cross-owner references.** A Controller that caches a `Representation*` uses `QPointer<Representation>` so a dtor-order race (the UFG-30 class) becomes a null check rather than a deref.
3. **Direct signal/slot connections in v1.7.4.** Queued connections are only for cross-thread (`ControllerJob`); within the GUI thread the contract is direct. Mismatched connection types caused the latent ordering bug in UFG-32.
4. **GL context ownership.** No Controller touches the GL context. If a Controller needs render-time data it goes through `Renderer::query…()`. The UFG-26 spam happened because a widget painted onto a `QOpenGLWidget` outside the paint cycle.
5. **`deleteLater()` never in dtors.** `~XSection()` does NOT call `deleteLater()` on its children; Qt does the parent walk for us. Manual `deleteLater` in dtors is the UFG-32 class.

`999.61` audits ~6 known sites and codifies the rules; a clang-tidy custom check (`ball-no-raw-deletelater`) ships as a follow-up.

## 10. Opaque-paint contract — the design system encodes it

> **Any container that hosts an animated child must be opaque.**

Source: UFG-05 / 09 / 10 — the section expand/collapse animation
(`QPropertyAnimation` on `maximumHeight`) caused transient transparent
strips that ghosted text from sibling sections.

Concretely (per `999.62`):

- `InspectorSection`, `InspectorBody`, `InspectorView`, the `QScrollArea` and its viewport, and the inner contents widget **all** carry `WA_OpaquePaintEvent` + `setAutoFillBackground(true)` + an explicit `paintEvent` that `fillRect`s the background BEFORE any child paints.
- The QSS rule that establishes the section background is centralized — a single `palette().color(QPalette::Window)` token.
- A CI lint job (`cmake/scripts/check-opaque-paint.sh`) greps for `QPropertyAnimation` and asserts every animated widget's parent chain hits `WA_OpaquePaintEvent` within 3 hops. **Rollout: warn-only first.** The lint ships as `STATUS` (warn-only) with a `cmake/scripts/opaque-paint-whitelist.txt` and synthetic positive/negative tests proving it catches a real miss and passes a real fix; it flips to `BLOCKING` only after one week of clean STATUS CI. (Codex LOW: a grep that can't be shown to catch the bug — and can't be quieted on a legitimate exception — should not gate merges on day one.)

Dark mode (v1.8) cannot land safely without this — the failure mode at higher contrast is even worse.

## 11. Contract tests — the actual enforcement (`999.60`)

Grep gates miss aliases, helpers, lambdas, macros, manager indirection, processor mutation, friends, Python, MOC, base-pointer calls. **Grep is not the contract.** Contract TESTS are.

> **Sequencing (Codex MEDIUM #7).** `999.60`'s harness + compile-fail
> infra land **FIRST**, before `999.59` cuts controllers over. The
> harness ships with the per-controller fixtures **disabled / expected-
> fail**; then `999.59` cuts controllers over one-by-one and flips each
> fixture green as its controller conforms. This breaks the
> `999.59 ↔ 999.60` circular dependency the first draft had (where
> `999.60` depended on `999.59` AND `999.59` acceptance depended on
> `999.60` tests). See the dependency note in `999.59-01-PLAN.md` and
> `999.60-01-PLAN.md`.

Three contract test classes ship in `999.60`:

### 11a. Surface-parity tests

For every state domain × surface combination, run the same operation
through every surface and assert the owner postcondition is bit-equal.

```cpp
TEST_F(ContractTest, coloring_method_change_parity)
{
  auto inspectorBefore = colorViaInspector_("Element");
  auto toolbarBefore   = colorViaToolbar_("Element");
  auto menuBefore      = colorViaMenu_("Element");
  auto pythonBefore    = colorViaPython_("Element");

  inspectorBefore.applyAndSnapshot();
  toolbarBefore  .applyAndSnapshot();
  menuBefore     .applyAndSnapshot();
  pythonBefore   .applyAndSnapshot();

  EXPECT_EQ(snapshots[0], snapshots[1]);
  EXPECT_EQ(snapshots[1], snapshots[2]);
  EXPECT_EQ(snapshots[2], snapshots[3]);
}
```

**9** Controllers × 4 surfaces × ~4 representative ops ≈ ~144 tests
(skip the Python surface when `BALL_HAS_PYBALL=OFF`, dropping to
3-surface parity). Generated, not hand-written.

### 11b. Re-entrancy tests

Force a Controller to apply while a notification it's about to fire is
already in flight. Assert the second apply is dropped (returns `false`),
not stacked. This is exactly why `apply()` returns `bool` (§2).

### 11c. Owner-narrowing compile tests

Negative test files in `test/contract/` that try to `stage_->setX()` /
`rep_->setX()` from a non-Controller TU; expect compile failure with a
diagnostic matching `... no matching public member function set...` (or
the platform-equivalent "is private" diagnostic). The
`StageMutation`/`RepresentationBuilder` friends are the only legal
mutators, so the negative test must NOT compile while a positive test
through a friend MUST.

## 12. What about the bus replacement?

Out of v1.7.4 scope. The current `ConnectionObject` tree (manual
`notify_` → root → broadcast → leaves) is pre-1.6 debt. **Replacement is
v2.0** because:

- It's a cross-cutting rewrite (~30 `ModularWidget` subclasses).
- The bus interacts with the apply contract — we want one stable
  enough to swap out wholesale.
- v1.7.4's command-shaped payloads survive the replacement: a
  Qt-signals or event-bus implementation consumes the same payload
  type the contract emits.

The v2.0 replacement is **easier** with the v1.7.4 contract in place,
not harder.

## 13. Migration cookbook (for `999.59` plan authors)

For each existing Controller, the cut-over recipe (note: 7 of 9 already
mutate — for those this is *harmonization*, not extraction):

1. **Inventory** the Controller's current `apply()` body (mutating ones diverge in guard/event/invalidation; the two stubs — Clipping/Label — need a real body).
2. **Move** the existing mutation body into a private `applyInternal_()`.
3. **Rewrite** `apply()` to be the §2 `bool` wrapper that calls `applyInternal_()` between the guard/emit/invalidate steps, declaring its §2a invalidation level.
4. **Audit** the section that binds to the Controller — ensure it calls `controller_->setX(v)` then `controller_->apply()`, never raw owner methods.
5. **Run** the (already-landed, expected-fail) `999.60` fixture for this Controller's domain; flip it to enabled and watch it go green. If not, you've found the residual bypass.
6. **Narrow** the matching owner setter to `private` + the `StageMutation`/`RepresentationBuilder` friend (`999.59-04`).
7. **Add** the reversible-payload capture (`999.59-05`).
8. **Refresh** the Python binding for any narrowed setter (`999.59-06`).

Each Controller cut-over is ~2–4 hours of work after the base class lands.
