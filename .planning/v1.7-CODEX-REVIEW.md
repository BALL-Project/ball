## Q2 — Phase 8 sizing

**Verdict: P0 — must split into 8a/8b/8c. Single-phase Phase 8 is the highest schedule risk in the plan.**

The three platforms have orthogonal risk profiles, lead times, and failure modes:

| Sub-phase | Cert lead time | Skill | Failure surface |
|---|---|---|---|
| 8a macOS | $99/yr Apple Developer (1-3 days, well-trodden) | notarytool, codesign, create-dmg, stapler | "Notarization queue rejected, opaque error" — historically painful |
| 8b Windows | SignPath Foundation OSS approval (**weeks**, manual review) | signtool, CPack NSIS, SmartScreen reputation | Cert blocked → fallback Path B (Azure $120/yr) → Path C (commercial $200-500/yr) — each is a new procurement |
| 8c Linux | None (unsigned by convention) | AppImage/.deb/.rpm packaging, FFTW-GPL split | License-compliance review (FFTW GPL path) |

**The risk register already acknowledges** "SignPath certificate provisioning is org-bureaucratic + may block Windows installer signing" with mitigation "ship macOS signed + Linux + Windows-unsigned-with-warning as fallback." But the phase structure doesn't reflect this: if Phase 8 is one phase with one PLAN.md, "8b is delayed by 6 weeks while SignPath reviews" forces 8a + 8c to wait, OR forces a mid-phase split anyway (with all the planning rework that implies).

**Recommend:** 8a (macOS, lead) → 8c (Linux, parallel with 8a) → 8b (Windows, separately gated by cert acquisition starting day-1 of Wave 1). 8b can complete asynchronously; v1.7 ships when 8a+8c are done with 8b as "unsigned Windows installer with warning" if SignPath isn't through. This matches the existing risk-register mitigation but makes it the default plan-shape rather than a contingency.

**Bonus risk missed:** macOS notarization requires Apple ID + app-specific password + ASC API key stored as GitHub secrets. Who owns the Apple Developer account? Personal vs org? Renewal cadence? Bus factor of 1 person knowing the keychain password is real. Add to risk register.

## Q5 — CI gating risk

**Verdict: P0 — Stage 1→2→3 risks a Windows-surprise closure crunch. Cheaper mitigation than full-matrix-always exists.**

v1.6.2 evidence is concrete: 5 release-pipeline iterations on Windows alone. Windows surfaces unique bugs:
- vcpkg cache invalidation (Phase 999.36 reports a `cb392cc4` cache-masking class still open)
- MSVC C4910/C4267 narrowing patterns absent on clang/gcc
- Bison `-Wformat-truncation` differs (the 19 CIFParser warnings on Linux GCC don't surface on MSVC)
- SignPath signing infrastructure has never been exercised in CI
- ccache + Ninja interaction on Windows (Phase 999.2 newly landed in v1.6.1, still single-digit weeks of production data)

Stage-3 promotion is "All Wave 1 + Wave 2 COMPLETE." That means Windows ONLY sees v1.7 work after **9 of 10 phases land.** If Phase 8b SignPath integration explodes on first Windows CI contact at Stage 3, the closure cycle becomes another 5-iteration Windows pipeline crunch — at the worst time (closure-gate buffer is "≥2 weeks," but 5 iterations × ~1 day cold-cache each = closure slip).

### Cheaper mitigation than full-matrix-always

**Recommend: "Windows weekly + on-tag" instead of "Windows-only-at-closure."**

- Add a `cron: 0 6 * * 1` (Monday 06:00 UTC) job that runs the full matrix including Windows, weekly
- Add Windows to PR runs that touch `cmake/`, `.github/workflows/`, `source/FORMAT/CIFParser*`, `include/BALL/KERNEL/atom.h`, `include/BALL/VIEW/`, or `vcpkg.json` (path-aware trigger — see Q4 P2 above)
- Stage-1 stays macOS-only for all other PR work

This costs ~5× a Windows-only run per week + selective per-PR for high-risk paths. Catches the "phase 8b SignPath integration explodes on Windows" surprise on week-1, not at closure. Cheaper than running Windows on every commit (which v1.6.1's 80-min Windows wall-clock cost would multiply by ~50 PRs across the milestone).

**Concrete actionable:** before Wave 1 dispatches, land a one-PR change to `ci.yml` that adds the weekly cron + path-aware trigger for Windows. ~2 hours of work, eliminates the headline closure-risk.
