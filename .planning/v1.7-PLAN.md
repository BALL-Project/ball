## v1.7 narrative

v1.6.x cleaned the substrate. v1.7 is when BALLView becomes a real shippable application:
- end users get a signed, notarized macOS bundle they can double-click without "unidentified developer" warnings
- end users get a signed Windows installer they can run without SmartScreen warnings
- both auto-update via Sparkle/WinSparkle
- the warning census from 999.22 actually gets executed
- the v1.4 → v1.7 modernization journey gets captured in a retrospective + audit-procedure document so the next maintainer can understand what was done and why

No substrate rewrites in v1.7 — those are v2.0 (KERNEL MoleculeStore, PIPE-01 renderer, gemmi, YAML, deprecated-code removal). v1.7 is "ship the v1.6.x substrate properly to end users."

## CI matrix gating strategy

User direction (2026-05-17): **macOS only for initial test-builds → +Linux when phases complete → +Windows as v1.7 closure gate.**

### Stage 1 — macOS-only (initial, default for all early v1.7 work)
- `build (macos-arm64)` blocking
- `lint` blocking
- coverage and other Linux jobs **commented out** in matrix on v1.7-modernization branch
- Windows job **commented out** in matrix
- `build (linux-x64)`, `build (linux-arm64)` **commented out**
- macOS Phase 9 test gatekeeper still runs (it's macOS-side)
- Rationale: fastest iteration cycle for early v1.7 phase work; macOS-arm64 is the canonical dev platform here

### Stage 2 — +Linux (triggered when Wave 1 phases land + a critical mass of Wave 2 lands)
- Uncomment `linux-x64` + `linux-arm64` matrix entries (blocking)
- Uncomment `coverage (Linux, gcov, non-blocking)`
- Rationale: cross-arch + cross-toolchain regression net before approaching closure
- Promotion criterion (revised post-review): **any 4 of 9 W1 dispatch units COMPLETE** (drops the Phase 8-specifically requirement — 8a/8b/8c independently gated; 8b can be weeks-late on SignPath without blocking Stage 2 promotion of small phases that need Linux coverage)

### Stage 2.5 — Windows safety net (NEW, added post-review for Q5 mitigation)

Before Stage 3 promotion, **CI-HARDEN-W1** (Wave 1 ~2hr `ci.yml` PR) adds:
- **Weekly Windows cron** (`cron: 0 6 * * 1` — Monday 06:00 UTC): full matrix incl. Windows runs once per week unconditionally, regardless of Stage gating. Catches week-1 regressions instead of waiting for Stage 3.
- **Path-aware Windows PR triggers**: any PR touching `cmake/**`, `.github/workflows/**`, `source/FORMAT/CIFParser*`, `include/BALL/KERNEL/atom.h`, `include/BALL/VIEW/**`, or `vcpkg.json` adds Windows to the per-PR matrix. Catches "Phase 8b SignPath integration explodes on first Windows contact" surprises BEFORE closure.
- Other PRs (docs, tests, source areas not in the list) stay macOS-only per Stage 1 gating.

Net cost: ~5 Windows runs/week + selective per-PR. Much cheaper than full-matrix-always (which would multiply v1.6.1's 80-min Windows wall-clock by ~50 PRs across the milestone) and much safer than wait-for-closure.

### Stage 3 — +Windows blocking (v1.7 closure gate)
- Uncomment `windows-x64` matrix entry as blocking on all PRs
- Wire `release.yml` to v1.7 tag pattern
- Rationale: by closure, Windows is well-warmed via Stage 2.5 weekly + path-aware; this promotion makes it required for all PRs, removing the "non-touching paths can land without Windows verification" gap
- Promotion criterion: All Wave 1 + Wave 2 COMPLETE; v1.7-RC-1 candidate being prepared

### Implementation
- Edit `.github/workflows/ci.yml` on v1.7-modernization branch only; v1.6-modernization branch's matrix is untouched (v1.6.2 release pipeline keeps its full matrix)
- Use commented-out matrix entries with clear "STAGE-N gate" annotation rather than `if:` conditions, so the matrix shape is the documentation
- CI-HARDEN-W1 PR (Stage 2.5 setup) lands FIRST in Wave 1, before any other ci.yml edits, so subsequent rebases see the cron + path-aware triggers as a stable base
