## Goal

Codify the QObject-lifetime conventions that emerged from the
UFG-30/32/18/26 cycle into a canonical doc, audit the 6 known sites,
and ship a small CI lint that catches the most common foot-gun
(`deleteLater()` in destructors).

## Why now

C++ + Qt fails through lifetime bugs more than through algorithmic
ones. Five v1.7.0 RC crashes traced to dtor-order / dangling-pointer /
GL-context / event-loop-ownership issues. The fixes were correct but
folkloric — a new contributor would step on the same rakes.

The conventions doc is the write-once artifact that prevents that, and
rule 2 (`QPointer<T>`) + rule 3 (direct-by-default connections) are
prerequisites the `999.59` base `Controller` depends on.

## The 5 rules (preview — full bodies in the doc)

1. **Owner-rooted parentage.** Every `QObject*` you `new` has a parent OR a documented `deleteLater()` reason.
2. **`QPointer<T>` for cross-owner references.** Dtor-order races become null checks.
3. **Direct connections by default.** Queued is for cross-thread only; explicit when chosen. The single cross-thread path in v1.7.4 is `ControllerJob`'s worker→GUI result hand-off (999.59-05).
4. **GL context ownership stays with `QOpenGLWidget`.** Controllers/sections never touch the context.
5. **No `deleteLater()` inside destructors.** Qt does the parent walk for us.

## Audit cookbook (excerpt)

For each flagged site:

1. Identify the lifetime owner (the parent QObject).
2. Replace raw pointers with `QPointer<T>` where the referent's lifetime can run shorter than the holder.
3. If a `deleteLater()` is in a dtor — restructure (Qt's parent walk does it; if you need explicit destruction order, do it BEFORE the parent dtor runs).
4. Add a brief in-source comment naming the rule that motivated the fix.
