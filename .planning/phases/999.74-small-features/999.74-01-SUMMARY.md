# Phase 999.74 Plan 01: PropertyPlotter axis/value limits Summary

Added user-controllable `-p1_min`/`-p1_max`/`-p2_min`/`-p2_max` flags to the
PropertyPlotter CLI so distribution/scatter plots stay usable on outlier-heavy
data, emitting gnuplot `set xrange`/`set yrange` and filtering out-of-range
points, with the no-flag path left byte-identical (FEATPLOT-01, #524).

## What was built

- **Flag registration** — four new optional flags after `p2`. Each maps to a
  gnuplot range bound:
  | Flag      | Effect on data                          | gnuplot directive                |
  |-----------|-----------------------------------------|----------------------------------|
  | `-p1_min X` | drop molecules with prop1 < X         | `set xrange [X:*]` (or `[X:Y]`)  |
  | `-p1_max Y` | drop molecules with prop1 > Y         | `set xrange [*:Y]` (or `[X:Y]`)  |
  | `-p2_min X` | (scatter) drop molecules with prop2 < X | `set yrange [X:*]` (or `[X:Y]`) |
  | `-p2_max Y` | (scatter) drop molecules with prop2 > Y | `set yrange [*:Y]` (or `[X:Y]`) |

  An unset side of a range uses gnuplot's `*` autorange token.
- **Data filtering** — the read loop computes prop1 (and, in scatter mode, prop2)
  once, then `continue`s past any molecule outside the requested limits, keeping
  the distribution histogram and the scatter data file consistent.
- **Histogram domain** — in single-property (distribution) mode, supplied p1
  limits replace the scanned data extremes so the 100 buckets span exactly the
  requested domain. `-p2_*` is ignored in distribution mode (no p2 axis).
- **gnuplot emission** — `set xrange`/`set yrange` lines are emitted only when a
  limit is supplied, after the existing xlabel/ylabel and before the `plot` line.
  Values are written as numeric doubles by the stream (never raw user strings),
  closing the injection vector in threat T-999.74-01.

## How it maps to gnuplot (concrete)

- `-p1 score -p1_min 0 -p1_max 5` → `set xrange [0:5]`, histogram buckets span 0..5.
- `-p1 score -p1_min 1` → `set xrange [1:*]`.
- `-p1 score -p2 weight -p1_min 0 -p1_max 5 -p2_min 250 -p2_max 450` →
  `set xrange [0:5]` + `set yrange [250:450]`, scatter rows filtered to both ranges.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug / Rule 3 - Blocking] Used registerOptionalStringParameter instead of registerOptionalDoubleParameter**
- **Found during:** Task 1 (first GREEN build).
- **Issue:** The plan's interface block assumed `parpars.get("p1_min") == NOT_FOUND`
  detects an unset flag. In reality `registerOptionalDoubleParameter(name, desc)`
  passes its `0.0` default into `CommandlineParser::checkAndRegisterParameter`,
  which stringifies it to `"0"` and — because `"0" != ""` (commandlineParser.C:87)
  — pre-populates `parameter_map_`. So `get()` returns `"0"` and `has()` returns
  true even when the user omits the flag. The first build emitted a spurious
  `set xrange [0:0]` on a plain `-p1 score` run, breaking the byte-identical-default
  must_have.
- **Fix:** Registered the four numeric limits as `registerOptionalStringParameter`
  with the empty-string default, so the parameter stays out of `parameter_map_`
  until the user supplies it, the `NOT_FOUND` sentinel reliably means "not given",
  and `0.0` remains a legal, honored limit. Values are parsed with `String::toDouble()`,
  exactly as the plan's `<action>` specified.
- **Impact:** The plan's `contains: registerOptionalDoubleParameter` artifact check
  and the `grep -c 'registerOptionalDoubleParameter' # expect 4` verify gate are no
  longer literally satisfiable. This was an unavoidable trade-off: the plan's own
  stated behavior ("do NOT rely on the 0.0 default — 0.0 is a legal limit") and the
  byte-identical-default must_have take precedence over the named-API heuristic. All
  behavioral must_haves and success criteria are met.
