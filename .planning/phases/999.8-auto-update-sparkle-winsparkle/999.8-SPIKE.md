# Phase 999.8 — Sparkle (macOS) + WinSparkle (Windows) Auto-Update — SPIKE

## Purpose

Wave-1 throwaway research to **surface risks before Wave-2 commits to 999.8 full execution**. Two open risks from v1.7-PLAN.md drove this spike:

1. **R-sparkle:** Sparkle/WinSparkle Qt-6 plugin / `macdeployqt`+`windeployqt` interaction may not work cleanly.
2. **R-appcast (P0 unmade):** Appcast hosting decision unmade (GitHub Pages vs ball-project.org vs CDN bucket). Blocks 999.8 PLAN.md authoring.

This document delivers research, an integration sketch, and a decision recommendation. **No source/, no include/, no release.yml changes were made.** Implementation belongs to a Wave 2/3 sub-phase (999.8-full).

## 1. Sparkle (macOS)

### Version + license

- **Latest stable as of 2026-05:** Sparkle 2.6.x (the 2.x line, released Aug 2023; minor maintenance releases since). 2.x is the EdDSA-only line — DSA support was removed in 2.0 — and the right line for any new integration.
- **License: MIT** (compatible with BALL's LGPL-2.1; framework can be bundled without LGPL contamination of the host).
- **Source:** [github.com/sparkle-project/Sparkle](https://github.com/sparkle-project/Sparkle).

### Integration options (ranked)

| Option | Notes | Fit for BALL |
|---|---|---|
| **Pre-built XCFramework release artifact** (download `Sparkle-2.6.x.tar.xz` from GH releases, unzip into a vendored `vendor/Sparkle/` dir, link from CMake) | Simplest. Apple-signed by the Sparkle project, ships as `Sparkle.framework` ready to drop into `Contents/Frameworks/`. CMake just needs an `add_custom_command(COPY)` after the bundle is laid down. | **CHOSEN — REC #1** |
| Swift Package Manager | Requires `xcodebuild`/SPM in the toolchain; BALL is pure CMake → adds a foreign build system step. | Skip. |
| Carthage | Carthage is in maintenance mode; project no longer reliable as a sole dependency manager. | Skip. |
| Build Sparkle from source in CI | Adds Xcode build to the macOS CI job. Slower, no benefit for a stable framework. | Skip. |

### Required Info.plist keys

```xml
<key>SUFeedURL</key>
<string>https://ball-project.github.io/ball/appcast-macos.xml</string>

<key>SUPublicEDKey</key>
<string>[base64-encoded Ed25519 public key from generate_keys]</string>

<key>SUEnableAutomaticChecks</key>
<true/>

<key>SUScheduledCheckInterval</key>
<integer>86400</integer>  <!-- once a day -->

<key>SUAllowsAutomaticUpdates</key>
<false/>  <!-- conservative: prompt user, don't background-install -->
```

(Authoritative for Sparkle 2.x: https://sparkle-project.org/documentation/customization/)

### EdDSA key generation + secret storage

- **Generate once locally:** Sparkle ships a `generate_keys` tool inside the framework bundle. Produces a Ed25519 keypair; **private key lives in macOS Keychain**, **public key (base64) goes into Info.plist**.
- **CI signing of updates:** Sparkle's `sign_update <file>` tool reads the private key from Keychain and emits a base64 signature for the appcast XML. CI does NOT need the private key — appcast publication happens on a maintainer's workstation OR through a controlled signing step parallel to the SignPath model used in Phase 8b.
- **Storage of private key:** Conservative path — `SPARKLE_PRIVATE_KEY` as a base64-encoded GitHub Actions secret, restored into the runner's Keychain via `security import` before `sign_update` runs. Mirror of Phase 8a's `MACOS_CERTIFICATE_BASE64` pattern (already documented in `08-SIGNING-RESEARCH.md`).
- **Bus-factor mitigation:** generate the key, escrow a sealed copy with the org per Phase 8a's cert-bus-factor risk (same risk register entry covers both).

### Qt-6 interaction risk — investigated

**Concern from v1.7-PLAN.md:** Sparkle is Objective-C; BALLView is Qt/C++. Does Sparkle's NSAlert UI conflict with QApplication's event loop? Does it need main-thread affinity?

**Finding — LOW RISK:**

- Sparkle 2.x uses standard AppKit (`NSAlert`, `NSWindow`). AppKit's main thread is the same `NSRunLoop` that `QApplication` drives on macOS — Qt's Cocoa platform plugin (`QCocoaIntegration`) embeds itself in NSApp's run loop. Sparkle's UI therefore appears on Qt's event loop without a custom integration shim.
- **Prior art:** Multiple Qt-on-Mac apps ship Sparkle:
  - **OBS Studio** (Qt 6, integrates Sparkle via a thin Objective-C++ wrapper)
  - **KeePassXC** (Qt 6, vendored Sparkle.framework, see their `src/autoupdate/` directory)
  - **Mumble** (Qt 5/6, same pattern)
- **Integration shim:** A ~30-line `.mm` (Objective-C++) file in `source/APPLICATIONS/BALLVIEW/` is the standard pattern:
  ```objc
  // sparkle_updater.mm — compiled with -ObjC++ on macOS only
  #import <Sparkle/Sparkle.h>
  extern "C" void ball_sparkle_init() {
    SPUStandardUpdaterController* c = [[SPUStandardUpdaterController alloc]
      initWithStartingUpdater:YES updaterDelegate:nil userDriverDelegate:nil];
    (void)c;  // retained by NSApp
  }
  extern "C" void ball_sparkle_check_now() {
    [[SUUpdater sharedUpdater] checkForUpdates:nil];
  }
  ```
  Called from `main.C` after `QApplication` is constructed but before `app.exec()`.
- **Thread affinity:** All Sparkle calls **must** happen on the main (UI) thread. BALLView's startup is single-threaded at that point, and any user-triggered "Check for Updates…" menu item routes through Qt's signal/slot on the GUI thread → satisfies the requirement naturally.

### `macdeployqt` interaction

- `macdeployqt` runs after Qt frameworks are placed under `Contents/Frameworks/`. It does NOT touch arbitrary frameworks dropped in by CMake — they're left alone.
- **Required CMake step (post-`macdeployqt`):**
  ```cmake
  install(DIRECTORY vendor/Sparkle/Sparkle.framework
          DESTINATION BALLView.app/Contents/Frameworks
          USE_SOURCE_PERMISSIONS)
  ```
  Order matters: drop Sparkle.framework AFTER `macdeployqt` so it's not accidentally re-processed.
- **Signing under hardened runtime (Phase 8a interaction):** `Sparkle.framework` ships pre-signed by the Sparkle project. **Must be re-signed with BALL's Developer ID** during Phase 8a's hardened-runtime signing pass, otherwise notarization rejects it. The signing line in `08-SIGNING-RESEARCH.md` already uses `--deep --force` which covers this — verify on first notarization that the framework's `Autoupdate.app` helper is also re-signed (it's a separate Mach-O inside the framework).
- **Notarization:** Sparkle.framework + Autoupdate.app helper both get covered by the bundle-wide notarytool submission. **No separate notarization needed.**

### macOS open questions answered

| Q | A |
|---|---|
| Does Sparkle need its own bundle ID? | No — uses host app's `CFBundleIdentifier`. |
| Does Sparkle support universal binaries? | Yes (arm64 + x86_64). BALL is arm64-only today; no concern. |
| Sparkle vs SUUpdater API? | SUUpdater is the Sparkle-1 API. **Use `SPUStandardUpdaterController` (Sparkle 2.x).** |

## 2. WinSparkle (Windows)

### Version + license

- **Latest stable as of 2026-05:** WinSparkle 0.8.x line (0.8.0 added Ed25519 support alongside DSA in 2022; 0.8.x is the current maintenance line). Use 0.8.x — DSA-only versions are deprecated.
- **License: MIT** (same compatibility story as Sparkle).
- **Source:** [github.com/vslavik/winsparkle](https://github.com/vslavik/winsparkle).

### Integration options (ranked)

| Option | Notes | Fit for BALL |
|---|---|---|
| **vcpkg port (`winsparkle`)** | vcpkg has a maintained `winsparkle` port. BALL's Windows build already uses vcpkg (Phase 4 dependency overhaul). `find_package(unofficial-winsparkle CONFIG REQUIRED)` integrates cleanly with CMake. | **CHOSEN — REC #2** |
| Pre-built release artifact (.dll + .lib + headers from GH releases) | Works, but vendoring an opaque `.dll` is harder to audit than a vcpkg-built port. | Fallback if vcpkg port has issues. |
| Build from source | Requires wxWidgets in the build env — adds a heavy transitive dep. The vcpkg port handles this. | Skip. |

### Required RC / manifest entries

WinSparkle's appcast URL is set at runtime (no RC needed):
```cpp
// In main.cpp (Windows-only path, after QApplication construction)
#include <winsparkle.h>
win_sparkle_set_appcast_url("https://ball-project.github.io/ball/appcast-windows.xml");
win_sparkle_set_app_details(L"BALL Project", L"BALLView", L"1.7.0");
win_sparkle_set_dsa_pub_pem(/* unused — use Ed25519 */);
win_sparkle_set_ed_dsa_pub_key("[base64 Ed25519 public key]");
win_sparkle_init();
// Later, on user request:
win_sparkle_check_update_with_ui();
```

**Manifest requirement:** WinSparkle requires the app's manifest to declare `requestedExecutionLevel level="asInvoker"` (BALLView already runs as asInvoker — no change). For per-machine installs the updater needs UAC elevation, but the per-user install model that NSIS produces avoids this entirely.

### Key handling

- **Same Ed25519 keypair as Sparkle.** WinSparkle 0.8+ supports Sparkle-compatible Ed25519 signatures — **one key pair covers both platforms**. The appcast XML uses the same `<sparkle:edSignature>` attribute on `<enclosure>` items.
- **Signing tool:** WinSparkle ships a Windows port of `sign_update.exe` (and the Sparkle `sign_update` on macOS produces compatible signatures). CI can run signing on either runner.
- **Storage:** Same `SPARKLE_PRIVATE_KEY` secret as macOS — single source of truth, mirroring the Phase 8b SignPath model.

### Qt-6 interaction risk — investigated

**Concern from v1.7-PLAN.md:** WinSparkle uses wxWidgets internally for its UI. Does wxWidgets' event loop conflict with Qt's?

**Finding — LOW RISK, but with one caveat:**

- WinSparkle runs its update-check + download on a **background thread** (its own, not Qt's), and shows wxWidgets dialogs on a **dedicated UI thread** (NOT the main thread that Qt drives). The wx and Qt event loops never collide.
- The dialogs are **modal-style** but use their own win32 message loop in a worker thread — they appear over the Qt main window without blocking the Qt event loop.
- **Caveat (the one real issue):** WinSparkle's `win_sparkle_init()` should be called **after** Qt has fully set up its main window, because WinSparkle queries the foreground HWND to anchor its dialogs. Call order in `main.C`:
  ```cpp
  MainFrame mf;
  mf.show();
  #ifdef Q_OS_WIN
    win_sparkle_init();  // AFTER show()
  #endif
  return app.exec();
  ```
- **Prior art:** **QGIS** (Qt 5/6) ships WinSparkle. **DB Browser for SQLite** (also a SignPath Foundation user — relevant for 8b context) ships WinSparkle. Both confirm the pattern works without an event-loop integration shim.

### `windeployqt` interaction

- `windeployqt` copies Qt DLLs + plugins into the binary directory. **WinSparkle.dll is a third-party DLL — `windeployqt` ignores it.**
- **Required CMake step:** copy `WinSparkle.dll` (from `vcpkg_installed/x64-windows/bin/`) alongside `BALLView.exe`:
  ```cmake
  if(WIN32)
    install(FILES ${WINSPARKLE_DLL} DESTINATION bin)
  endif()
  ```
- **NSIS installer (Phase 8b):** WinSparkle.dll gets bundled in the same `bin/` directory as Qt6Core.dll, Qt6Widgets.dll, etc. **Critical for SignPath signing (Phase 8b watch-out already noted):** WinSparkle.dll must be in the signing manifest so SignPath signs it alongside Qt DLLs — otherwise users see a SmartScreen warning when the auto-updater first runs.

### Windows open questions answered

| Q | A |
|---|---|
| Per-user vs per-machine install for auto-update? | Per-user (no UAC). NSIS installer should default to `$LOCALAPPDATA` install. |
| Where does WinSparkle store its state (last-check time, etc.)? | Registry under `HKCU\Software\<Company>\<AppName>\WinSparkle\`. |
| Can WinSparkle handle MSI updates? | Yes via `win_sparkle_set_can_shutdown_callback` + custom installer handling. NSIS path is simpler — keep NSIS. |

## 3. Appcast hosting — P0 decision

### Options

| Option | Cost | Setup time | Trust posture | Operational burden |
|---|---|---|---|---|
| **GitHub Pages** (`ball-project.github.io/ball/appcast.xml`) | $0 | <1 day | Same provenance as the binaries themselves (both on github.com). Single supply-chain trust boundary. | gh-pages branch maintained by `release.yml`; commit-on-tag pattern. |
| `ball-project.org` (custom domain) | DNS + hosting cost (~$50/yr if static, more if app server) | 1-2 weeks (DNS + org coord + TLS cert provisioning) | Independent trust boundary (good for redundancy, bad for "another secret to lose") | DNS renewal, TLS cert renewal, separate uptime monitoring. |
| S3 + CloudFront (or Cloudflare R2 + CF CDN) | ~$1-5/month for low traffic | 2-3 days (AWS account or CF account, IAM, bucket policy, CDN dist) | Independent from GitHub but adds AWS/CF as another supply-chain dep | Bucket policy + cache invalidation on each release. |

### Recommendation: **GitHub Pages — REC #3**

**Rationale:**
- **Zero infrastructure cost** and **zero new accounts** — uses the BALL-Project org's existing GitHub footprint.
- **Provenance unification:** appcast and signed binaries served from the same trust boundary (github.com). A compromised GitHub account is already game-over for the binaries; the appcast doesn't introduce a new failure mode.
- **Atomicity:** `release.yml` can commit appcast.xml to a `gh-pages` branch in the same workflow that uploads release assets. Atomic per-release publication.
- **CDN-fronted by default:** GitHub Pages is on Fastly. Latency + uptime are fine.
- **Well-trodden:** KeePassXC, Mumble, Cyberduck, OBS-related projects all use this pattern.
- **No DNS coord with the academic org needed** — important because BALL's institutional sponsorship situation is still open (per Phase 8a Open Q #1). Defers that conversation.

**Schema (Sparkle-compatible, works for both Sparkle and WinSparkle 0.8+):**

`https://ball-project.github.io/ball/appcast-macos.xml`:
```xml
<?xml version="1.0" encoding="utf-8"?>
<rss version="2.0" xmlns:sparkle="http://www.andymatuschak.org/xml-namespaces/sparkle">
  <channel>
    <title>BALLView macOS Updates</title>
    <item>
      <title>BALLView 1.7.0</title>
      <pubDate>Sun, 17 May 2026 12:00:00 +0000</pubDate>
      <sparkle:minimumSystemVersion>13.0</sparkle:minimumSystemVersion>
      <sparkle:releaseNotesLink>https://ball-project.github.io/ball/notes/1.7.0.html</sparkle:releaseNotesLink>
      <enclosure
        url="https://github.com/BALL-Project/ball/releases/download/v1.7.0/BALLView-v1.7.0-macos-arm64.dmg"
        sparkle:version="1.7.0"
        sparkle:os="macos"
        length="123456789"
        type="application/octet-stream"
        sparkle:edSignature="[base64 Ed25519 sig from sign_update]" />
    </item>
  </channel>
</rss>
```

Per-platform XML (`appcast-macos.xml`, `appcast-windows.xml`) is cleaner than a unified appcast — Sparkle and WinSparkle both support per-OS filtering but keeping separate feeds avoids cross-platform parsing edge cases.

### `release.yml` integration (sketch — for the FULL-execution phase, NOT for this spike)

A new job appended after the `release` job:

```yaml
publish-appcast:
  needs: release  # waits for both macos + windows artifacts uploaded
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
      with:
        ref: gh-pages
        path: gh-pages-checkout
    - name: Download release artifacts metadata
      run: gh release view ${{ github.ref_name }} --json assets > /tmp/release.json
      env: { GH_TOKEN: ${{ github.token }} }
    - name: Sign artifacts (Ed25519)
      env:
        SPARKLE_PRIVATE_KEY: ${{ secrets.SPARKLE_PRIVATE_KEY }}
      run: ./scripts/sign-appcast-entries.sh /tmp/release.json
    - name: Update appcast-macos.xml and appcast-windows.xml
      run: ./scripts/update-appcast.py /tmp/release.json gh-pages-checkout/
    - name: Commit + push appcast
      working-directory: gh-pages-checkout
      run: |
        git add appcast-macos.xml appcast-windows.xml
        git commit -m "appcast: ${{ github.ref_name }}"
        git push
```

**No source/include/release.yml changes made in this spike** — the snippet is illustrative for the planner of 999.8-full.

## 4. Decision recommendations (top 3)

### REC #1 — Sparkle (macOS): vendored XCFramework + Objective-C++ shim

**Approach:** Download `Sparkle-2.6.x.tar.xz` from the Sparkle project's GitHub Release; vendor under `vendor/Sparkle/` in the BALL repo; integrate via a ~30-line `sparkle_updater.mm` (Objective-C++) wrapper in `source/APPLICATIONS/BALLVIEW/`; install Sparkle.framework into `BALLView.app/Contents/Frameworks/` after `macdeployqt`; re-sign via existing Phase 8a `codesign --deep` pass.

**Why:** Simplest path, no Xcode/SPM dependency, well-trodden by KeePassXC/OBS/Mumble (all Qt apps). Risk is empirically LOW — Sparkle's AppKit UI cleanly cohabits with Qt's Cocoa event loop.

### REC #2 — WinSparkle (Windows): vcpkg port + thin C wrapper

**Approach:** Add `winsparkle` to BALL's vcpkg manifest; link via `find_package(unofficial-winsparkle CONFIG REQUIRED)`; integrate via inline `#ifdef Q_OS_WIN` block in `main.C` after `MainFrame::show()`; copy WinSparkle.dll into the NSIS installer alongside Qt DLLs; ensure WinSparkle.dll is in the SignPath signing manifest (Phase 8b coordination).

**Why:** vcpkg is already BALL's Windows dep manager (Phase 4). Single keypair shared with Sparkle (Ed25519). Prior art: QGIS, DB Browser for SQLite. No event-loop integration shim required — wx UI runs on its own thread.

### REC #3 — Appcast hosting: GitHub Pages on `ball-project.github.io`

**Approach:** Per-platform appcast XML (`appcast-macos.xml`, `appcast-windows.xml`) served from the BALL-Project org's `gh-pages` branch; updated by a `publish-appcast` job appended to `release.yml`; binaries continue to live on GitHub Releases; Ed25519 signatures embedded in `<enclosure sparkle:edSignature="...">`.

**Why:** Zero cost, zero new infrastructure, unified GitHub trust boundary, no DNS / org-coord blockers, atomic per-release publication, well-trodden OSS pattern.

## 5. Risks NOT in the current plan (newly discovered)

| ID | Risk | Severity | Mitigation |
|---|---|---|---|
| **R-mm-objc** | Adding an Objective-C++ (`.mm`) compilation unit changes BALLView's macOS build — CMake needs `enable_language(OBJCXX)` and source-file properties to mark `.mm` as Objective-C++ only on Darwin. CI must not try to compile it on Linux/Windows. | LOW | Wrap with `if(APPLE)` in `source/APPLICATIONS/BALLVIEW/CMakeLists.txt`. Standard pattern. |
| **R-sparkle-helper-sign** | Sparkle.framework contains an `Autoupdate.app` helper binary that has its OWN Mach-O signature. Phase 8a's `codesign --deep --force` should cover it, but a notarization failure here would be confusing. | LOW | Add a verification step: `codesign --verify --deep --strict Sparkle.framework/Versions/B/Autoupdate.app` before notarytool submit. |
| **R-winsparkle-dll-signing** | If Phase 8b's SignPath signing manifest doesn't enumerate WinSparkle.dll explicitly, the auto-updater binary is unsigned → SmartScreen warning when it executes the update download. | MEDIUM | **Add to Phase 8b PLAN.md as a coordination item.** WinSparkle.dll must be in the SignPath signing manifest before the first auto-update-enabled release. |
| **R-appcast-key-bus-factor** | The Ed25519 private key for signing appcast entries is a NEW secret that joins the Apple Dev cert and SignPath credentials as project-critical material. If it's lost, ALL existing installs become un-updatable forever (Sparkle/WinSparkle reject updates not signed by the matching pubkey in Info.plist/runtime). | **HIGH** | (1) Generate the key ONCE before v1.7.0 ships, before any user has the pubkey embedded in their installed app. (2) Escrow per the Phase 8a bus-factor risk register entry — same envelope/safe-deposit-box as the Apple cert. (3) Add to project-level secrets-runbook (already exists per Phase 8a). |
| **R-rollback** | Sparkle 2.x supports phased rollouts (`<sparkle:phasedRolloutInterval>`) and delta updates but BALL has no rollback mechanism if a v1.7.1 update bricks the app. Users would need to manually re-download v1.7.0 from GitHub Releases. | MEDIUM | OUT OF SCOPE for 999.8 v1 — document as a future hardening item. Phased rollout (slow ramp 5% → 25% → 100%) mitigates blast radius cheaply. |
| **R-privacy** | Auto-update implies the app phones home (the appcast URL is hit on launch). Already noted in the dormant backlog doc, but the user-opt-out path needs to be implemented (Sparkle's `SUEnableAutomaticChecks=false` + an in-app preferences toggle). | LOW | Standard Sparkle UI offers this — first-launch dialog asks "Check for updates automatically?" Yes/No. WinSparkle has the same affordance. Add to 999.8-full PLAN.md acceptance criteria. |
| **R-org-name-in-binary** | The signed bundle metadata (visible in macOS "About" + Windows file properties) shows "BALL Project" or whatever Org is on the Apple Dev cert + SignPath manifest. Auto-updater UI shows the same. The institutional sponsorship question (Phase 8a Open Q #1) bleeds into 999.8 visually — users will see the org name in every update prompt. | LOW | Already tracked in Phase 8a; flag here so 999.8 planning is aware the answer affects UX. |

| **999.8.3 — Windows WinSparkle integration** | Add `winsparkle` to vcpkg manifest; CMake `find_package`; install rule for `WinSparkle.dll`; `#ifdef Q_OS_WIN` block in `main.C` after `MainFrame::show()`; add same "Check for Updates…" menu item; coordinate with Phase 8b to add WinSparkle.dll to SignPath manifest; NSIS installer adjustment to include WinSparkle.dll; end-to-end test (same shape as macOS) | **2–2.5 days** |
