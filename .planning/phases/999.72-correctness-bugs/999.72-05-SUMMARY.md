# Phase 999.72 Plan 05: DisplayProperties leak (#636) verdict Summary

**Verdict: BUG-636 resolved-by-deletion. No residual leak. No source edit made.**

The #636 leak was the `DisplayProperties::rep_` member used as a temporary for both an owning (`createRepresentation`) and a non-owning raw pointer, leaking the `Representation` on the owning path. DisplayProperties was deleted entirely in Phase 999.67; the owning logic migrated to `RepresentationBuilder::createRepresentation`, where the dual-use temporary no longer exists.

## Evidence audit (Task 1)

**(1) Deletion confirmed**
- `git ls-files | grep -i displayProperties | grep -v "^.planning"` → no source file (only `.planning` archives remain).
- `grep -rn "rep_" source/VIEW/MODELS/representationBuilder.C source/VIEW/KERNEL/representationCreator.C` → nothing. The dual-use member is gone.
- Task-1 automated gate: `git ls-files | grep -i "DIALOGS/displayProperties" | grep -v "^.planning" | grep -c .` → `0` → **deleted-OK**.
- Additional corroborating evidence: the dormant `test/RepresentationManager_test.C` is **unregistered and uncompilable** because it still `#include <BALL/VIEW/DIALOGS/displayProperties.h>` (line 12) — a header that no longer exists. This confirms the header was fully removed by 999.67.

**(2) `new Representation()` ownership trace — `createRepresentation` (representationBuilder.C:120-177)**
- Both early-outs occur BEFORE the allocation: `if (composites.size() == 0) return 0;` (l.128) and `if (first_composite == 0) return 0;` (l.132). No allocation can be orphaned there.
- The single `Representation* rep = new Representation();` (l.135) is followed by a straight-line body with no further early returns and no throwing call before ownership transfer. `main_control.getRepresentationManager().insert(*rep, false)` (l.161) hands ownership to the manager (`RepresentationManager::insert` push_backs; `remove` does `if (!willBeUpdated(...)) delete &representation`).
- Both exit paths — `if (hidden) return rep;` (l.172) and the final `return rep;` (l.176) — occur AFTER `insert`, so the manager owns `rep` on every path.

**(3) hidden path + String-driven path (representationManager.C:501)**
- The `hidden == true` path differs only in skipping `rep->update(true)`; it still returns the already-inserted (manager-owned) pointer. No orphan.
- `RepresentationManager` (l.501) calls `RepresentationBuilder::createRepresentation(...)`; at l.505 `if (rep == 0) continue;` — but `rep == 0` only results from the two pre-`new` early-outs, so nothing was allocated when it is null. After that, `rep` is already manager-owned. No dropped allocation.

Conclusion: every `new Representation()` reachable from the migrated path has exactly one owner on every exit path. **No residual leak.**

## ASan validation (Task 2)

Per Task 2, since no residual leak was found, **no source edit was made** and the resolution was validated with a sanitizer build:
- Configured `build/asan` with `-DUSE_ASAN=ON -DBALL_LICENSE=GPL` (gated in `cmake/BALLCompilerSpecific.cmake`, adds `-fsanitize=address -fno-omit-frame-pointer`).
- Built `libVIEW` clean under ASan — the `representationBuilder.C` TU (the createRepresentation path) is instrumented.
- Ran a registered VIEW model test (`BallAndStickModel_test`) that drives the VIEW representation machinery under ASan (`QT_QPA_PLATFORM=offscreen`): **PASSED, 0 AddressSanitizer errors** (no use-after-free / heap-overflow in the representation path).

**Platform note (per plan):** macOS/AppleClang ASan does **not** include LeakSanitizer — running with `detect_leaks=1` aborts with `detect_leaks is not supported on this platform`. So the macOS run validates memory-safety of the representation path but cannot itself assert leak-absence. The dedicated leak-presence confirmation (LSan) should run on **ci-linux** (GCC/Clang ASan with LSan), where a "Direct leak ... createRepresentation / Representation" report would surface if one existed. The static ownership audit above already proves single-owner on every exit path, so no leak is expected there.
