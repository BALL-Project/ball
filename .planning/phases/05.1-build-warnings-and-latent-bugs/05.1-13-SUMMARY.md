# Phase 05.1 Plan 13: BACKLOG Task D4 — Windows release LNK1104 `--config Release` Summary

No-op plan. Both `--config Release` insertions targeted by Plan 05.1-13 were
already in place in prior commits before this plan executed; closing out
per the plan's decision-default policy.

## What Plan 13 Was Meant to Do

BACKLOG.md Task D4 (Windows path): on the Visual Studio multi-config generator
`cmake --build --preset ci-windows --target BALL VIEW BALLView` defaults to
**Debug** when `--config` is omitted, so MSBuild tried to link against
`tbb12_debug.lib`. The `x64-windows-release` vcpkg overlay triplet only
builds Release variants of TBB by design, so the linker failed with
`LNK1104: cannot open file 'tbb12_debug.lib'`. This blocked the Windows
installer for the v1.6.0 release.

Plan 13 directed a one-line edit per file in both
`.github/workflows/release.yml` and `.github/workflows/ci.yml`:

```yaml
- name: Build (Windows)
  shell: pwsh
  run: |
    cmake --build --preset ci-windows --config Release --target BALL VIEW BALLView
```

## What I Found

Both target lines already contained `--config Release` at plan-start time.

### release.yml — line 193

```text
$ grep -nE "cmake --build.*--preset ci-windows" .github/workflows/release.yml
193:          cmake --build --preset ci-windows --config Release --target BALL VIEW BALLView
```

Fixed by commit `381c129` (`fix(release): pass --config Release to cmake --build
on Windows (D4)`) on `v1.6-modernization` and propagated to master via
`8b2667a` (`ci(release): sync release.yml with the codesign + --config Release
fixes`) and `afa00c2` (`release(v1.6.0): consolidate iter-5 fixes`). Surrounding
9-line comment block above line 193 documents the post-mortem on release run
25908337693, exactly matching the rationale BACKLOG D4 records.

### ci.yml — line 315

```text
$ grep -nE "cmake --build.*--preset ci-windows" .github/workflows/ci.yml
315:          cmake --build --preset ci-windows --target BALL VIEW BALLView --config Release
```

Token order differs from release.yml (`--config Release` at end vs. between
`--preset` and `--target`) but the grep pattern in the plan's verify block
(`cmake --build --preset ci-windows.*--config Release`) matches both with the
`.*` between the `ci-windows` and `--config Release` anchors. cmake parses
both orderings identically (cmake's `--build` arg parser is order-insensitive
on these flags).

`git blame -L 313,316 .github/workflows/ci.yml` traces line 315 back to commit
`e63f061` (`feat(04-04): wire Windows CI job with real vcpkg + choco
provisioning`) authored 2026-05-14 18:34:52 +0200. That predates the
2026-05-15 release run that surfaced the gap in release.yml. **ci.yml never
had the latent gap that BACKLOG D4 claimed** — `--config Release` was on the
Windows build line from the very first commit that wired the real Windows
job.

The BACKLOG D4 entry was authored under the (incorrect) assumption that
ci.yml had the same gap as release.yml. The actual asymmetry: release.yml
was a brand-new workflow (`a186fb5`, `feat(ci/release): add best-effort
unsigned installer workflow`) and its author copied the Windows build
recipe without `--config Release` — the bug was specific to that workflow.

## Decisions Made

1. **Closed out as no-op per the plan's decision-default policy.** The plan
   explicitly stated: *"If both files already contain `--config Release` (e.g.
   someone fixed this between BACKLOG.md and now), document that and close
   out with a no-op commit + SUMMARY."* That branch was taken without
   ambiguity — both files contained the flag.

2. **No regression risk to validate.** Since the plan does not modify either
   workflow file, there is no diff to review for accidental regression of
   plan-11 (v5 action pins) or plan-12 (apt-cache `*.deb` path narrowing).
   Both prior fixes remain in place untouched.

3. **BACKLOG D4 attribution correction documented.** The BACKLOG claim that
   ci.yml had a latent matching gap was inaccurate. ci.yml had `--config
   Release` from the moment the real Windows job was wired in (commit
   `e63f061`, Phase 04-04). Only release.yml was ever missing the flag —
   that gap was patched in `381c129`. Recording this in SUMMARY so a future
   reader doing BACKLOG-source-of-truth lookups against past phases doesn't
   re-investigate the ci.yml side on the (incorrect) BACKLOG hypothesis.

the Phase 04-04 `feat(04-04): flip Windows CI to blocking after first

**blocking** after the wire-up that included `--config Release`, so any
regression of the flag would have already broken the milestone branch's
