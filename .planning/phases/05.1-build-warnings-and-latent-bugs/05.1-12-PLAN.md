<objective>
Fix BACKLOG.md Task **D3** — Linux ccache cache-save tar failure.

The Linux build job's post-build cache-save step intermittently emits:

    Failed to save: "/usr/bin/tar" failed with error: The process '/usr/bin/tar' failed
    with exit code 2

Impact: subsequent runs on the same cache key cold-compile, slowing iteration. Build
itself still green. Could be transient (race / runner storage pressure / cache size limit
hit) or real (corrupted state, permission issue).

**Diagnosis-first** per BACKLOG. The fix is not pre-determined — this plan starts with
investigation steps and only applies a fix if a recurring cause is identified.

Plan is non-autonomous because diagnosis involves judgement calls on each piece of
evidence and the maintainer should approve the chosen fix (or the "no fix, classified
transient" classification).

Not Codex cross-checked.

Purpose: BACKLOG.md task D3.
Output: diagnosis trail in SUMMARY; optionally a small edit to
`.github/workflows/ci.yml`.
</objective>

    - .github/workflows/ci.yml — find the Linux ccache cache step; understand the cache key strategy and what the cache contains
    - the last 5-10 ci.yml runs on the `v1.6-modernization` branch — `gh run list --branch v1.6-modernization --limit 20 --json databaseId,conclusion,createdAt,headSha` then for each: `gh run view <id> --log 2>/dev/null | grep -E "Failed to save|tar.*exit code|ccache"` to extract per-run evidence
  </read_first>
  <action>
    **Step 1 — measure recurrence.** Pull the last 10 ci.yml runs on
    `v1.6-modernization`. For each run, check whether the Linux cache-save step
    succeeded or failed. Tabulate:

        | Run ID | Date | Linux cache-save | Notes |
        |--------|------|------------------|-------|
        | ...    | ...  | success / failed | ...   |

    **Step 2 — classify.** If failure rate is:

    - **< 20% (1-2 in 10):** likely transient. No fix needed; document the rate as
      observed; revisit if the rate climbs. Skip to SUMMARY.
    - **20-80%:** intermittent — capture more evidence. Run with
      `ACTIONS_RUNNER_DEBUG=true` on the cache step by adding it as a `env:` on the cache
      step in a throwaway PR. Inspect the tar invocation and stderr.
    - **> 80% (chronic):** root cause is structural — almost certainly cache size or
      permissions.

    **Step 3 — identify cause.** Three common causes per BACKLOG:

    - **Cache size exceeds 10 GB GitHub-imposed limit:** check `gh cache list --limit 10`
      and look at sizes. If any caches are at or near 10 GB, this is the cause. Fix
      direction: split the ccache cache into multiple keys (e.g. per-target or per-build-
      type) OR shrink the ccache `max_size` setting.
    - **Runner disk pressure:** the runner ran out of disk during tar. Fix direction: add
      a pre-save cleanup step (`sudo rm -rf /tmp/* ~/.cache/*-stale*`) before the cache
      save.
    - **File permissions on ccache_dir:** files written with a uid that the cache action
      can't read. Fix direction: `chmod -R u+rw $CCACHE_DIR` before save, or run the
      build under the same uid as the cache action.

    Record the diagnosis trail in SUMMARY.
  </action>
