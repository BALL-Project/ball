# Phase 05.1 Plan 10: Qt5LinguistTools Missing on Windows vcpkg (D1 / D6 root cause) Summary

Stabilised the Windows LinguistTools provisioning path by (1) confirming `qttools` is already in `vcpkg.json` (D6 root-cause fix landed earlier on this branch) and (2) defensively adding `QUIET` + downgrading the missing-tools `MESSAGE(WARNING ...)` to `MESSAGE(STATUS ...)` in `CMakeLists.txt`, so CMake's built-in `By not providing FindQt6LinguistTools.cmake` warning is suppressed even in edge cases where the port is unavailable (e.g. a local non-vcpkg dev build). Translation pipeline behaviour is unchanged on the happy path; on the absent-tools path it now logs a single controlled STATUS line and `BALLViewTranslations.cmake` continues to early-`RETURN()`.

## Objective Recap

Eliminate the Windows CI Configure-step warning

```
CMake Warning at C:/vcpkg/scripts/buildsystems/vcpkg.cmake:908: By not providing
FindQt5LinguistTools.cmake ... CMake did not find one.
```

which surfaced because the vcpkg manifest historically did not declare `qttools` (Qt 6) / `qt5-tools` (Qt 5), so the LinguistTools CMake config was never installed on the Windows runner. Per CONTEXT.md, D1 (user-visible symptom) and D6 (root-cause manifest gap) are the same fix.

## What Landed

### Option (a) — vcpkg.json (already in place)

`vcpkg.json` already declares `qttools` at line 8 of the `dependencies` array:

```json
{
  "dependencies": [
    "qtbase",
    "qttools",
    ...
  ]
}
```

This was the D6 root-cause fix (per BACKLOG.md §D6 status note: "v1.6.0 tag commit `c394543`: FIXED 2026-05-15"). At the time the plan was authored, BACKLOG.md still listed `v1.6-modernization` HEAD as "STILL MISSING `qttools`", but inspection of the manifest on this branch shows it has since landed. No change required to vcpkg.json — verified with `python3 -c "import json; json.load(open('vcpkg.json'))"` (clean parse).

### Option (b) — CMakeLists.txt defensive guard (this commit)

Even with `qttools` provisioned, the original code at `CMakeLists.txt:344` used the bare form

```cmake
FIND_PACKAGE(Qt6LinguistTools ${QT_MIN_VERSION})
```

which emits CMake's built-in "By not providing FindQt6LinguistTools.cmake" warning whenever the config package is genuinely absent (e.g. a developer building locally on a Qt install that did not include LinguistTools). The follow-up `IF(NOT Qt6LinguistTools_FOUND) MESSAGE(WARNING ...)` then layered a second warning on top.

Replaced with:

```cmake
FIND_PACKAGE(Qt6LinguistTools ${QT_MIN_VERSION} QUIET)

IF(NOT Qt6LinguistTools_FOUND)
    MESSAGE(STATUS "Qt6LinguistTools not found — translations disabled (add 'qttools' to vcpkg.json on Windows or install qttools via system Qt to enable).")
ENDIF()
```

`QUIET` silences the built-in CMake warning; the controlled `MESSAGE(STATUS ...)` documents the consequence and points to the remediation. `cmake/BALLViewTranslations.cmake:6-8` already early-`RETURN()`s when `Qt6LinguistTools_FOUND` is false, so the translation pipeline is correctly skipped — no further wiring needed.

## Why STATUS Instead of WARNING

Translations are strictly i18n (English source strings + their localised translations under `data/BALLView/translations/`). Missing translations:
- do NOT prevent the build
- do NOT prevent BALLView from running
- do NOT affect any code path other than `QApplication::translate()` string lookup

A WARNING was over-loud for an entirely cosmetic absence. STATUS conveys the same information without inflating the warning count CI dashboards key off.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — defence-in-depth] Combined options (a) + (b) instead of picking one.**

- **Found during:** Task 1 read-first / discovery step.
- **Issue:** The plan presented options (a) vcpkg.json port-add and (b) CMakeLists.txt conditional as alternatives ("pick whichever is less work to verify"). Discovery surfaced that option (a) was already complete on this branch (`qttools` already in `vcpkg.json:8`, landed as the D6 root-cause fix). Doing only the verified-already work (option a) would have left the latent bug intact: the bare `find_package(... )` call would still emit the built-in CMake warning on any non-vcpkg build path where LinguistTools happens to be absent (local dev, future Qt install variants).
- **Fix:** Applied option (b) on top of the already-landed option (a). `QUIET` + STATUS gives defence-in-depth: vcpkg provisions the tools on Windows CI; the CMake guard catches every other absent-tools path.
- **Files modified:** `CMakeLists.txt` (lines 344–348 → 344–354, +5 net lines incl. the explanatory comment block)
- **Commit:** (this commit — see hash in completion footer)

Rationale: Rule 2 ("auto-add missing critical functionality") covers correctness/robustness gaps. The bare `find_package` without `QUIET` is the exact pattern the plan's option (b) calls out as the alternative remediation; landing both is strictly better than landing only the manifest fix, at the cost of 5 lines of CMake.
