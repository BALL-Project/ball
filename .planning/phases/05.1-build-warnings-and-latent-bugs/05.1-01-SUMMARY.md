# Phase 05.1 Plan 01: C4717 getline Infinite Recursion Fix — Summary

**One-liner:** Removed 4 `move(` tokens from two `BALL::String&&` `getline` overloads in `string.iC`; they now dispatch to the standard `std::getline(istream&, std::string&, ...)` overload via the existing `(string&)str` cast, eliminating MSVC C4717 (infinite recursion) and a real stack-overflow vulnerability.

## What Changed

Two near-identical 4-line inline overloads in `include/BALL/DATATYPE/string.iC` (in the `namespace std { ... }` block extending standard `getline` to `BALL::String`):

**string.iC:1761** (3-arg overload, with delimiter):
```cpp
// before
return getline(is, move((string&)str), delim);
// after
return getline(is, (string&)str, delim);
```

**string.iC:1767** (2-arg overload):
```cpp
// before
return getline(is, move((string&)str));
// after
return getline(is, (string&)str);
```

The two pre-existing lvalue overloads at lines 1748–1757 already use exactly this `(string&)str` pattern — the fix is a correctness alignment between the rvalue and lvalue overload families.

## Why It Mattered

The standard library exposes four `std::getline` overloads, all of which bind their string argument as `std::string&` — there is no `std::getline(istream&, std::string&&, ...)`. So when the previous body wrote `getline(is, move((string&)str), delim)`:

1. The argument `move((string&)str)` is an rvalue of type `std::string`.
2. There is no standard overload taking `std::string&&`, so overload resolution looks at the candidates in scope.
3. The being-defined `getline(istream&, BALL::String&&, char)` is in scope. The candidate `std::string&&` argument can convert to `BALL::String&&` via the **non-explicit** converting constructor `BALL::String(string&& s)` declared at `string.h:161`.
4. The function therefore recurses on itself with the same arguments — guaranteed infinite recursion → stack overflow.

MSVC catches this as warning **C4717** (`function recursive on all control paths`). gcc and clang silently emit the same recursion. Anyone calling `std::getline(stream, std::move(some_BALL_String), ...)` was guaranteed a crash.

Dropping `move()` makes the call falls into the standard `std::getline(istream&, std::string&[, char])` overload, where the `(string&)str` cast invokes `String::operator string&()` (declared at `string.h:252`) yielding a real `std::string&` reference to the internal `str_` buffer. That overload then fills the buffer in place — exactly what callers expect.
