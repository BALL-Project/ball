# Phase 999.59 Plan 01: Controller cut-over foundation Summary

Landed the base `Controller` command-contract types — base `Controller`
QObject, nest-aware `ControllerApplyGuard`, `ApplyPayload`, and the
`BALL_VIEW_CONTROLLER_APPLY_RETURNS_BOOL` feature macro — with zero
behavior change to the nine existing controllers, wiring the new base
into libVIEW and flipping the 999.60 harness fixtures live.

## What landed

- **`controllerApplyGuard.h`** — upgraded from a one-shot `bool&` flag to
  a nest-aware RAII `int&` depth counter (ctor `++depth`, dtor `--depth`;
  callers test `depth > 0` before constructing). Documented GUI-thread-only
  (a re-entry shield, not a mutex; §4 Codex HIGH #6). A transitional
  `bool&` overload was retained so the not-yet-migrated controllers still
  compile (see Deviations).
- **`applyPayload.h` (NEW)** — `struct ApplyPayload { String command_id,
  before, after; void* target; long t_us; }`. Header-only,
  copy-constructible POD, no QObject base — ready for v2.0 undo capture (§2).
- **`controller.h` + `controller.C` (NEW)** — `class BALL_VIEW_EXPORT
  Controller : public QObject` (Q_OBJECT) in `BALL::VIEW`, owner-rooted
  ctor (§9). Declares `virtual bool apply()` (base returns false),
  `virtual void reset()` (base no-op, the 999.64 single-event reset path),
  protected `virtual void invalidateDeclared_()` (§2a hook, base empty),
  and protected `int applying_depth_`. Defines
  `BALL_VIEW_CONTROLLER_APPLY_RETURNS_BOOL` at file scope (exact spelling
  the harness checks).
- **Build wiring** — `controllers/controller.C` added to `SOURCES_LIST`
  in `source/VIEW/KERNEL/sources.cmake`; headers auto-globbed; AUTOMOC
  scans `controller.h` via its same-name paired `.C`.
- **Harness flip** — `contractTestHarness.h` now includes `controller.h`
  so the macro is defined before its `CONTRACT_FIXTURE_DISABLED` `#if`,
  flipping `CONTRACT_FIXTURE_DISABLED` to `0` (fixtures live).

## Verification

The worktree has no pre-configured CMake build dir bound to it (the
existing `build*/` dirs are bound to the main repo source tree, not this
worktree), and a full from-scratch configure + libBALL + VIEW build is
prohibitively long for a foundation type-only change. Verification was
therefore **targeted compilation against the real Qt5.15 (Homebrew) +
BALL include tree + the main build's generated `config.h`**, which is the
authoritative check for type-level work:

- `controller.C` compiles to a real object file (`clang++ -c`, exit 0,
  1704 bytes) — full codegen, zero errors/warnings.
- `moc controller.h` generates valid meta-object code (95 lines); the
  generated TU compiles clean with the AUTOMOC `-p` prefix — the Q_OBJECT
  surface is well-formed.
- `applyPayload.h` includes standalone and is copy-constructible
  (`ApplyPayload q = p` compiles).
- `ControllerApplyGuard` nest semantics verified at runtime: depth
  `0→1→2→1→0`; the legacy `bool&` one-shot sets/clears correctly.
- The exact legacy controller pattern (`bool applying_;
  ControllerApplyGuard g(applying_)`) compiles + runs — confirming the 7
  existing controllers are unbroken.
- **Harness flip confirmed**: a preprocessor probe replicating a contract
  test's include order (`contractTestHarness.h` first, then the controller
  header) shows `CONTRACT_FIXTURE_DISABLED == 0` and the macro visible. A
  negative control (harness include line removed) re-disables the
  fixtures — proving the flip is driven exclusively by this plan's change.

Full multi-OS `cmake --build --target VIEW` remains the CI gate; the
local targeted compile is a strong proxy that libVIEW will build clean.

## 999.60 harness fixture behavior with the macro defined

Behaves exactly as the plan predicted. Defining the macro flips
`CONTRACT_FIXTURE_DISABLED` to `0`, which activates the previously-skipped
`#else` parity blocks in all nine `*_contract_test.C` fixtures (and
`reentrancy_test.C`). Those blocks assume `bool apply()`
(`bool mutated = c.apply();`) — but the nine controllers still return
`void` in this foundation phase (their cut-over is 999.59-02/03).
Consequently the **contract-tests executables will not compile until
02/03 land the per-controller `bool apply()` cut-overs**. This is the
plan's explicitly-anticipated "not-yet-cut-over controllers expected-fail
until Plans 02/03" outcome.

Critically, this breakage is **isolated to the `contract-tests` CI job**
(Linux-only): no VIEW library source includes the harness, and no
controller `.C` includes the base `controller.h`, so **libVIEW and
BALLView build clean** — the plan's primary gate is satisfied. See the
Open Item below.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Build wired via sources.cmake, not the named CMakeLists.txt**
- **Found during:** Task 3
- **Issue:** The plan's `files_modified` named
  `source/VIEW/KERNEL/controllers/CMakeLists.txt` and
  `source/VIEW/CMakeLists.txt`; neither exists. This tree registers VIEW
  sources through `sources.cmake` files consumed by `ADD_VIEW_SOURCES`.
- **Fix:** Added `controllers/controller.C` to `SOURCES_LIST` in

  `include/BALL/VIEW/KERNEL/sources.cmake`; AUTOMOC handles `controller.h`
  via its same-name `.C` (no `MOC_SOURCES_LIST` entry needed).
- **Commit:** `4e3058adc5`

**2. [Rule 3 - Blocking] Transitional bool& guard overload to keep libVIEW compiling**
- **Found during:** Task 3 verification (post Task 1)
- **Issue:** Task 1's `int&`-only guard signature broke the 7 existing
  controllers that construct `ControllerApplyGuard apply_guard(applying_)`
  with a `bool applying_` member ("no known conversion from bool to
  int&"). Migrating those callers to the depth counter is 999.59-02/03
  controller-harmonization work, explicitly out of scope here ("zero
  behavior change to existing controllers").
- **Fix:** Retained an explicit `ControllerApplyGuard(bool&)` overload
  alongside the canonical nest-aware `ControllerApplyGuard(int&)`. The
  bool form preserves the legacy one-shot set/clear; documented
  `@deprecated` transitional shim, removed once the last controller is cut
  over in 999.59-02/03.
- **Commit:** `7799c8a5e9`

### Plan-owned harness edit (not a deviation)

`test/contract/contractTestHarness.h` was modified to `#include
controller.h`. The plan explicitly grants this file for the feature macro
(frontmatter `key_links: from contractTestHarness.h → to controller.h via
BALL_VIEW_CONTROLLER_APPLY_RETURNS_BOOL`). Because this plan does NOT make
the controllers inherit the base, the harness include is the only
mechanism that makes the macro reach the harness's `#if defined(...)` this
phase.

## Open Item for 999.59-02/03 (and orchestrator awareness)

The `contract-tests` build is intentionally **red** from this commit until
all nine controllers reach `bool apply()` in 999.59-02/03, because the
single coarse `BALL_VIEW_CONTROLLER_APPLY_RETURNS_BOOL` macro flips all
nine fixtures live at once (the in-tree harness has no per-controller flip
granularity). The OVERVIEW's "each cut-over flips its fixture green
incrementally" intent cannot be fully incremental with the current
all-or-nothing switch. Options for 02/03 if an incremental green is
desired: (a) land 02 and 03 together so all nine compile before merging
the macro to the integration branch, or (b) introduce a per-controller
`#if`-guard in each fixture's `#else` block. This summary surfaces the
tension; resolving the flip granularity is a 02/03 / 999.60 concern, not
foundation scope. libVIEW / BALLView builds are unaffected.
