  <files>include/BALL/VIEW/KERNEL/controllers/controllerApplyGuard.h, include/BALL/VIEW/KERNEL/controllers/applyPayload.h</files>
  <action>

nest-aware RAII depth counter, per ARCHITECTURE-CONTRACT.md §4. Keep the

(the existing harness includes it directly). Change the guarded state from
`bool&` to `int&` (a depth counter): the constructor increments, the
destructor decrements. Add a static/inline helper or convention so a caller
checks "am I already applying?" by testing depth > 0 BEFORE constructing the
guard (the §2 body does `if (applying_depth_ > 0) return false;` then

ctor / assignment. Document GUI-thread-only semantics in the doc-comment:
the guard is a nest-aware flag, NOT a mutex; thread-safety is explicitly not
required because apply() runs only on the GUI thread (§4 Codex HIGH #6).
Keep a compatibility note that any controller calling a helper that re-enters
apply() at a deeper level is detected via depth, not corrupted.

Create `applyPayload.h` (NEW) declaring `struct ApplyPayload` in
`namespace BALL::VIEW` per §2: fields `String command_id;`,
`String before;`, `String after;` (string snapshots — cheap to compare and
print, matching the harness OwnerSnapshot string form), `void* target;` (or
`QObject* target;` — the mutated owner, non-owning), and
`PreciseTime t_us;` or a plain integer microsecond timestamp. Make it a
plain copy-constructible aggregate (no QObject base) so v2.0 can store it on
an undo stack. Header-only. Follow conventions: modeline, include guard
`BALL_VIEW_KERNEL_CONTROLLERS_APPLYPAYLOAD_H`, BALL String type from
`<BALL/DATATYPE/string.h>`.

Do NOT inline any apply() body here — these are pure type definitions.
