# 999.59-05 — ApplyPayload capture consolidation + ControllerJob scaffold

## What landed

### Task 1 — recordIntent_ / reversible-intent capture (§2 step 7 / §2d)
The per-apply() capture was **already complete and uniform** from 02/03: all 9
`apply()` bodies populate an `ApplyPayload` (before/after snapshots, unique
dotted `command_id`, target, timestamp) and call `recordIntent_(payload)`.

This plan **consolidated** the storage onto the base `Controller`:
- `controller.h`: added protected `recordIntent_(const ApplyPayload&)`,
  protected accessor `const ApplyPayload& lastIntent_() const`, and the
  capture-only member `ApplyPayload last_payload_`.
- `controller.C`: base definitions (store last payload; no UndoStack push, no
  UI consumer — v2.0 scope).
- Removed the 9 byte-identical per-controller `recordIntent_` definitions,
  header decls, and `last_payload_` members. All 9 now inherit the base; each
  still calls `recordIntent_(payload)` in apply() (verified: 0 per-controller
  copies remain, 9/9 still capture). `command_id`s remain unique per
  Controller × operation.

### Task 2 — ControllerJob async scaffold (§6)
- NEW `controllerJob.h/.C`: `class BALL_VIEW_EXPORT ControllerJob : QObject`
  (`Q_OBJECT`) with signals `started()`, `progress(int)`, `finished(const
  ApplyPayload&)`, and a `start()` that emits `started()` then queues
  `finished()` via `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` — the
  worker→GUI re-entry path a real job uses. NO concrete job ships.
- Base `Controller` gained the queued-result plumbing: `kickJob_(ControllerJob&)`
  connects `finished()` → `applyResult_()` with `Qt::QueuedConnection`, starts
  the job, and returns false (nothing mutated synchronously); `applyResult_()`
  is a virtual GUI-thread handler (base no-op) a subclass overrides to run the
  §2 apply() contract under the guard.
- Wired `controllers/controllerJob.C` into `source/VIEW/KERNEL/sources.cmake`
  (Q_OBJECT header MOC'd automatically as the companion to the listed .C).
