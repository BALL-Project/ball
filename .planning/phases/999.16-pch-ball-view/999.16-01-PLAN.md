**BALL target wiring (CMakeLists.txt):**
- Line 598: `ADD_LIBRARY(BALL SHARED ${BALL_sources} ${BALL_headers})` — the canonical BALL library target. `CUDA_ADD_LIBRARY(BALL ...)` at line 593 is the CUDA-enabled branch (gated on `BALL_HAS_CUDA`); PCH wiring must follow whichever branch was taken. **VIEW target wiring:**

**ccache wiring (.github/workflows/ci.yml):**
- Line 88-95: `Cache ccache` step uses `actions/cache@v5` with per-OS `ccache_dir` matrix entries (macOS `~/Library/Caches/ccache`, Linux `~/.cache/ccache`, Windows `C:\Users\runneradmin\AppData\Local\ccache`).
- Lines 85-86: comment notes "configure steps below wire CMAKE_<LANG>_COMPILER_LAUNCHER=ccache."
- NO existing `ccache --set-config sloppiness=` invocation. The sloppiness setting needs to be added — either as a step after `Cache ccache` restore (one `ccache --set-config sloppiness=pch_defines,time_macros,include_file_mtime` line per platform), OR via the `CCACHE_SLOPPINESS` environment variable in the matrix block. Environment-variable form is cleaner (single source of truth, no per-platform shell quoting); recommended.

**Header-set audit method (per ROADMAP §999.16 scope step 1):**
- `grep -h '#include' source/{KERNEL,CONCEPT,COMMON,DATATYPE,MATHS,SYSTEM}/*.C 2>/dev/null | sort | uniq -c | sort -rn | head -25` produces the top-25 most-included headers in BALL core modules.
- Same exercise for VIEW: `grep -h '#include' source/VIEW/**/*.C | sort | uniq -c | sort -rn | head -25`.
- Top ~10-20 from each are the PCH candidates. Quality criteria: heavy/template-dense (Qt, Boost, Eigen, BALL/CONCEPT, BALL/COMMON); included by ≥50% of TUs in the audit; stable (not currently churning).

**ccache sloppiness rationale (ccache 4.x with PCH):**
- `pch_defines` — accept cache hits when the macro state at PCH creation matches; without this, every TU that uses the PCH must have identical macro state including `__DATE__` / `__TIME__`-style variants.
- `time_macros` — accept hits when the only difference is `__DATE__` / `__TIME__` / `__TIMESTAMP__`.
- `include_file_mtime` — accept hits based on content hash rather than mtime; CI runners reset mtimes on every checkout so this is essential.
- Without these three, PCH-enabled builds frequently bust ccache hits silently — the build still works, just slower than non-PCH because of double-compile.

**Acceptance thresholds (per ROADMAP §999.16):**
- Cold-cache Windows Build: ≥15% reduction (current cold baseline ~85 min per Phase 999.2 SUMMARY).
- Cold-cache Linux + macOS Build: ≥10% reduction.
- Warm-cache build: should not regress (ccache should still hit; sloppiness ensures it).
- If reduction is smaller than threshold: investigate header set (maybe top-25 was wrong; iterate). If reduction is negative: revert and document why.
