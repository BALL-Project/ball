# Phase 999.50: Code Review Report

**Reviewed:** 2026-05-21
**Depth:** standard
**Files Reviewed:** 3
**Status:** issues_found

## Summary

Phase 999.50 replaces the boost::serialization-based Ward cluster-tree archive
with a hand-rolled magic+version-headed binary/text format
(`poseClusteringSerialization.C`) and adds ccache restore/save steps plus a new
job-level `env` block to `release.yml`. The compile-time motivation is sound and
the happy path round-trips correctly under the existing test fixtures.

The dominant defect class is **missing defensive validation on the read path**.
`deserializeWardClusterTree` trusts every count word (`order`, `num_poses`,
`num_edges`) it reads and never checks stream state between reads. A truncated,
EOF-mid-record, or malformed stream does NOT fail loudly via `BALL::Exception` as
the task brief requires — instead it either silently builds a corrupt/partial
tree or attempts an unbounded `add_vertex` / pose-insert loop driven by an
attacker- or corruption-controlled 32/64-bit count. This is the one Critical
finding (CR-01). Several portability/fidelity hazards intrinsic to hand-rolled
serialization (host-byte-order binary, non-fixed-width integer types, default
6-significant-digit text float precision) are latent today on the all-little-endian
CI fleet but are real WARNINGs.

The `release.yml` changes are mechanically correct: the per-OS ccache paths and
the `CCACHE_SLOPPINESS`/`CCACHE_EXTRAFILES` env block match `ci.yml` verbatim,
and the restore/save split mirrors the existing vcpkg cache pattern. One WARNING
(WR-05) concerns the `cache-hit` save gate being effectively a no-op given the
SHA-pinned key, and there are minor INFO items.

## Critical Issues

### CR-01: Read path does not validate counts or stream state — malformed/truncated stream silently corrupts or hangs instead of throwing

**File:** `source/DOCKING/COMMON/poseClusteringSerialization.C:170-200` (binary), `221-248` (text)

**Issue:**
After the magic+version header is validated, every subsequent value is read with
zero validation:

- `order`, `num_poses`, and `num_edges` are `Size` (`BALL_SIZE_TYPE`, an unsigned
  type). They are read raw and immediately drive loops:
  `for (Size v = 0; v < order; ++v) { boost::add_vertex(...); }`,
  `for (Size p = 0; p < num_poses; ++p) { ... props.poses.insert(pose); }`,
  `for (Size i = 0; i < num_edges; ++i) { ... }`.
  A corrupt or hostile stream supplying a huge count (e.g. `0xFFFFFFFF...`) causes
  an effectively unbounded `add_vertex`/insert loop — memory exhaustion / hang —
  not a loud `BALL::Exception`. The brief explicitly requires "absurd vertex/edge
  counts ... fail loudly via BALL::Exception rather than silently ... over-allocating.
  Check counts are validated before resize/loop." That validation is absent.

- The stream state is never re-checked after the header. In the binary path,
  `readBinary_` (`in.read`) on a truncated stream leaves `value` partially/zero
  filled and sets `failbit`, but the code reads `order`, then loops reading vertex
  records, then `num_edges`, then edges — all without ever testing `in`. A stream
  that EOFs mid-record produces a **silently truncated tree** with default-zero
  trailing fields. In the text path, `in >> order >> root` / `in >> num_poses`
  etc. on malformed/short input likewise sets `failbit` and yields a partial tree
  with no exception.

- Edge indices `parent`/`child` are passed straight to
  `boost::add_edge(parent, child, cluster_tree_)` with no check that they are
  `< order`. For a `vecS` vertex container, `add_edge` with an out-of-range vertex
  descriptor is undefined behavior / silent vector growth, corrupting the tree
  invariant ("indices map directly onto vertex descriptors").

Net effect: only the magic/version mismatch is caught loudly. Every other class
of corruption (truncation, absurd counts, out-of-range edges) is handled silently
or unsafely. Because these trees are read from on-disk files produced by external
tooling (`ExtractClustersFromWardTree.C`, `DockPoseClustering.C`), this is a
correctness-and-robustness defect on untrusted input.

**Fix:**
Validate stream state after the header and after each count, and bound each count
before looping. Suggested pattern (binary shown; mirror in text path):

```cpp
// After reading each count, fail loudly on a bad stream.
readBinary_(in, order);
readBinary_(in, root);
if (!in)
{
  throw Exception::InvalidFormat(__FILE__, __LINE__,
    "PoseClustering Ward tree: truncated header (could not read order/root).");
}

for (Size v = 0; v < order; ++v)
{
  ClusterTreeNode node = boost::add_vertex(cluster_tree_);
  ClusterProperties& props = cluster_tree_[node];

  Size num_poses = 0;
  readBinary_(in, num_poses);
  if (!in)
  {
    throw Exception::InvalidFormat(__FILE__, __LINE__,
      "PoseClustering Ward tree: truncated stream while reading vertex record.");
  }
  // Optional sanity bound: pose count cannot exceed total poses in tree.
  for (Size p = 0; p < num_poses; ++p)
  {
    Index pose = 0;
    readBinary_(in, pose);
    props.poses.insert(pose);
  }
  readBinary_(in, props.size);
  readBinary_(in, props.merged_at);
  if (!in)
  {
    throw Exception::InvalidFormat(__FILE__, __LINE__,
      "PoseClustering Ward tree: truncated stream in vertex payload.");
  }
}

Size num_edges = 0;
readBinary_(in, num_edges);
if (!in)
{
  throw Exception::InvalidFormat(__FILE__, __LINE__,
    "PoseClustering Ward tree: truncated stream before edge list.");
}
for (Size i = 0; i < num_edges; ++i)
{
  unsigned int parent = 0, child = 0;
  readBinary_(in, parent);
  readBinary_(in, child);
  if (!in || parent >= order || child >= order)
  {
    throw Exception::InvalidFormat(__FILE__, __LINE__,
      "PoseClustering Ward tree: edge references out-of-range vertex or stream truncated.");
  }
  boost::add_edge(parent, child, cluster_tree_);
}
// Final sanity check.
if (!in && !in.eof())
{
  throw Exception::InvalidFormat(__FILE__, __LINE__,
    "PoseClustering Ward tree: stream error during deserialization.");
}
```

At minimum, add a stream-state check after every block of reads and an
`order`-bounds check on edge endpoints. Counts that exceed a defensible cap (e.g.
`num_poses > getNumberOfPoses()` once known, or edges `> order`) should throw.

## Warnings

### WR-01: BINARY format is host-byte-order and not endianness-defined (latent cross-arch portability hazard)

**File:** `source/DOCKING/COMMON/poseClusteringSerialization.C:50-62, 73-105`

**Issue:**
`writeBinary_` / `readBinary_` do `out.write(reinterpret_cast<const char*>(&value), sizeof(T))`
in raw host byte order (the header comment even labels it "fixed-width, host byte
order"). A binary `.ward`/`.dat` written on a little-endian host will be silently
mis-decoded on a big-endian host: the magic string compares byte-for-byte and
passes, the version word is byte-swapped (likely tripping the version check, or
worse, not), and all counts/indices/floats are garbage. All three CI runners
(macОS-arm64, ubuntu x64/arm64, windows-x64) are little-endian, so tri-OS CI will
not exercise this — but it is a real latent portability defect for a persisted
on-disk format, and the comment overstates safety by calling it "fixed-width."

**Fix:**
Either (a) document explicitly in the on-disk format comment and the public
Doxygen that the BINARY variant is little-endian-only and not portable across
endianness, or (b) serialize via fixed-width little-endian helpers (e.g. write
each integer byte-by-byte LE, and floats via a `uint32_t` bit-cast written LE) so
the format is architecture-independent. Given BALL targets only LE platforms
today, (a) is acceptable as a minimum; (b) is the correct long-term fix for a
persisted format.

### WR-02: BINARY format uses platform-variable integer widths, not fixed-width types

**File:** `source/DOCKING/COMMON/poseClusteringSerialization.C:76-104, 170-199`

**Issue:**
`order`/`num_poses`/`num_edges` are `Size` (`BALL_SIZE_TYPE`), poses are `Index`
(`BALL_INDEX_TYPE`), and `props.size` is `Size` — all configured macros whose
underlying width is set at CMake-configure time and can differ across builds/
platforms (e.g. 32- vs 64-bit). `sizeof(T)` therefore varies, so a binary file
written by one build is not guaranteed readable by another even on the same
endianness. The comment claims "fixed-width," which is inaccurate. This compounds
WR-01: there is no width tag in the header, so a width mismatch is undetectable
and decodes as silent corruption.

**Fix:**
Serialize the binary variant using explicit fixed-width types (`uint32_t` /
`int32_t` / `uint64_t`), casting on write and validating range on read, rather
than `Size`/`Index`/`unsigned int` whose widths are configuration-dependent.
Alternatively, embed the byte widths in the header and validate them on read so a
mismatch throws `InvalidFormat` instead of corrupting silently.

### WR-03: TEXT variant writes `merged_at` at default 6-significant-digit precision — lossy float round-trip that can flip threshold-boundary cluster counts

**File:** `source/DOCKING/COMMON/poseClusteringSerialization.C:123` (write), `237` (read)

**Issue:**
`out << ... << props.merged_at` uses the default stream precision (6 significant
digits). A 32-bit `float` requires `std::numeric_limits<float>::max_digits10 == 9`
significant decimal digits for an exact round-trip. The text variant therefore
truncates `merged_at` to 6 sig-figs on write and cannot recover the original bits
on read.

This is load-bearing, not cosmetic: `extractClustersForThreshold` compares
`cluster_tree_[...].merged_at < threshold` and pushes `merged_at` directly into
`cluster_scores_` (`poseClustering.C:151,154,172,176`), and the tests assert exact
cluster counts at thresholds (`extractClustersForThreshold(0.5)` → 6 clusters) and
scores like `1.09569e-05` and `2.34918` (`PoseClustering_test3.C:328-391`). A
`merged_at` value sitting just below a threshold can round up across it after a
6-digit text round-trip, changing the partition. The current fixture happens to
survive because its values are well-separated relative to the test PRECISION
tolerances, but the format is one regenerated fixture away from a spurious
count/score change, and the TEXT variant is the default (`binary = false`).

**Fix:**
Set max-fidelity precision before writing floats in the text path:

```cpp
#include <limits>
// ...
out << ' ' << props.size << ' ';
const std::streamsize old_prec = out.precision(std::numeric_limits<float>::max_digits10);
out << props.merged_at << '\n';
out.precision(old_prec);
```

(Or set `out << std::setprecision(std::numeric_limits<float>::max_digits10)` once
for the whole text payload. `props.size` and indices are integral and unaffected.)

### WR-04: No stream-failure check after reading the text version token — a header read failure can be misreported

**File:** `source/DOCKING/COMMON/poseClusteringSerialization.C:207-219`

**Issue:**
In the text path, `in >> magic >> version` is followed by
`if (!in || magic != ...)` which correctly catches a failed magic read, but the
*version* check `if (version != POSECLUSTERING_WARD_VERSION)` runs even when
extraction of `version` failed for a reason other than what `!in` caught earlier
(e.g. the magic parsed but `version` extraction set `failbit` because the token
was non-numeric). In that case `version` retains its initialized `0`, which
differs from `1`, so it happens to throw the "unsupported version 0" message
rather than a clearer truncation/parse error. Functionally it still throws, but
the diagnostic is misleading. This is a minor robustness/diagnostics gap that
overlaps with CR-01 (the same missing post-read `!in` discipline).

**Fix:**
Check `!in` immediately after `in >> magic >> version` and throw a
truncation/parse `InvalidFormat` before interpreting `version`, so a malformed
header is reported as such rather than as an "unsupported version" mismatch.

### WR-05: `release.yml` ccache save gate `cache-hit != 'true'` is a near-permanent no-op given the SHA-pinned key

**File:** `.github/workflows/release.yml:210, 246, 247` (macOS save gate; mirrored Linux ~591, Windows ~999)

**Issue:**
The restore key is `ccache-${{ matrix.os }}-pch-v2-${{ github.sha }}` (exact SHA).
`steps.ccache-*.outputs.cache-hit` is `'true'` only on an *exact-key* hit. On a
release tag, the cache is virtually always populated via the `restore-keys`
prefix fallback (a prior CI run on a *different* SHA), which yields
`cache-hit == 'false'` (a partial/restore-key hit, not an exact hit). So the save
step runs on essentially every release build and re-uploads the warmed cache under
the new SHA key. That is not incorrect — it is in fact the desired warm-forward
behavior — but the inline comment ("an exact-key hit doesn't redundantly
re-upload an unchanged cache") implies dedup that almost never triggers here,
because release tags rarely share a SHA with a prior *release* run that already
saved this exact key. The practical risk is redundant cache uploads and, over
many tags, cache-store churn/eviction pressure on the shared Actions cache.

**Fix:**
This is acceptable as-is (it mirrors `ci.yml`/vcpkg), but either tighten the
comment to state that the gate only suppresses re-upload on a same-SHA re-run
(rare for releases), or consider whether release builds should save at all given
`ci.yml` already warms the per-SHA cache. No code change strictly required;
flag for awareness so the comment does not mislead future maintainers.

## Info

### IN-01: Public Doxygen comments still say "boost::serialize format" after the boost dependency was removed

**File:** `include/BALL/DOCKING/COMMON/poseClustering.h:478-484`

**Issue:**
`serializeWardClusterTree` / `deserializeWardClusterTree` are documented as
"Export/Import the cluster tree to/from boost::serialize format." The whole point
of this phase is that the format is no longer boost::serialization — it is the
hand-rolled BALLWARD magic+version format, and old boost files are explicitly
rejected. The public API docs now actively misdescribe the format and omit the
`binary` parameter and the format-break behavior.

**Fix:**
Update the Doxygen to describe the BALLWARD hand-rolled format, document the
`binary` parameter (`@param binary` — true = raw binary variant, false = ASCII
text), and note (`@throw Exception::InvalidFormat`) that non-BALLWARD / wrong-version
streams are rejected. Reference the format-break note already in the `.C` header
comment and RELEASE-NOTES.

### IN-02: `magic[16]` buffer is read but never NUL-terminated — relies entirely on length-bounded std::string comparison

**File:** `source/DOCKING/COMMON/poseClusteringSerialization.C:151-154`

**Issue:**
`char magic[16]; in.read(magic, POSECLUSTERING_WARD_MAGIC_LEN);` reads exactly 8
bytes into an uninitialized 16-byte buffer, then compares via
`std::string(magic, POSECLUSTERING_WARD_MAGIC_LEN)`. This is correct (the
length-bounded `std::string` ctor does not read past byte 8, so the uninitialized
tail is never observed), but the oversized-yet-unterminated buffer is a foot-gun:
any future code that treats `magic` as a C-string would read uninitialized memory.
The `16` is also a magic number with no relation to `POSECLUSTERING_WARD_MAGIC_LEN`
(8).

**Fix:**
Either size the buffer to `POSECLUSTERING_WARD_MAGIC_LEN` exactly, or
zero-initialize (`char magic[POSECLUSTERING_WARD_MAGIC_LEN] = {};`) to remove the
uninitialized tail and the unexplained `16`.

### IN-03: `serializeWardClusterTree` does not flush or check the output stream for write errors

**File:** `source/DOCKING/COMMON/poseClusteringSerialization.C:65-137`

**Issue:**
The serializer writes the whole payload but never checks `out` for failure (e.g.
disk full, broken pipe) and never throws on a bad write. A partial/failed write
silently produces a truncated file that will then fail to deserialize later
(post-CR-01 fix) far from the actual error site. Symmetry with the proposed
read-side validation argues for at least a final `if (!out) throw ...`.

**Fix:**
After emitting the payload, add `if (!out) { throw Exception::... }` so a write
failure is surfaced at serialization time rather than as a confusing deserialize
failure later.
