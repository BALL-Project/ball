# Phase 999.65 Plan 01: Headless RepresentationBuilder Extraction Summary

Created a dialog-free `RepresentationBuilder` (+ `RepresentationSpec` value object) in the MODELS layer that reproduces `DisplayProperties::createRepresentation`'s orchestration through the 999.57 `ModelProcessorFactory` / `ColorProcessorFactory`, plus a static project-restore `parseDataString` helper matching the `Representation::toString` 6-field round-trip — a pure addition with no consumer repointed.

## What Was Built

**`include/BALL/VIEW/MODELS/representationBuilder.h`** (Task 1)
- `struct RepresentationSpec` — the headless replacement for every dialog widget read: `model_type` (default `MODEL_STICK`, the fresh-panel default), `coloring_method` (`COLORING_ELEMENT`), `drawing_mode` (`DRAWING_MODE_SOLID`), `drawing_precision` (`DRAWING_PRECISION_HIGH`), `surface_drawing_precision` + `use_custom_surface_precision` (the custom-vs-presets branch), `transparency`, `custom_color`, `model_update_enabled` / `coloring_update_enabled` (default true), plus embedded `ModelProcessorParams model_params` and `ColoringOverrides coloring_overrides`. ## parseDataString Field Offsets

Layout (matches `Representation::toString`, representation.C:551-595):
```
<system>;<model> <mode> <drawing_prec> <surf_prec> <coloring> <transparency> [<id,id,...>]|<color>|<H?><\named*props>
```
1. Split on `;` → `[0]` = `system_index`, `[1]` = settings + ids + color + props (`< 2` tokens → fail).
2. Split `[1]` on `[]` → `[0]` settings, `[1]` id list, `[2]` tail (`< 3` tokens → fail); `[2].hasSubstring("|H")` → `hidden`.
3. Split id list on `,` → `composite_indices` (empty → fail).
4. `|`-split the settings token → `[1]` = `custom_color` (the `|color|` block).
5. Whitespace-split the settings token → 6 fields: `model_type`, `drawing_mode`, `drawing_precision`, `surface_drawing_precision`, `coloring_method`, `transparency` (`< 6` fields OR non-muteable model → fail).
6. Split settings token on `\` then `*` → `named_property_blocks` (raw base64, undecoded — Plan 03 replays).

These offsets are byte-identical to the legacy parse so Plan 03's restore is unchanged.

## Messaging Strategy Chosen

**Strategy A (access-adapted) — a `Notifier` callback, not a `ConnectionObject&`.** The plan offered Strategy A (notifier param) or B (builder derives from ConnectionObject) and preferred A. The literal Strategy A signature (`ConnectionObject& notifier`) is unusable: `ConnectionObject::notify_` is **protected** (connectionObject.h:183), so the builder cannot call it on a foreign `ConnectionObject&`. The `RepresentationBuilder::Notifier` abstract interface preserves A's intent — the builder is pure logic with zero ConnectionObject lifecycle, the caller (DisplayProperties in Plan 02, RepresentationManager in Plan 03 — both ConnectionObjects) supplies a one-method adapter forwarding to its own `notify_`. The same message sequence fires: `ADD_TO_GEOMETRIC_CONTROL`, then `CENTER_CAMERA` when fewer than two representations exist.
