default-representation creation (displayProperties.C:319-335) — off `DisplayProperties::createRepresentation`
and onto the headless `RepresentationBuilder` (Plan 01). This is the project's CORE value path: loading
a molecule must still auto-create the same default representation and render it.

Behavior-preserving mechanism: add a `DisplayProperties::buildCurrentSpec()` that snapshots the dialog's
CURRENT widget state into a `RepresentationSpec` (the same state `applyModelSettings_` /
`applyColoringSettings_` read today), then the NEW_MOLECULE branch calls
`RepresentationBuilder::createRepresentation(spec, clist, *getMainControl(), *this)`. The dialog stays
the SOURCE of the default settings (its persisted/last-used widget values, default MODEL_STICK); only the
ORCHESTRATION moves to the headless builder. This mirrors the 999.57 `buildColoringOverrides()` recipe.

orchestration. One consumer at a time, GUI-verified before the next. After Plan 03 the dialog's
createRepresentation is fully dead.

Output: onNotify NEW_MOLECULE builds via RepresentationBuilder; buildCurrentSpec added; GUI UAT confirms
molecule-load renders identically; BALLView links clean BALL_UI_V2=ON.
