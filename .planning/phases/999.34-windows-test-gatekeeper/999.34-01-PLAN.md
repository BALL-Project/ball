# Phase 999.34 Plan 01: Windows test gatekeeper bring-up

## Objective

Wire `ctest` into the Windows CI matrix and release pipeline so the BALL test
suite is a first-class release gatekeeper on `windows-x64`, at parity with the
macOS arm64 + Linux gatekeepers landed in TEST-CLOSE-02 (Phase 9). Today the
Windows build job builds BALL + VIEW + BALLView but does NOT run any tests;
the BALLView Windows binary ships without unit-test verification.

### Why Windows was deferred (PHASE-9-BASELINE.md:84)

vcpkg + MSVC test integration was non-trivial vs. the macOS/Linux gatekeeper
flip: BALL.dll lives in `build\ci-windows\bin\` while the test binaries land in
`build\ci-windows\bin\TEST\`. Windows DLL search order finds the EXE's own dir
first, then PATH — but the test EXEs are in a subdirectory so PATH must be
explicitly extended. Qt 6 DLLs live in `build\ci-windows\vcpkg_installed\x64-windows-release\bin\`
and must ALSO be on PATH for the VIEW_TESTS (which link the Qt-dependent VIEW
library). Triage decided this was worth its own slot, not bundled into TEST-CLOSE-02.

### Quarantine inheritance from macOS/Linux

Per 09-TRIAGE.md decision table:
- `AssignBondOrderProcessor_test2` — currently `WILL_FAIL TRUE` only on Apple
  Silicon ARM (FP fine-penalty bug); Linux x64 passes cleanly. MSVC x64 uses the
  Intel x87/SSE FP path, so should match Linux x64 behavior → **does NOT need
  the WILL_FAIL extension to Windows.** Leave the gate Apple-only.
- `AmberFF_test` — ARM-tolerance fix landed in 41bfae621 (loosened precision);
  the test passes on Intel paths (Linux GCC, MSVC x64). No Windows-specific
  quarantine needed.
- `PeptideCapProcessor_test`, `Peptides_test`, `RotamerLibrary_test` — all 3
  are platform-independent OOS PR-merge data regressions (45dce6971 PRO.db).
  They're already unconditionally `WILL_FAIL TRUE` and will be expected-fail on
  Windows the same way they are on macOS/Linux.

### Windows-specific test concerns

`Directory_test` — proven false-alarm on macOS arm64 (09-TRIAGE.md row 1) under
the main-tree build with `BALL_DATA_PATH` set; uses `FileSystem::canonizePath()`
to handle symlinks portably. On Windows the path separator (`\` vs `/`) is also
normalized by `FileSystem`, so the test should pass — **but we cannot prove
this without running it.** The first Windows CI run is the baseline; if
Directory_test or any other test fails Windows-specifically, Rule 1 / Rule 2
will apply (auto-quarantine with a `Phase 999.35-style` backlog stub for the
fix, mirror the macOS pattern).

## Tasks

### Task 1: Wire Windows test build + run into ci.yml (`type=auto`)

Add three new steps to the Windows-x64 branch of the ci.yml build matrix, after
the existing "Upload .ninja_log artifact (windows-x64)" step (line ~934) so it
sits at the same logical position as the macOS/Linux gatekeepers (after build,
before render-smoke). Steps:

1. **"Build BALL test suite (Windows — Phase 9 gatekeeper, blocking)"** —
   `if: matrix.os == 'windows-x64'`, `continue-on-error: false`,
   `timeout-minutes: 45`, pwsh shell, builds `build_tests` target with
   `cmake --build build\ci-windows --target build_tests --config Release`.

2. **"Run BALL test suite (Windows — Phase 9 gatekeeper, blocking)"** —
   `if: matrix.os == 'windows-x64'`, `continue-on-error: false`,
   `timeout-minutes: 60`, pwsh shell, `cd build\ci-windows`, sets:
   - `$env:BALL_DATA_PATH = "${{ github.workspace }}\data"`
   - `$env:PATH = "$pwd\bin;$pwd\vcpkg_installed\x64-windows-release\bin;$env:PATH"`
     so test EXEs find BALL.dll + VIEW.dll + Qt6Core.dll + Boost DLLs.
   - Runs `ctest --output-on-failure --timeout 120 --output-junit ${{ github.workspace }}\ball-tests-windows-ui_v2_${{ matrix.ui_v2 }}.xml`

3. **"Upload test results (Windows)"** — `if: always() && matrix.os == 'windows-x64'`,
   uploads the JUnit XML via `actions/upload-artifact@v6` with name
   `ball-tests-windows-ui_v2_${{ matrix.ui_v2 }}-${{ github.run_id }}` so the
   test-report job's `pattern: ball-tests-*` glob picks it up. 30-day retention.

Also update the `# Windows test gatekeeper deferred to Phase 999.34.` comments
(2 occurrences in ci.yml, lines ~451 and ~636) to read
`# Windows test gatekeeper landed in Phase 999.34.`.

**Verify:** `head -5 .github/workflows/ci.yml | grep -c name:` parses YAML
implicitly; explicit verification is the next CI run.
