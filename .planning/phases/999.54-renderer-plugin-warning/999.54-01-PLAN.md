<grounding>
GitHub #501 (reporter): "When no renderer plugins are found, everything starts fine but
nothing is of course displayed and the user has no clue as to what is happening until he
checks the list of loaded plugins and sees that there are actually no renderers present.
Having default renderer will help but with the plugin systems it can always happen than no
plugin will be found for whatever reason."

How renderers actually register in this tree (grep-verified, NOT a runtime QPluginLoader path
for renderers): renderers are constructed by `RendererFactory::makeRenderer(...)` and pushed
into `Scene::renderers_` (a `std::vector<boost::shared_ptr<RenderSetup>>`) inside
`Scene::registerRenderers_()` (source/VIEW/WIDGETS/scene.C ~line 206). That vector is the
single place where the live "renderer count" is known at startup. An empty `renderers_` is the
exact in-tree manifestation of issue #501's "no renderers present" condition — the Scene then
has nothing to render into.

Construction order matters (verified at scene.C ~line 158-178):
  1. Scene ctor body runs `registerRenderers_();`  (line ~166)
  2. THEN `registerWidget(this);` attaches the Scene to MainControl (line ~169)
So inside `registerRenderers_()`, `getMainControl()` is NOT yet valid — the status-bar API is
unsafe there. `Scene::initializeWidget(MainControl& main_control)` (scene.C ~line 1294) runs
LATER, with a valid `main_control` reference, and is the correct place to push status-bar text.
=> Split the surfacing: `Log.warn()` immediately in `registerRenderers_()`; status-bar text in
`initializeWidget()`, gated on a flag set by the guard.

Standard surfacing APIs already used in this file:
  - `BALL::Log.warn() << ... << std::endl;`  (warning log; e.g. scene.C ~line 2482, 2496)
  - `main_control.setStatusbarText(const String&, bool important=false, bool beep=false)`
    (declared include/BALL/VIEW/KERNEL/mainControl.h:672) — pass important=true so it is not
    instantly overwritten by routine status text. `Scene::setStatusbarText(...)` also exists
    but routes through getMainControl(), so call it on the `main_control` argument inside
    initializeWidget() to be safe.

Existing startup-diagnostic precedent to match in tone (DIAG-01): the single GL-capability
line emitted in `GLRenderWindow::initializeGL()` (source/VIEW/RENDERING/glRenderWindow.C ~line
123) — a deliberate, plainly-worded, non-fatal startup diagnostic. Match that spirit: one clear
sentence, no throw.
