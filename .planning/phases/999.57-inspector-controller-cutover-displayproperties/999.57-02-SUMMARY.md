# Phase 999.57 Plan 02: ColorProcessorFactory headless relocation Summary

**Relocated `createColorProcessor` + its `applySettingsTo` override-application out of the legacy ColoringSettingsDialog into a headless `ColorProcessorFactory` (pure function of a `ColoringOverrides` struct, zero Qt-widget dependency); the dialog now packs its tables/buttons/sliders into the struct and delegates — behavior byte-identical, CONFIG-01 compiled-defaults invariant preserved, render path untouched.**

## Accomplishments
- New `ColorProcessorFactory` lives in the MODELS layer with no dependency on any dialog widget — `create(ColoringMethod, const ColoringOverrides&)` reproduces the exact 13-case switch + per-method RTTI override dispatch.
- `ColoringOverrides` carries every color-table / color-button / value-slider knob the dialog previously read, each defaulted to a "no override" sentinel (empty container or `has_*` flag left false) so a default-constructed struct keeps each processor's compiled default color map — exactly the molecule-load default-rep render behavior (CONFIG-01).
- `ColoringSettingsDialog::createColorProcessor` thinned from a 66-line switch to a pack-overrides-then-delegate one-liner (`ColorProcessorFactory::create(method, buildColoringOverrides_())`); the dialog no longer constructs any per-method ColorProcessor itself.
- libVIEW builds clean on macOS-arm64 (BALL_UI_V2=ON) after each task.

## ColoringOverrides field set

- **Table groups (empty == no override):**
  - `element_colors` (vector&lt;ColorRGBA&gt;, per-index, getColors(COLORING_ELEMENT) layout)
  - `residue_name_colors` (StringHashMap&lt;ColorRGBA&gt;, residue name -> color)
  - `chain_colors`, `molecule_colors` (vector&lt;ColorRGBA&gt;)
- **Color-button / slider groups (each gated by a `has_*` presence flag):**
  - `has_residue_number_colors`: first/middle/last residue-number colors
  - `has_atom_charge_colors`: negative/neutral/positive charge colors
  - `has_atom_distance_settings`: null/max distance colors + distance + show-selected
  - `has_occupancy_colors`: minimum/maximum occupancy colors
  - `has_secondary_structure_colors`: helix/coil/strand/turn colors
  - `has_temperature_factor_settings`: unassigned/min/max colors + max value
  - `has_force_settings`: min/max colors + min/max values
  - `has_residue_type_colors`: basic/acidic/aromatic/polar/hydrophobic/other colors
- **COLORING_CUSTOM** carries no overrides (legacy applySettingsTo early-returns for CustomColorProcessor).

## Compiled-defaults invariant (CONFIG-01)

Each color processor's constructor already loads its compiled default color map (that is exactly how the dialog's `setDefaultValues_` populates its tables — by constructing dummy processors). `ColorProcessorFactory::create` therefore constructs the per-method processor (compiled defaults), then layers only the overrides whose group is present/non-empty. A default-constructed `ColoringOverrides` layers nothing, so the factory returns a compiled-default-colored processor — byte-equivalent to today's molecule-load default-rep render output, consistent with CONFIG-01's compiled-defaults-show-through principle.

## Where the factory lives

- Header: `include/BALL/VIEW/MODELS/colorProcessorFactory.h`

- The relocated `applySettingsTo` logic is a file-local anonymous-namespace helper `applyOverridesTo_(ColorProcessor&, const ColoringOverrides&)` called by `create` before returning.

## Decisions Made
- **ColoringMethod include path:** included `<BALL/VIEW/KERNEL/common.h>` (the canonical home of `enum ColoringMethod`) exactly as Plan 01's `modelProcessorFactory.h` and the sibling `colorProcessor.h` do. The factory header writes no literal Qt-widget includes (verified by the headless-invariant grep), so it is consistent with the existing MODELS layer.
- **Presence flags for always-applied groups:** the legacy `applySettingsTo` had no emptiness check for the color-button/slider groups — it always wrote their values. To both (a) preserve that always-apply behavior for the dialog and (b) honor the "empty ColoringOverrides == compiled defaults" contract that Plan 03's headless render path depends on, each such group carries a `has_*` flag. `buildColoringOverrides_()` sets them all true (dialog still always applies); a default-constructed struct leaves them false (compiled defaults).
- **applySettingsTo kept, not deleted:** grep found an external caller (`displayProperties.C:502`) outside `createColorProcessor`. Per the plan, the dialog method stays intact; Plan 03 will repoint it (mirrors Plan 01's identical applySettingsTo decision).
