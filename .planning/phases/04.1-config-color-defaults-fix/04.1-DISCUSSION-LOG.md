# Phase 4.1 — Discussion Log

Human-readable record of the `/gsd-discuss-phase 4.1` session. For agent
consumption use [`04.1-CONTEXT.md`](04.1-CONTEXT.md); this file is for audit
and retrospectives only.

## Trigger context provided by user

> "4.1 - note that the windows build of BALLView showed the old (wrong)
> colors - part of the installer bundle?"

Verified before discussion: the Windows release artifact (zip from
`release.yml`) does **not** bundle a `.BALLView` config — only `BALLView.exe`
+ Qt DLLs + `data/`. The old colors on Windows come from a pre-existing
`C:\Users\<user>\.BALLView` left over from a prior install. This is the
exact Phase 4.1 bug, observed in the wild. The user's question
"part of the installer bundle?" → **no**, but the underlying behaviour is
what Phase 4.1 fixes.

## Areas selected for discussion (multiselect)

All four phase-specific gray areas selected:
1. Fix strategy
2. Existing-config migration
3. Scope: element + residue or element only
4. Stale-detection heuristic

## Area 1 — Fix strategy

**Options presented:**
- (A) Version/checksum + fallback — small change, loses customizations on bumps.
- (B) "Reset" Preferences action only — fails criterion 1.
- (C) Diff/override persistence — structurally eliminates the bug class.
- (A + B), (C + B) combined variants.

**Selected:** **C — diff/override only** (recommended option).

**Rationale captured in CONTEXT.md D-01:** persists only user-customized
entries; compiled defaults flow through for un-touched indices; future
defaults bumps just work; bug class becomes structurally impossible.

**Derived decision (D-02):** Criterion 3's "reset from Preferences"
requirement is still in scope — implemented as a one-line button on the
Coloring Settings dialog that clears the override map.

## Area 2 — Existing-config migration

**Options presented:**
- Smart-diff against a hardcoded pre-PyMOL palette (preserves real
  customizations).
- Optimistic discard (drop legacy block entirely).
- Conservative preserve-all (defeats criterion 1 on upgrade).
- One-time prompt dialog.

**Selected:** **Optimistic discard**.

**Rationale captured in CONTEXT.md D-03:** legacy `Elements=` key on first
v1.6+ launch → silently discarded → override map starts empty → PyMOL
defaults render immediately. The Windows case the user reported is fixed
without user action.

**Tradeoff accepted:** users who manually customized element colors years
ago lose those edits on upgrade. They re-customize via the existing
Coloring Settings dialog. Cost judged acceptable vs. implementation
simplicity.

## Area 3 — Scope: element + residue or element only

**Options presented:**
- Both together (recommended; same mechanism, ~1.5x code).
- Element only — residue deferred.

Verified during scout: chain and molecule color processors are **not**
persisted in `COLORING_OPTIONS` — they don't have this bug. So the
natural maximum scope is element + residue.

**Selected:** **Element only — residue deferred**.

**Rationale captured in CONTEXT.md D-04:** keeps Phase 4.1 small. Residue
follow-up is a backlog item the planner should stub out at phase close
(suggested 999.4b / 999.5).

## Area 4 — Stale-detection heuristic

**Options presented:**
- Key-name change + defensive all-white check (recommended).
- Key-name change only.
- Schema version tag + all-white check.

**Selected:** **Key-name change + defensive all-white check**.

**Rationale captured in CONTEXT.md D-05:**
1. Format discrimination by INI key: legacy `Elements=` → discard,
   new `ElementColorOverrides=` → parse as diffs.
2. All-white sanity: any saved override equal to `#ffffff` for a
   known-colored element (C/N/O/P/S) is dropped as corruption — fallback
   to compiled default for that index. Honors criterion 2's
   "implausible all-white" case.

Final key name (`ElementColorOverrides=` proposed) is plan-time-decided.
