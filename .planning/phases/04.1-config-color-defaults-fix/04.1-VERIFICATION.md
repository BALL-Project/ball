## Critical Blocker Analysis

### CR-01: Read-path override hides rather than overrides base virtual — entire read body is dead code

**Base virtual** (`include/BALL/VIEW/KERNEL/preferencesEntry.h:108`):
```
virtual void readPreferenceEntries(const INIFile& inifile);
```

**Derived declaration** (`include/BALL/VIEW/DIALOGS/coloringSettingsDialog.h:75`):
```
virtual void readPreferenceEntries(INIFile& inifile);
```

`const INIFile&` and `INIFile&` are distinct parameter types in C++. The derived function does NOT override the base virtual — it occupies a new vtable slot reachable only by calling through a `ColoringSettingsDialog*` directly. No `override` specifier was used, so the compiler did not flag the mismatch.

**Production call chain:**

```
MainControl::fetchPreferences(INIFile&)           mainControl.C:1057
  -> preferences_dialog_->fetchPreferences(...)   preferences.C:151
       -> for each PreferencesEntry* entry:
            (**it).readPreferenceEntries(inifile)  preferences.C:174
```

At line 174, `*it` is typed `PreferencesEntry&`. C++ overload resolution looks up `readPreferenceEntries` in the base class scope, finds `const INIFile&` virtual, dispatches it. The base body registers/restores widgets registered via `registerWidgets_()`. The `ColoringSettingsDialog`-specific body (legacy-discard, override-parse, all-white sanity check) is never reached.

**Observable consequence:** The phase goal — "Users see compiled defaults for any color they have not explicitly customized" — is met only because `setDefaultValues_()` runs unconditionally in the constructor. This is the pre-Phase-4.1 behavior, unchanged. The phase adds no new startup behavior. The legacy `Elements=` line remains in `~/.BALLView` permanently; the log line "dropping legacy Elements= block" is never emitted; any `ElementColorOverrides=` written by the new write path is silently ignored on the next launch; user overrides from mid-session writes are lost.

**The SUMMARY.md claim "launching BALLView with a pre-existing ~/.BALLView containing legacy Elements= ... renders carbon as PyMOL green after the read path runs" is incorrect.** The read path does not run. Carbon is PyMOL green because setDefaultValues_() pre-loaded it. The legacy Elements= line is still in the file.

**Fix required:** Change derived signature to match base:
- `coloringSettingsDialog.h:75`: `virtual void readPreferenceEntries(const INIFile& inifile);`
- `coloringSettingsDialog.C:229`: `void ColoringSettingsDialog::readPreferenceEntries(const INIFile& inifile)`
- The body calls `inifile.deleteLine(it)` which requires a non-const reference. Resolution: `const_cast<INIFile&>(inifile).deleteLine(it)` at mutation sites, or change the base virtual to take `INIFile&` (larger impact — 6+ subclass declarations and 3+ call sites must change).
- Add `override` to all derived virtual declarations to prevent recurrence.

### CR-02: getSectionLastLine loops skip the last line — deleteLine never fires when target is the last entry

**Source** (`source/FORMAT/INIFile.C:411-421`):
```cpp
INIFile::LineIterator INIFile::getSectionLastLine(const String& section_name)
{
    SectionIterator sit = getSection(section_name);
    list<String>::iterator line_it(sit->lines_.end());
    if (sit->lines_.size() > 0) line_it--;          // points to LAST ACTUAL line
    return LineIterator(sections_, getSection(section_name), line_it);
}
```

`getSectionLastLine` returns an iterator to the LAST line, not past-the-end.

**Loop pattern in coloringSettingsDialog.C (lines 242-251 and 203-211):**
```cpp
INIFile::LineIterator it  = inifile.getSectionFirstLine("COLORING_OPTIONS");
INIFile::LineIterator end = inifile.getSectionLastLine("COLORING_OPTIONS");
for (; it != end; ++it)
{
    if ((*it).hasPrefix("Elements=")) { inifile.deleteLine(it); break; }
}
```

When `it == end` initially (single-entry section) or when the target key is at the last position, the loop body never executes. The `hasEntry()` guard fires (returns true), the log fires, but `deleteLine` is never called. The line survives.

**Realistic case:** A pre-Phase-4.1 `~/.BALLView` has `[COLORING_OPTIONS]` with `Elements=` last (after `ResidueNames=` and `ResidueNameColors=`). After Phase 4.1 writes the file on quit, the last line in `[COLORING_OPTIONS]` will be `ElementColorOverrides=` (the only key the write path appends). Both deletion scenarios fail.

**Fix required:** Use the past-the-end idiom in both loops:
```cpp
INIFile::LineIterator end = inifile.getSectionLastLine("COLORING_OPTIONS").getSectionNextLine();
```
This is the documented idiom at `source/DOCKING/COMMON/dockingAlgorithm.C:103`.

**Note:** CR-02 is currently latent due to CR-01 (the loops are inside the unreachable read path), but affects the write path's empty-overrides cleanup branch (lines 203-211) which IS reachable. The empty-overrides cleanup branch has the same off-by-one: if `ElementColorOverrides=` is the last line of `[COLORING_OPTIONS]`, the cleanup scan will not delete it.

### CR-03: Unguarded parse throws instead of falling back — contradicts CONFIG-01 criterion 2

**Source** (`coloringSettingsDialog.C:282-283`):
```cpp
Position atomic_number = parts[0].toUnsignedInt();  // throws Exception::InvalidFormat
ColorRGBA override_color(parts[1]);                  // UB or throws on wrong length
```

`String::toUnsignedInt` throws `Exception::InvalidFormat` for non-numeric strings. `ColorRGBA(const String&)` reads 6 or 8 chars; in release builds the behavior is undefined for shorter strings (buffer overread in `stringToRGBA_`).

CONFIG-01 criterion 2 states: "a stale or partial saved color block falls back to compiled defaults." An unguarded throw propagates out of `readPreferenceEntries`, causing `Preferences::fetchPreferences` to abort mid-iteration. This is the opposite of graceful fallback.

**Currently latent due to CR-01.** Once CR-01 is fixed, CR-03 becomes a crash-on-launch regression for tampered or partially-written `~/.BALLView` files.

## Gaps Summary

Phase 4.1 delivers a correct **write path** (D-01/D-06 diff/override serialization, upsert idiom) and a functional **reset button** (D-02). These are real, working improvements.

The **read path** — which is the mechanism that makes CONFIG-01 criterion 1 observably true ("Users see compiled defaults for any color they have not explicitly customized, and a stale or partial saved color block falls back to compiled defaults") — is dead code at runtime. A single C++ signature mismatch (`INIFile&` vs. `const INIFile&` on the `readPreferenceEntries` override) causes the derived function to hide rather than override the base virtual, so the polymorphic dispatch in `Preferences::fetchPreferences` never reaches the Phase 4.1 code.

Compounding this, the `getSectionLastLine()` sentinel bug (CR-02) means the legacy-discard and empty-overrides-cleanup loops would fail to delete the target line in the most realistic case (target key at tail of section) even if CR-01 were fixed. And the unguarded parse (CR-03) would abort preferences loading on malformed input instead of falling back gracefully, directly contradicting CONFIG-01 criterion 2.

**Concretely:** A Windows user launching v1.6 with a pre-existing `~/.BALLView` containing `Elements=ffffffff;...`:
- Will see PyMOL green carbon (correct, but only because setDefaultValues_() runs in the constructor — pre-Phase-4.1 behavior)
- Will NOT have the legacy `Elements=` line removed from their config file
- Will see the log warning on every launch (once CR-01 is fixed, or never if it stays broken)
- Will have any `ElementColorOverrides=` written by the new write path silently ignored on the next launch (user overrides lost)

Three fixes are required before the phase goal is met:

1. **CR-01 (signature fix):** Change `readPreferenceEntries(INIFile&)` to `readPreferenceEntries(const INIFile&)` in both the header and the .C file, resolve the resulting const-ness constraint for mutation calls, and add `override` specifiers.

2. **CR-02 (sentinel fix):** Replace `getSectionLastLine(...)` with `getSectionLastLine(...).getSectionNextLine()` in both deletion loops (lines 203-211 and 242-251).

3. **CR-03 (exception guard):** Wrap the per-token parse (lines 280-311) in a try/catch block; add a string-length pre-check before `ColorRGBA(parts[1])` construction; log and `continue` on any parse failure.
