# Phase 4.1: Config Color-Defaults Fix — Context

**Trigger:** Promoted 2026-05-14 from backlog 999.4 after the PyMOL element
palette swap (`a3201c1`) landed in source but did not visibly take effect on
machines with a pre-existing `~/.BALLView`. The persisted color tables in the
INI file silently overwrite the compiled defaults at startup.

**User observation 2026-05-15 (motivating Phase 4.1):** The Windows build of
BALLView still rendered the old (pre-PyMOL) element colors. Traced to the
same persist-and-shadow path — the Windows release artifact does **not**
ship a default `.BALLView` (verified in [`release.yml`](../../../.github/workflows/release.yml)
"Bundle data/ next to .exe" step — only `data/` and Qt DLLs are bundled).
So the old colors come from a `C:\Users\<user>\.BALLView` left over from a
prior BALLView install, not from the installer bundle. This confirms Phase 4.1
as the right (and only needed) fix.

**element** color defaults. After Phase 4.1, editing the compiled

<decisions>
## Implementation Decisions

### Fix strategy
- **D-01:** **Strategy C — diff/override only.** `~/.BALLView` persists only
  the color entries the user has explicitly customized (an override map),
  not the full 111-entry table. Compiled defaults always show through for
  any element index the user has not touched. This makes the
  bug class structurally impossible: there is no stored "shadow copy" of
  the defaults to drift out of sync with the compiled palette.
  - *Why not A (version/checksum + fallback):* would lose user
    customizations on every defaults bump.
  - *Why not B alone (Preferences reset button):* fails CONFIG-01
    criterion 1 — colors stay stale until the user clicks reset.
- **D-02:** **A "Reset element colors to defaults" Preferences action is
  still in scope** to satisfy CONFIG-01 criterion 3. With strategy C this
  is a one-line operation: clear the override map and re-`writePreferences`.
  No deep UX needed — a button on the Coloring Settings dialog next to the
  element table.

### Existing-config migration
- **D-03:** **Optimistic discard of legacy full-table `Elements=`.** On
  first launch of v1.6+, if the read path finds the legacy `Elements=` key
  (the old full 111-entry encoding produced by pre-Phase-4.1 BALLView), it
  is silently dropped and the override map starts empty. Compiled defaults
  flow through everywhere immediately.
  - *Why not smart-diff against the pre-PyMOL palette:* would require
    hardcoding the old palette as a migration constant; user chose the
    simpler path.
  - *Tradeoff accepted:* anyone who *did* manually customize element
    colors years ago will lose those edits on upgrade. They can
    re-customize via the existing Coloring Settings dialog. The user-facing
    cost is judged acceptable vs. the implementation simplicity.
  - *Effect on the Windows case that motivated this phase:* the stale
    pre-PyMOL `Elements=` line in `C:\Users\<user>\.BALLView` is discarded
    on first launch; PyMOL defaults render correctly immediately, no user
    action required.

### Scope
- **D-04:** **Element table only.** Residue color persistence has the same
  bug pattern (same `applySettingsTo()` overwrite at
  [`coloringSettingsDialog.C:194`](../../../source/VIEW/DIALOGS/coloringSettingsDialog.C:194))
  and the same eventual fix, but is deferred to a new backlog item to keep
  Phase 4.1 small. The planner should add a backlog stub for the residue
  follow-up at the end of the phase.

### Stale-detection heuristic
- **D-05:** **Key-name change + defensive all-white check.** Two-pronged:
  1. **Format discrimination by INI key.** New format writes under a new
     key (proposed: `ElementColorOverrides=` — final name picked at plan
     time). Read path: presence of the new key → parse as diff overrides;
     presence of the old `Elements=` key → legacy → discard per D-03.
     Both present (shouldn't happen, but defensive) → prefer new, discard
     old.
  2. **All-white sanity check on override entries.** When reading override
     entries, if a saved override is `#ffffff` for a known-colored element
     (carbon, nitrogen, oxygen, phosphorus, sulphur — the real-case set
     from criterion #2), drop that single entry as likely corruption and
     fall back to the compiled default for that index. This honors
     CONFIG-01 criterion 2 ("stale or partial saved color block ... is
     detected and compiled defaults are used instead").

### Write path
- **D-06:** **Diff is computed against the live compiled defaults at
  write time.** When `writePreferenceEntries` runs, iterate the dialog's
  element table; for each row, compare against
  `ElementColorProcessor().getColorMap()[atomic_number]` (the freshly
  constructed default). Differences become entries in `ElementColorOverrides=`;
  matches are omitted. This means "reset" is implicit too: if a user
  edits a color and then edits it back to the default, it correctly
  disappears from the override map.

</decisions>

<specifics>
## Specific Implementation Notes

- **Diff comparison:** at write time, instantiate a temporary
  `ElementColorProcessor` (no args) to get the live compiled defaults,
  then compare row-by-row against the dialog's table. Cheap — 111
  `ColorRGBA` comparisons. No need to cache.
- **Backwards-incompatibility:** v1.6+ writes `ElementColorOverrides=`;
  older BALLView versions reading a v1.6-written config would not find
  `Elements=` and would fall back to their own compiled defaults — which
  is fine (older versions had different defaults anyway; nobody is going
  back to old BALLView from v1.6).
- **Tri-OS CI is the oracle (per Phase 5.1 D-07 carry-forward):**
  verification is "build cleanly on macOS/Linux/Windows, launch the app,
  visually confirm carbon = green PyMOL color." If practical, a tiny test
  that pre-writes a legacy `Elements=` block in a temp HOME, launches
  BALLView in a way that exercises the read path, and asserts the override
  map is empty afterwards, would mechanize this.
- **CONFIG-01 acceptance criteria coverage by decision:**
  - Criterion 1 (defaults show through over existing config) → D-01 + D-03.
  - Criterion 2 (stale/partial detection → fallback) → D-03 + D-05.
  - Criterion 3 (reset from Preferences without deleting `~/.BALLView`) → D-02.

</specifics>
