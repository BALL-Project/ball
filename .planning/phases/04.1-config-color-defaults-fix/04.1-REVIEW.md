# Phase 4.1: Code Review Report

**Reviewed:** 2026-05-15
**Depth:** standard
**Files Reviewed:** 3
**Status:** issues_found

## Summary

Phase 4.1 implements diff-based element-color persistence ("Strategy C"): the dialog
writes only entries that differ from the live compiled `ElementColorProcessor`
defaults under a new `ElementColorOverrides=` key, silently discards the legacy
`Elements=` key on read, and exposes a "Reset element colors to defaults" button.
The intent is sound and the write-path implementation is largely correct.

However, two structural problems block the phase from delivering CONFIG-01:

1. **The entire read-path block is unreachable through the standard preferences
   call chain.** `ColoringSettingsDialog::readPreferenceEntries(INIFile&)` does
   not override the base `PreferencesEntry::readPreferenceEntries(const INIFile&)`
   — the parameter is non-const in the derived, const in the base, so the
   signatures differ and only the base virtual is in the vtable slot dispatched
   via the `HashSet<PreferencesEntry*>` iteration in `Preferences::fetchPreferences`.
   Phase 4.1 inherited this hiding bug (acknowledged out-of-scope in
   `04.1-01-SUMMARY.md`) but then put the entire CONFIG-01 criterion-1/criterion-2
   migration logic *inside* that unreachable function. The legacy-`Elements=`
   discard, the override parsing, and the all-white sanity check never run at
   application startup.

2. **The `LineIterator` loops use the wrong sentinel.** `getSectionLastLine()`
   returns an iterator to the *last actual line* in the section, not a
   past-the-end iterator. The loop `for (it; it != end; ++it)` therefore never
   inspects the last line. When the legacy `Elements=` (or a stale
   `ElementColorOverrides=`) is the last line of `[COLORING_OPTIONS]` — which is
   the common case after a v1.6 write that appends new keys to the tail — the
   `hasEntry` guard fires, the log message is emitted, but `deleteLine` is never
   called. The line silently survives. `dockingAlgorithm.C:103` documents the
   correct idiom: `getSectionLastLine(name).getSectionNextLine()`.

Combined, these two bugs mean the user-observable scenario that motivated the
phase — a stale `~/.BALLView` on Windows shadowing the PyMOL palette — is **not
fixed** by the merged code. The compiled defaults will appear (because the
unreachable read path never applies overrides either), but only by accident; the
legacy `Elements=` line will remain in the file forever, the log spam fires on
every launch, and any explicit user customization is silently lost across
restarts (write succeeds, read is dead).

There is also one secondary correctness defect (off-by-one excluding atomic
number 111) and several robustness/maintainability issues.

## Critical Issues

### CR-01: Read-path override is hidden, not overridden — entire Phase 4.1 read logic is dead code

**File:** `include/BALL/VIEW/DIALOGS/coloringSettingsDialog.h:75`
**Also affects:** `source/VIEW/DIALOGS/coloringSettingsDialog.C:229-312`

**Issue:**
The derived declaration is

```cpp
virtual void readPreferenceEntries(INIFile& inifile);
```

while the base virtual in `include/BALL/VIEW/KERNEL/preferencesEntry.h:108` is

```cpp
virtual void readPreferenceEntries(const INIFile& inifile);
```

`INIFile&` and `const INIFile&` are different parameter types in C++; the
derived function does **not** override the base virtual — it occupies a new
vtable slot and merely hides the base name in derived-class scope.

The application reaches this code via
`Preferences::fetchPreferences(INIFile& inifile)`
(`source/VIEW/DIALOGS/preferences.C:151`), which iterates
`HashSet<PreferencesEntry*> entries_` and calls
`(**it).readPreferenceEntries(inifile)` with `*it` typed as
`PreferencesEntry&`. Overload resolution looks up the name in the base scope,
finds the `const INIFile&` virtual, and dispatches it. The
`ColoringSettingsDialog` override is never reached.

`MainControl::fetchPreferences` (`source/VIEW/KERNEL/mainControl.C:1057`)
invokes `preferences_dialog_->fetchPreferences(inifile)`, so this is the
production code path.

Consequence: the legacy-`Elements=` discard branch (lines 240-253), the
`ElementColorOverrides=` parse branch (lines 257-311), the all-white sanity
check (lines 285-298), and even the pre-existing `ResidueNames=`/`ResidueNameColors=`
restore (lines 314-337) are all unreachable at startup. CONFIG-01 criterion 1
(defaults show through over existing config) is satisfied only *by accident*
because the read path that would apply user customizations is dead too —
the `element_table_` shown is whatever `setDefaultValues_` populated. The
saved overrides written by Plan 01's write path are silently lost on the next
launch.

The plan's "by code review" verification claims the legacy-discard fires on
startup; this is incorrect — the derived function is not invoked.

**Fix:** Make the override real. Either change the derived signature to match
the base, or fix the base to take a non-const reference (the base body and
existing callers mutate the inifile via `inifile.getValue` which is const, so
matching the base signature is the lower-impact change):

```cpp
// include/BALL/VIEW/DIALOGS/coloringSettingsDialog.h
virtual void readPreferenceEntries(const INIFile& inifile) override;

// source/VIEW/DIALOGS/coloringSettingsDialog.C
void ColoringSettingsDialog::readPreferenceEntries(const INIFile& inifile)
{
  PreferencesEntry::readPreferenceEntries(inifile);
  // ...
}
```

However, the new body needs `deleteLine`/`setValue` calls on the inifile — see
CR-02. Either:
(a) pass a `const_cast<INIFile&>(inifile)` for the mutating operations (ugly
but localised), or
(b) change the BASE virtual to `INIFile&` (touches every subclass that
currently declares the const overload — `pythonSettings.C:176`,
`pluginDialog.C:233`, `mainControlPreferences.C:131`, plus base callers in
`preferences.C:174`, `modularWidget.C:126`, `pluginDialog.C:243`,
`molecularStructure.C:1137-1143`).

Use `override` on every derived declaration going forward so the compiler
catches future mismatches. Enable `-Woverloaded-virtual` in the build to
surface the rest.

### CR-02: `getSectionLastLine` loops skip the last line — legacy/stale entries are not deleted when they are the last line of the section

**File:** `source/VIEW/DIALOGS/coloringSettingsDialog.C:203-211`
**Also affects:** `source/VIEW/DIALOGS/coloringSettingsDialog.C:242-251`

**Issue:**
`INIFile::getSectionLastLine` returns an iterator to the **last actual line**
of the section, not a past-the-end iterator
(`source/FORMAT/INIFile.C:411-422`: `line_it = sit->lines_.end(); if (size>0) line_it--;`).
The half-open loop pattern

```cpp
INIFile::LineIterator it  = inifile.getSectionFirstLine("COLORING_OPTIONS");
INIFile::LineIterator end = inifile.getSectionLastLine("COLORING_OPTIONS");
for (; it != end; ++it)
{
  if ((*it).hasPrefix("Elements=")) { inifile.deleteLine(it); break; }
}
```

terminates before inspecting `end`. When the target key is the last line of
the section, `hasEntry(...)` returns true, the log line "dropping legacy
Elements= block" is emitted, but `deleteLine` is never called. The stale
line persists, the log fires every launch, and `hasEntry` returns true forever.

This is the realistic-case configuration for the very scenario Phase 4.1
exists to fix: a pre-Phase-4.1 `~/.BALLView` typically has `Elements=` at the
tail of `[COLORING_OPTIONS]` (after `ResidueNames=` / `ResidueNameColors=`).
For the cleanup branch (lines 200-213), `ElementColorOverrides=` will likewise
often be the last line, since it is the only new key Phase 4.1 writes and it
is appended via `insertValue`.

The correct idiom is documented elsewhere in the codebase
(`source/DOCKING/COMMON/dockingAlgorithm.C:103`):

```cpp
INIFile::LineIterator end = inifile.getSectionLastLine(name).getSectionNextLine();
```

**Fix:** Use the past-the-end form in both loops:

```cpp
INIFile::LineIterator it  = inifile.getSectionFirstLine("COLORING_OPTIONS");
INIFile::LineIterator end = inifile.getSectionLastLine("COLORING_OPTIONS").getSectionNextLine();
for (; it != end; ++it)
{
  if ((*it).hasPrefix("Elements="))
  {
    inifile.deleteLine(it);
    break;
  }
}
```

Apply the same change to the empty-overrides cleanup loop at lines 203-211.
Also: the legacy-discard log message on line 252 currently fires
unconditionally on `hasEntry==true`, which becomes misleading when the
delete silently fails. Move the log inside the `if ((*it).hasPrefix(...))`
branch (after `deleteLine` returns true), so the message only fires when
the line is actually removed.

### CR-03: Unguarded `String::toUnsignedInt` and `ColorRGBA(String)` can throw out of `readPreferenceEntries`

**File:** `source/VIEW/DIALOGS/coloringSettingsDialog.C:282-283`

**Issue:**

```cpp
Position atomic_number = parts[0].toUnsignedInt();
ColorRGBA override_color(parts[1]);
```

`String::toUnsignedInt` (`source/DATATYPE/string.C:454`) throws
`Exception::InvalidFormat` if the string is not numeric. `ColorRGBA(const String&)`
delegates to `stringToRGBA_` which in `BALL_VIEW_DEBUG` builds throws
`Exception::InvalidRange` if the length is not 6 or 8 — and in release builds
silently reads past the end of the input buffer for shorter strings
(`source/VIEW/DATATYPE/colorRGBA.C:255-282`), which is undefined behaviour.

A user-tampered `~/.BALLView` (or a partial write after a crash) like
`ElementColorOverrides=garbage:zz;` will propagate `InvalidFormat` out of
`readPreferenceEntries`, aborting the whole preferences load. Combined with
CR-01 this is currently latent, but once the read path is reached the
exception is real.

The phase's intent (D-05.2: "stale or partial saved color block is detected
and compiled defaults are used instead") explicitly calls for graceful
fallback on malformed input — silently skipping a bad token is what
CONFIG-01 criterion 2 requires.

**Fix:** Wrap the per-token parse in a try/catch and skip the token on any
exception:

```cpp
for (Position t = 0; t < (Position)tokens.size(); ++t)
{
  if (tokens[t].isEmpty()) continue;

  std::vector<String> parts;
  tokens[t].split(parts, ":");
  if (parts.size() != 2 || parts[0].isEmpty() || parts[1].isEmpty()) continue;

  // Defensive length check before constructing ColorRGBA — stringToRGBA_
  // reads 6 or 8 chars without bounds checking in release builds.
  if (parts[1].size() != 6 && parts[1].size() != 8)
  {
    Log.warn() << "ColoringSettingsDialog: dropping malformed override token '"
               << tokens[t] << "'" << std::endl;
    continue;
  }

  Position atomic_number;
  ColorRGBA override_color;
  try
  {
    atomic_number = parts[0].toUnsignedInt();
    override_color = ColorRGBA(parts[1]);
  }
  catch (const Exception::GeneralException&)
  {
    Log.warn() << "ColoringSettingsDialog: dropping unparseable override token '"
               << tokens[t] << "'" << std::endl;
    continue;
  }

  // ... existing all-white check + table update
}
```

## Warnings

### WR-01: Off-by-one in atomic-number filter silently drops element 111 (Rg) customizations

**File:** `source/VIEW/DIALOGS/coloringSettingsDialog.C:161, 172`

**Issue:**

```cpp
const Size BALL_VIEW_NUMBER_ELEMENTS_LOCAL = 111;
// ...
if (e.getAtomicNumber() == 0 || e.getAtomicNumber() >= BALL_VIEW_NUMBER_ELEMENTS_LOCAL)
{
  continue;
}
```

`Element::NUMBER_OF_ELEMENTS == 111` covers atomic numbers 1..111. The
condition `>= 111` skips atomic number 111 (Roentgenium). The write path
therefore silently drops a user customization of element 111.

Separately: defining a local magic-number `BALL_VIEW_NUMBER_ELEMENTS_LOCAL`
that shadows the existing `BALL_VIEW_NUMBER_ELEMENTS` macro (defined at
`source/VIEW/MODELS/standardColorProcessor.C:24`) is a code-smell — the two
can drift. Use `Element::NUMBER_OF_ELEMENTS` (a real C++ constant in
`include/BALL/KERNEL/PTE.h:190`) directly.

There is a separate, pre-existing defect in
`ElementColorProcessor::ElementColorProcessor()` that defines the table only
for indices 0..110 (loop `i < BALL_VIEW_NUMBER_ELEMENTS == 111` => keys
0..110, missing atomic number 111). That is out of Phase 4.1 scope but is
why the off-by-one here happens to be invisible today. Once the defaults
table is extended to cover Rg, this filter will silently drop it.

**Fix:**

```cpp
if (e.getAtomicNumber() == 0 || e.getAtomicNumber() > Element::NUMBER_OF_ELEMENTS)
{
  continue;
}
```

Remove the `BALL_VIEW_NUMBER_ELEMENTS_LOCAL` local constant.

### WR-02: `Log.info()` legacy-discard message fires unconditionally regardless of whether the delete succeeded

**File:** `source/VIEW/DIALOGS/coloringSettingsDialog.C:240-253`

**Issue:** The log message is emitted after the loop in **all** cases where
`hasEntry` returned true, including the (currently broken — see CR-02) case
where the loop terminates without finding/deleting the line. The message
claims the legacy block has been dropped, but it hasn't. This is misleading
for diagnostics and will spam the log on every startup as long as the line
remains in the file (which is forever, given CR-02).

Once CR-02 is fixed, the log line still fires unconditionally — but the
deletion now actually happens, so it's no longer misleading. Still, moving
the log inside the success branch is more defensive.

**Fix:** Move the `Log.info()` inside the matched-prefix branch, after the
`deleteLine`:

```cpp
for (; it != end; ++it)
{
  if ((*it).hasPrefix("Elements="))
  {
    inifile.deleteLine(it);
    Log.info() << "ColoringSettingsDialog: dropped legacy Elements= ..." << std::endl;
    break;
  }
}
```

### WR-03: All-white sanity-check set rebuilt per call

**File:** `source/VIEW/DIALOGS/coloringSettingsDialog.C:263-268`

**Issue:** `std::set<Position> known_colored` is constructed and populated
on every call to `readPreferenceEntries`, with five `insert` calls. This is
not a performance issue at the function level (the call runs once at
startup) but the inline construction couples the magic-number set with the
parse loop and makes the D-05.2 "known-colored elements" rule hard to
reuse / unit-test.

Defining a file-scope `static const Position kKnownColoredAtomicNumbers[] = {6, 7, 8, 15, 16};`
plus a small helper (or even `std::find(begin, end, atomic_number) != end`)
keeps the rule in one named place.

**Fix:**

```cpp
namespace
{
  // D-05.2: atomic numbers whose all-white override is treated as corruption
  // (carbon, nitrogen, oxygen, phosphorus, sulphur).
  constexpr Position KNOWN_COLORED_ATOMIC_NUMBERS[] = {6, 7, 8, 15, 16};

  bool isKnownColoredElement(Position atomic_number)
  {
    return std::find(std::begin(KNOWN_COLORED_ATOMIC_NUMBERS),
                     std::end(KNOWN_COLORED_ATOMIC_NUMBERS),
                     atomic_number) != std::end(KNOWN_COLORED_ATOMIC_NUMBERS);
  }
}
```

then drop the `<set>` include (the only consumer in this TU).

### WR-04: `resetElementColors` duplicates the element-population loop from `setDefaultValues_`

**File:** `source/VIEW/DIALOGS/coloringSettingsDialog.C:491-513`

**Issue:** `resetElementColors()` reimplements lines 56-74 of
`setDefaultValues_()` verbatim:

```cpp
ElementColorProcessor elp;
const HashMap<Position, ColorRGBA>& color_hash_map = elp.getColorMap();
vector<String> names;
vector<ColorRGBA> colors;
HashMap<Position, ColorRGBA>::ConstIterator it = color_hash_map.begin();
for (; it != color_hash_map.end(); it++)
{
  if (it->first == 0) continue;
  names.push_back(PTE[it->first].getSymbol());
  colors.push_back(it->second);
}
names.push_back(PTE[0].getSymbol());
colors.push_back(color_hash_map[0]);
element_table_->setContent(names, colors);
```

The two copies will drift. Plan 02 notes this is intentional ("Body mirrors
`setDefaultValues_` lines 53-72 exactly") but explicit code duplication is
still a maintenance hazard — a future change to the element-table population
in `setDefaultValues_` will silently leave the reset action behind.

Additionally, `color_hash_map[0]` on a non-const `HashMap` would insert a
default-constructed entry if key 0 were absent. Here `color_hash_map` is
bound to a `const HashMap<Position, ColorRGBA>&`, so this would not compile
if `operator[]` were the mutating overload — it works because the iteration
order is undefined for `HashMap` so `color_hash_map[0]` retrieves the
existing key 0 entry (populated by the default-table constructor).
Compilation aside, indexing a const hashmap is brittle.

**Fix:** Extract a private helper:

```cpp
// In .h, protected:
void populateElementTableFromDefaults_();

// In .C:
void ColoringSettingsDialog::populateElementTableFromDefaults_()
{
  ElementColorProcessor elp;
  const HashMap<Position, ColorRGBA>& color_hash_map = elp.getColorMap();
  vector<String> names;
  vector<ColorRGBA> colors;

  HashMap<Position, ColorRGBA>::ConstIterator it = color_hash_map.begin();
  HashMap<Position, ColorRGBA>::ConstIterator end = color_hash_map.end();
  HashMap<Position, ColorRGBA>::ConstIterator unknown_it = color_hash_map.find(0);

  for (; it != end; ++it)
  {
    if (it->first == 0) continue;
    names.push_back(PTE[it->first].getSymbol());
    colors.push_back(it->second);
  }
  if (unknown_it != end)
  {
    names.push_back(PTE[0].getSymbol());
    colors.push_back(unknown_it->second);
  }
  element_table_->setContent(names, colors);
}
```

then call it from both `setDefaultValues_()` and `resetElementColors()`.

## Info

### IN-01: Lack of `override` keyword on virtual declarations made CR-01 invisible at compile time

**File:** `include/BALL/VIEW/DIALOGS/coloringSettingsDialog.h:72, 75, 79-83`

**Issue:** None of the virtual functions in `ColoringSettingsDialog` use the
C++11 `override` specifier. Had `readPreferenceEntries(INIFile& inifile)`
been declared `override`, the compiler would have rejected it (no matching
base), and CR-01 would have surfaced at build time on Phase 4.1.

This is a project-wide convention question rather than a per-commit fix, but
the new Phase 4.1 declarations (`resetElementColors()`,
`readPreferenceEntries`, `writePreferenceEntries`) are a natural place to
start adopting it.

**Fix:** Add `override` to the four `Q_SLOTS` overrides and the two
preferences-entry overrides:

```cpp
virtual void maxDistanceChanged() override;
virtual void maxTFChanged() override;
virtual void forceMaxValueChanged() override;
virtual void forceMinValueChanged() override;
virtual void resetElementColors();    // no base — new slot
virtual void writePreferenceEntries(INIFile& inifile) override;
virtual void readPreferenceEntries(const INIFile& inifile) override;  // post-CR-01 fix
```

(Slots without a base counterpart, like `resetElementColors`, stay
unannotated.)
