<objective>
Fix the read and write paths in `ColoringSettingsDialog` so `~/.BALLView` persists
only the residue-color entries the user has explicitly customized — a diff against
the live compiled `ResidueNameColorProcessor` defaults — under a new INI key
`ResidueNameColorOverrides=`. On read, the legacy `ResidueNames=` and
`ResidueNameColors=` keys are silently discarded; the new key is parsed as a diff
and applied to `residue_table_`.

This is a **direct application of the Phase 4.1 fix pattern** (commits 3051009 +
9703563) to the residue-color persistence path. Phase 4.1 handled
`ElementColorProcessor` per-element overrides via `ElementColorOverrides=`; this
phase handles the structurally identical bug for `ResidueNameColorProcessor`
per-residue overrides. The four locked decisions D-01 (diff/override only), D-03
(legacy discard on read), D-05 (key naming + conflict rule), and D-06 (diff
against live compiled defaults at write time) all carry forward unchanged — the
only delta is the data type: `HashMap<Position, ColorRGBA>` (atomic-number keyed)
becomes `StringHashMap<ColorRGBA>` (residue-name keyed).

Purpose: structurally eliminates the bug class where a saved full-table
`ResidueNames=`/`ResidueNameColors=` line silently shadows the compiled residue
palette. The persisted file no longer contains a shadow copy of the defaults at
all, so they cannot drift out of sync. Resolves CONFIG-02 (residue-color
persistence — the companion requirement to CONFIG-01 closed by Phase 4.1).

Output: a single-file change to `source/VIEW/DIALOGS/coloringSettingsDialog.C`
mirroring the Phase 4.1 write-path block (currently at lines 153-213) and
read-path block (currently at lines 231-318), inserted for the residue path.
</objective>

From `include/BALL/VIEW/MODELS/standardColorProcessor.h:222-251`:
- `class BALL_VIEW_EXPORT ResidueNameColorProcessor : public ColorProcessor`
- `ResidueNameColorProcessor()` — populates `color_map_` with 26 entries: 21 amino acid 3-letter codes + 5 nucleotide single-letter codes + a `---` "nomatch" sentinel at index 0 (`source/VIEW/MODELS/standardColorProcessor.C:196-248`; macro `BALL_NR_RESIDUES == 26` is local to the .C, so the dialog must NOT depend on it).
- `StringHashMap<ColorRGBA>& getColorMap()` / `const StringHashMap<ColorRGBA>& getColorMap() const` — key type is `String` (residue name), not `Position`. Mirrors Phase 4.1's `HashMap<Position, ColorRGBA>` access pattern with one type substitution.

From `source/VIEW/DIALOGS/coloringSettingsDialog.C` (the existing residue-path patterns this plan replaces):
- Write path (lines 234-243): currently emits full-table `ResidueNames=` (`;`-separated names) and `ResidueNameColors=` (`;`-separated RGBA hex). Bare `insertValue` (no upsert pair) — same Issue 1 hazard Phase 4.1 fixed for elements.
- Read path (lines 352-375): currently parses both legacy keys, splits on `;`, builds a `std::vector<ColorRGBA>`, calls `residue_table_->setContent(split_names, split_color_rgba)` — which REPLACES the table content wholesale rather than overlaying overrides. This is the structural shadow-default bug.
- `residue_table_->item(p, 0)->text()` — residue name (String); `residue_table_->item(p, 1)->background().color()` — color (QColor → ColorRGBA via the existing pattern at line 239 / Phase 4.1's element pattern at line 123).
- `applySettingsTo(ColorProcessor&)` ResidueNameColorProcessor branch (lines 392-400) iterates `residue_table_` rows and writes to the processor's `color_map_` keyed by residue name. UNCHANGED by this plan — the table now holds compiled defaults for untouched names + override values for touched ones, which is exactly what `applySettingsTo` already expects (mirrors Phase 4.1 element-branch reasoning at PLAN line 42-43).

New `ResidueNameColorOverrides=` schema (mirrors Phase 4.1 `ElementColorOverrides=`):
- Format: `<residue_name>:<rgba_hex>;<residue_name>:<rgba_hex>;...`
- Example: `GLY:33ff33ff;ALA:ffaa00ff;`
- Residue-name keys are 1-3 ASCII chars (per BALL's residue code conventions); no `:` or `;` chars appear inside a name → the same split-on-`;`-then-split-on-`:` parser shape from Phase 4.1 read path works verbatim with the data type substitution.

NOT carried forward from Phase 4.1:
- **All-white sanity check (D-05.2):** the element path drops all-white overrides for {C, N, O, P, S} because those are real-case CONFIG-01 corruption signals. The residue palette has multiple legitimately-white entries (GLY, ALA in the compiled defaults — `source/VIEW/MODELS/standardColorProcessor.C:204-205`), so an all-white override for those residues is INDISTINGUISHABLE from a legitimate user choice. Therefore: NO all-white sanity check on the residue path. Document this in the source as a comment so a future maintainer doesn't add one by symmetry-reflex.
- **Malformed-hex length pre-check + try/catch wrapper:** carry forward from Phase 4.1 Issue 2 (it guarded against ColorRGBA's `BALL_VIEW_DEBUG`-only InvalidRange and `String::toUnsignedInt`'s InvalidFormat). The residue path doesn't call `toUnsignedInt` (keys are strings, not numbers), but the `ColorRGBA(hex_str)` length-check still applies. KEEP that part; DROP the `toUnsignedInt` try.
