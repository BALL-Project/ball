# P4.3 — V21-ELEMENT-INSTANCE-ID: Misframed

**Phase:** P4.3 (V21-ELEMENT-INSTANCE-ID).
**Status:** RECOMMEND DROP — misframed; not a JSON gap.
**Date:** 2026-05-20.

## What the deferral list assumed

R8/R9 listed "Element-instance id-table for custom Element
round-trip" as a v2.1 JSON-completeness item: the idea that a
custom (non-PTE) `Element` set on an atom loses pointer identity
when serialized to JSON, and that an instance-id table would
preserve it.

## The finding (code-verified)

The element identity loss happens at **`setElement()` time, in the
store — NOT at JSON time.**

`Atom::writeStoreElement_(const Element* e)` (atom.C:152) stores
ONLY the atomic number:

```cpp
const std::uint8_t ei =
    (e == 0) ? 0 : static_cast<std::uint8_t>(e->getAtomicNumber());
store_->element_index(store_idx_) = ei;
```

`Atom::readStoreElement_()` (atom.C:161) reverse-resolves through
the canonical periodic table:

```cpp
return PTE[(Position)store_->element_index(store_idx_)];
```

So the moment you call `atom.setElement(custom_element)`, the store
keeps only `custom_element.getAtomicNumber()`. A subsequent
`atom.getElement()` — **with no JSON involved at all** — returns
`PTE[atomic_number]`, the canonical periodic-table instance, not
the custom one. The custom Element's name/mass/radius and its
pointer identity are gone at `setElement`, in memory, before any
serialization.

The JSON round-trip then faithfully preserves exactly what the
store holds: the atomic number. There is **no additional
JSON-specific loss**. `saveSystemJSON` writes `element_index`;
`loadSystemJSON` restores it; `getElement()` resolves it through
PTE identically before and after.

## Why V21-ELEMENT-INSTANCE-ID is the wrong fix

To "preserve custom Element identity" you would need the **store**
to hold more than the atomic number — a per-atom element-instance
id plus a custom-element registry. That is:

1. **A kernel change, not a JSON change.** The JSON layer is
   already faithful; the information was never in the store.
2. **Anti-SoA.** The element column is deliberately 1 byte/atom
   (atomic number). Widening it to a 4-byte instance-id +
   maintaining a registry adds 3 bytes/atom (300 KB at 100k atoms)
   to preserve a rare edge case — directly counter to the SoA
   compactness goal that motivates the whole v2.x kernel.
3. **For a near-nonexistent use case.** PTE has no public
   custom-element registration API; `PTE[Z]` / `PTE[symbol]` return
   canonical instances. A user *can* construct a standalone
   `Element` and `setElement` it, but its non-atomic-number
   attributes are dropped at `setElement` regardless of JSON.

## Recommendation: DROP from v2.1 (and likely entirely)

V21-ELEMENT-INSTANCE-ID does not describe a real JSON round-trip
gap. The element column is atomic-number-only **by design**, and
the JSON round-trip is faithful to that design. The "fix" would
widen the SoA element column against the kernel's core
compactness goal, for a use case BALL barely supports.

**Action:** drop V21-ELEMENT-INSTANCE-ID. Document the
atomic-number-only element model as intentional in
RELEASE-NOTES-v2.1.md "Known limitations" (it collapses custom
Elements to their PTE canonical by atomic number — a deliberate
SoA trade-off, not a serialization bug).

## Consequence for P4 scope

With P4.2 deferred to v2.2 (D42) and P4.3 dropped (this finding),
**P4 collapses to P4.1 alone** (V21-LOAD-BATCH, done — 16× load).
P4.1 is a load-performance fix that did NOT change the JSON
schema, so **P4.4 (schema MINOR bump) has nothing to bump** — the
K0.6 JSON schema is unchanged by v2.1.

Net: v2.1 P4 delivered the JSON **load 16× speedup** and nothing
schema-affecting. The two schema-affecting features originally
planned (bond properties, element instance-id) are respectively
deferred to v2.2 and dropped as misframed.
