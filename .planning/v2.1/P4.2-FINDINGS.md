# P4.2 — V21-BOND-PROPERTY-JSON: Premise Falsified

**Phase:** P4.2 (V21-BOND-PROPERTY-JSON).
**Status:** BLOCKED — design premise wrong; scope decision needed.
**Date:** 2026-05-20.

## What R16 C-B7 / R24 P24-6 assumed

Both reviews framed bond-property JSON as a clean win: "Bond's v0
`PropertyManager` is directly readable through
`detail::properties_to_json(const PropertyManager&)`, the same
helper already used for System/Molecule/Atom bags. No side table
required" (R24 P24-6).

That is correct on the **save** side. It is **impossible on the
load side** as the loader currently stands.

## The finding (code-verified)

Bonds in v2.1 are **dual-represented**:

1. **Store side:** `MoleculeStore::bonds_` holds `BondRecord {a, b,
   order, type, flags}` + the CSR adjacency. Store-based queries
   (`for_each_bond_of`, `bond_degree`, `bonds_of`) read this.

2. **Atom side:** `Atom::bond_[]` (an inline array of `Bond*`) +
   `Atom::number_of_bonds_` (atom.h:991). `atom.countBonds()` /
   `atom.getBond(i)` / the AtomBondIterator all read THIS. The
   `Bond*` heap objects carry the `PropertyManager` bag (bond.h:56
   `Bond : ... public PropertyManager`).

**The System JSON loader only populates the store side.**
`loadSystemJSON` (systemJson.C:580) calls `store.add_bond(...)`
directly — it never creates `Bond*` heap objects and never
populates `Atom::bond_[]`.

Consequence: **after `loadSystemJSON`, no `Bond*` objects exist.**
- `store.live_bond_count()` > 0 (store records restored) ✓
- `atom.countBonds()` == 0 (Atom-side graph not reconstructed) ✗
- There is no `Bond*` to attach restored properties to.

Confirmed by `SystemJson_test`: every bond assertion uses
`store.bond()` / `store.live_bond_count()` — the store side. None
test `atom.countBonds()` post-load. The Atom-side bond graph
reconstruction is simply not part of the v2.0/v2.1 System JSON
round-trip.

## Why this blocks P4.2 as scoped

V21-BOND-PROPERTY-JSON = "round-trip the Bond `PropertyManager`
bag." The bag lives on `Bond*`. On load there is no `Bond*`. So
the feature cannot complete without first reconstructing the
`Bond*` graph — which is a materially bigger change than "serialize
one more bag," and is arguably a separate latent gap (the Atom-side
bond graph is lost across a System JSON round-trip regardless of
properties).

R16 C-B7 and R24 P24-6 both missed this because they reasoned about
the SAVE side (where `Bond*` exists) and the store-record restore
(which works), without checking that the LOAD side reconstructs the
`Bond*` objects that own the bags. It does not.

## Options

### Option A — Reconstruct the `Bond*` graph in the loader, then restore properties

The loader's bond phase would, for each store bond, create a
`Bond*` (via `Atom::createBond` or equivalent) wiring `Atom::bond_[]`
on both endpoints, then restore the bag via
`detail::json_to_properties(*bond, ...)`.

- **Pro:** closes the latent "no Bond* / countBonds()==0 after
  load" gap (a real v2.0 round-trip fidelity bug) AND delivers bond
  properties.
- **Con:** materially larger than "one more bag." Touches the
  loader's bond phase, the RollbackGuard window, and the
  Atom-side bond wiring. Needs its own R-review. The Bond*
  reconstruction interacts with the v2.2 V21-BOND-THIN-HANDLE
  redesign — building Atom-side `bond_[]` now is work that v2.2
  may rip out.

### Option B — Store-native bond properties (keyed by bond-record index)

Add a per-bond-record property store to `MoleculeStore` (parallel
to the P1.4 atom property columns), keyed by bond record index.
Properties round-trip with the store; no `Bond*` needed.

- **Pro:** fits the SoA model; no Bond* dependency; aligns with the
  v2.2 thin-handle direction (bonds become store-native).
- **Con:** new store architecture (bond property columns). Does NOT
  fix the Atom-side `Bond*` gap. The save side currently reads from
  `Bond*::PropertyManager`, so a writer change is needed to source
  bond properties from wherever force-field code actually sets them
  (it sets them on `Bond*` today). So Option B alone doesn't
  round-trip what's currently set on `Bond*` either — it would
  require force-field code to write properties store-side, which is
  v2.2 mutation-wiring territory (deferred per D39).

### Option C — Defer P4.2 to v2.2; bundle with V21-BOND-THIN-HANDLE

The clean home for bond properties is the v2.2 bond-thin-handle
work, where `Bond` becomes a store-backed handle and bond
properties naturally live in store columns (same as atom
properties after the v2.2 inheritance flip). At that point both the
save and load sides have a coherent store-native home, and the
Atom-side `bond_[]` reconstruction question is resolved by the
redesign rather than patched.

- **Pro:** avoids building Atom-side `Bond*` wiring (Option A) or a
  standalone bond-property-column system (Option B) that v2.2 would
  rework. Honest about the dependency.
- **Con:** v2.1 ships without closing the v2.0 known gap (R16
  C-B7). The v2.1 RELEASE-NOTES would carry it forward as a v2.2
  item.

## Recommendation

**Option C (defer to v2.2).** The bond `PropertyManager` round-trip
is structurally entangled with the bond representation redesign:
- The bag lives on `Bond*`, which the loader doesn't reconstruct.
- The proper store-native home depends on the v2.2 bond-thin-handle
  flip + mutation wiring (D39, already deferred to v2.2).
- Options A and B both build scaffolding that v2.2 would rework.

P4.2 → v2.2. v2.1 P4 then delivers P4.1 (load 16× — done) + P4.3
(Element-instance-id) + P4.4 (schema bump for whatever P4 lands).
The v2.0 known-gap (R16 C-B7) carries forward to v2.2 with this
finding as the rationale.

## Open question for the maintainer

Pick A / B / C. The recommendation is C. If A is preferred (close
the round-trip fidelity gap now), it becomes its own sub-phase with
an R-review, because reconstructing the Atom-side `Bond*` graph is
load-bearing and easy to get wrong (RollbackGuard, double-wiring,
bond-order/type consistency with the store records).
