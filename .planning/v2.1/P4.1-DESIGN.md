# P4.1 — V21-LOAD-BATCH Design

**Phase:** P4.1 (post-P4.0 profile; gated by R24 planning review).
**Status:** DRAFT.
**Date:** 2026-05-20.
**Profile source:** `.planning/v2.1/P4-PROFILE.md` — insert bucket
is 95% of load (3414 ms of 3588 ms).

## Root cause (confirmed by code trace)

The loader creates 100k atoms with `new Atom` (orphan-store bound),
then `m->insert(*atom)` per atom. Each insert routes:

```
AtomContainer::append(Atom&)
  -> Composite::appendChild(atom)        // O(1), cheap
  -> sys->adopt(atom)                    // expensive
       -> for_each_bond_of(orphan, src_idx, fn)   // <-- O(n) per call
            -> ensure_csr_()             // rebuilds ENTIRE orphan CSR
```

`ensure_csr_()` (moleculeStore.C:805) does
`bond_csr_off_.assign(n_atoms + 1, 0)` + a full bonds_ scan — O(n_atoms).
It rebuilds whenever `csr_dirty_` is set, and **every**
`allocate_atom` (line 378/417) and `release_atom` (line 519) sets
`csr_dirty_ = true`. So between consecutive adopts the orphan CSR is
always dirty, forcing a full rebuild on the next adopt's bond scan.

During the load the orphan store holds ~100k atoms (all created up
front in the alloc phase). Each of the 100k adopts triggers an
O(100k) CSR rebuild → **O(n²) ≈ 10¹⁰ ops ≈ 3.4 s.**

Critically: **the orphan store has ZERO bonds during the load**
(atoms are created bondless; bonds are restored later, in the
destination store, in the loader's bond phase). So the entire CSR
rebuild produces an empty adjacency every time — pure wasted work.

## Fix — two layers

### Layer 1 (primary): short-circuit `for_each_bond_of` on empty bonds

`include/BALL/KERNEL/moleculeStore.h` `for_each_bond_of`:

```cpp
template <typename F>
void for_each_bond_of(Index i, F&& fn) const
{
    if (bonds_.empty()) return;   // NEW: nothing to iterate, no CSR rebuild
    ensure_csr_();
    // ... existing CSR walk ...
}
```

Same guard added to `bond_degree(i)` and `bonds_of(i)` (the other
two `ensure_csr_()` callers) for consistency.

**Effect:** when a store has no bond records, the bond-scan
primitives are O(1) and never trigger a CSR rebuild. The orphan
store during a fresh load has `bonds_.empty() == true`, so every
adopt's bond scan becomes O(1) → insert collapses from O(n²) to
O(n).

**Correctness:** `bonds_.empty()` ⟹ there are definitely no bonds
incident to any atom, so `for_each_bond_of` legitimately does
nothing. (If `bonds_` holds only tombstoned/dead entries it is
NOT empty, so we conservatively still rebuild — correct, just not
optimal for that rarer case.)

**Generality:** this fix benefits EVERY adopt path (interactive
single-atom adoption, adoptSubtree, JSON load), not just the
loader. Any "migrate bondless atoms" workload was paying the
O(n²).

### Layer 2 (defensive): loader pre-reserves the destination store

`source/KERNEL/systemJson.C` after `sys.getStore().clear()`:

```cpp
sys.getStore().reserve(n + 64);   // NEW: avoid per-adopt column realloc
```

The loader currently does NOT reserve (unlike JsonBench's build_
which does). Pre-reserving avoids ~17 incremental vector
reallocations of the destination store's 13 columns during the
adopt storm. Smaller win than Layer 1 but free and obviously
correct.

## Why NOT the "build atoms directly in dst store" strategy

P4-PROFILE.md listed "allocate atoms directly in the destination
store" as strategy 1. Rejected for v2.1 because:
- It requires a loader-only Atom-construction path that binds to a
  specific store + index, bypassing the orphan-store D16 contract.
  That's new public-ish surface + lifecycle complexity.
- Layer 1 achieves the same asymptotic win (O(n²) → O(n)) with a
  3-line guard on an existing primitive, no new construction path,
  and it generalises to all adopt callers.

## Expected result

- insert: 3414 ms → estimated ~80-150 ms (the residual is the
  100k O(1) appendChild + 100k O(1) adopt column-copies + the
  bounded column reallocs that Layer 2 removes).
- total load: ~3588 ms → estimated **~250-350 ms**, a **~10-14×
  load speedup**, comfortably under the roadmap's "≤2× save:load
  ratio" aspiration (save ~230 ms → 2× = 460 ms).

**Per D41.2, the committed target is set after the prototype
measures the actual drop**, not before. This doc states the
hypothesis; P4.1's implementation commit states the measured
number.

## Test plan

1. `JsonBench_test` load gate: currently `load_ms < 10000.0`.
   After P4.1, tighten to a value derived from the measured
   result (per D41.3 calibration, with headroom).
2. Re-run `BALL_JSON_LOAD_PROFILE=1` to confirm insert is no
   longer dominant.
3. Full CORE_ONLY ctest: 284/284 preserved (the for_each_bond_of
   guard must not change any bond-iteration semantics — verified
   by Bond_test, AtomContainer_test, MoleculeStore_test,
   SystemJson_test, MoleculeStoreJson_test).
4. New micro-test in MoleculeStore_test: a store with
   `bonds_.empty()` returns immediately from for_each_bond_of /
   bond_degree / bonds_of without dirtying or rebuilding CSR.

## Risk register

- **R-P4.1.A (LOW):** the `bonds_.empty()` guard changes the
  first-call behavior of for_each_bond_of. If any caller relied
  on the CSR being built as a side effect of for_each_bond_of
  (unlikely — CSR is internal), it could change. Mitigation:
  the guard only skips when there are zero bonds, in which case
  there is nothing for the CSR to represent.
- **R-P4.1.B (LOW):** reserve(n+64) over-allocates if the doc has
  many freed slots. Bounded waste; acceptable.
- **R-P4.1.C (LOW):** thread-safety — `bonds_.empty()` read
  outside the bond_mutex_. But `for_each_bond_of` already documents
  the D7 "no concurrent mutator" contract; reading bonds_.empty()
  under that contract is safe (same as reading bonds_ via the CSR).

## R24 review questions

1. Is `bonds_.empty()` the right predicate, or should it be
   "no live bonds" (which would need a cached live-bond count to
   stay O(1))?
2. Should Layer 1 also short-circuit `ensure_csr_()` itself
   (e.g. when bonds_.empty(), set empty CSR + clear dirty)
   instead of guarding each caller?
3. Does the adopt/adoptSubtree O(n²) merit a broader fix beyond
   the loader (it's a general kernel perf bug)? Or is the
   for_each_bond_of guard sufficient to close it everywhere?
4. Thread-safety of the unlocked `bonds_.empty()` read.
