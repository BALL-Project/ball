## New findings

- **R20-1 — Atom no longer being a `Composite` breaks broad source compatibility, not just insertion.** Many paths accept `Composite&` then test/cast to Atom, e.g. `Selector::operator()(Composite&)` dynamic-casts to `Atom&` after `RTTI::isKindOf<Atom>` ([selector.C](/Users/kohlbach/Claude/BALL2/source/KERNEL/selector.C:84)), and many view/NMR/structure paths dynamic-cast `Composite*` to `Atom*`. The P2 plan only addresses `atom->getParent()` source compatibility, but not `Composite& c = atom`, `appendChild(atom)`, `AtomIterator`, `RTTI::isKindOf<Atom>(&composite)`, or Python SIP APIs exposing `appendChild(Composite&)`.

- **R20-2 — The side-table topology stores handles, but current public APIs return `Composite*`.** P1's internal `CompositeTopologyView` is explicitly `Composite*` based ([moleculeStoreInternal.h](/Users/kohlbach/Claude/BALL2/include/BALL/KERNEL/_moleculeStoreInternal.h:112)). That cannot represent an Atom node after Atom stops deriving from `Composite`; P2 needs a new public node/reference abstraction or must keep an adapter `Composite` object per Atom, which would undermine the memory goal.

- **R20-3 — Adoption and release ordering can erase the only copy of P2 state.** After P2, `Atom a; a.setProperty(...); mol.insert(a);` writes P2 state into the orphan store, then `System::adopt` releases the orphan slot after migrating only core columns ([system.C](/Users/kohlbach/Claude/BALL2/source/KERNEL/system.C:172)). This is a data-loss blocker for properties, selection, and topology unless migration is added before the inheritance flip.

- **R20-4 — P2.1 standalone shim tests are not meaningful without an owning Atom/handle.** A constructed standalone `D17Composite_test` cannot query a real store unless the shim has per-instance state, global state, or a host-object callback. The plan says `reach_store_()` returns nullptr if no store reachable ([P2-PLAN.md](/Users/kohlbach/Claude/BALL2/.planning/v2.1/P2-PLAN.md:97)); a passing standalone test would not prove Atom forwarding works.

## Recommended P2 entry checklist (if GO)

Not GO yet. Required before P2 code lands:

1. Define the host/shim mechanism precisely: CRTP or explicit `Atom` overloads, non-virtual where needed for EBO, exact `getParent()` implementation, and compile-time size assertions for all target compilers.
2. Decide the `Composite` compatibility strategy: adapter nodes, new iterator/reference abstraction, or delayed removal of `Composite` inheritance. Include `appendChild(Atom&)`, `AtomIterator`, RTTI/dynamic_cast, SIP, and `Composite&` source-compatibility impacts.
3. Expand P2.7 to the full `PropertyManager` contract or explicitly change the phase gate. Include named-property iteration/materialization, bit properties, index access, copy/swap/equality, persistence, and object/smart-object fallback.
4. Move side-table migration into `System::adopt` and `System::adoptSubtree` before the flip: composite node/links, property columns/sparse bag, and selected bits.
5. Keep selection tree counters correct in P2 or narrow the phase gate/tests. Deferring parent counter propagation is not compatible with current `Composite::select/deselect` semantics.
6. Recut sub-phases so every commit builds and passes ctest. The inheritance flip must land in the same atomic commit as enough Composite/PM/Selectable forwarding, iterator bridging, adoption migration, and selection propagation to preserve behavior.

## Overall verdict

**NO-GO for P2 as planned.** The memory goal is clear, but the plan currently treats Atom's old bases as isolated APIs. They are also the public tree node type, iterator payload type, RTTI/dynamic-cast surface, selection propagation mechanism, and adoption state boundary. Those cross-class contracts need an explicit design before the inheritance flip can safely start.
